# 1. 失败诊断的脱敏边界

- 状态：已采纳
- 日期：2026-10-02
- 关联：[#4 错误信息返回能力架构地图](https://github.com/FeatherHunter/dsh-plugin-update/issues/4)、[#5 契约 v3](https://github.com/FeatherHunter/dsh-plugin-update/issues/5)、[#6 脱敏边界](https://github.com/FeatherHunter/dsh-plugin-update/issues/6)、[#18 规格](https://github.com/FeatherHunter/dsh-plugin-update/issues/18)

## 背景

[#5](https://github.com/FeatherHunter/dsh-plugin-update/issues/5) 定下了失败回包的形状：稳定错误码之外加一个可选的 `diag` 小诊断块，面板只认稳定码。它同时把脱敏定性为**生成属性**——敏感信息在构造时不产生，不是构造后过滤。

这个票要回答的是那条定性在代码里**具体长什么样**。定这件事时出了两个必须先解决的现实问题：

1. 现存规则和它注释里写下的承诺不一致。`ABSOLUTE_PATH_RE` 的 POSIX 分支只认行首与空白作为前置，而 Node 报告「文件不存在」时路径是用单引号包着的。承诺是"保证回给用户的字符串里不留路径原文"，实现只做到了尽力。
2. 全仓没有"永不外发"清单。令牌、URL 里的账号密码、邮箱、密码键值对，今天全部原样通过。

## 决策

### 1. 脱敏是生成属性，具体为「唯一自由文本出口」

`detail` 是全系统**唯一**的自由文本字段，它只有一个产出口。枚举与数字由类型系统管住，关联编号的形状由生成方式保证，两者都不需要运行时过滤。

**不引入**：运行时事后扫描、逐字段规则清单、完备性检查机制。

理由不是省事。事前扫描看起来是"双保险"，但它自己被自己的顺序规则推翻：先脱敏、再截断，那么截断只做减法，不可能凭空造出秘密——所以"截断后再扫一遍"是多余的。而真正要防的从来不是"有人手搓字符串绕过构造器"（那是一行代码，评审看得见），而是**顺序搞错**，顺序写死就够了。

[#18](https://github.com/FeatherHunter/dsh-plugin-update/issues/18) 已定的「阶段 × 字段期望表」断言本身就是最严格的门禁：新增字段必须回答"它在哪些阶段出现"，加不出静默。再建一个完备性检查是重复。

**但要说清这个门禁由谁执行**：`src/gate.ts` 的 `checkEventFields` 是一个**纯函数**——它读清单、算 `unknownFields`、返回 `{ok}`，**不抛错、不记日志、不被任何生产代码调用**。真正在守日志字段基线的是 `tests/phones.test.mjs` 与 `tests/routes.test.mjs` 里那几条**逐字键集断言**。`gate.ts` 是给别的接入方自查用的尺子，本包自己没有上膛。

同理，`GateEventEntry` 的 `rules`（具名正则名）与 `codes`（截断或散列代号）**目前是纯声明**——全仓没有任何代码读它们，注释里「命中只记规则名不记原文」这个行为也未实现。等五条规则落地时，这两栏要么接上真实现，要么明确标注为「声明格式，校验由测试执行」，**不能留成一份看起来在描述机制、实际是空文的文档**。

### 2. 抓到了之后：定位得到边界就替换，定位不到就整项丢弃

判据是机械的——**秘密片段的起止能否被规则无歧义地定位**。

- 路径终止于空白，定位得到，就地替换成 `<路径>`。
- URL 里的账号密码可能自身含 `@`，起止不唯一，**整项丢弃**。

这条规则最后产出的确实是"丢弃"，说明它不是装饰。

**理由**：被替换过的文本，和本来就没有秘密的文本，在产物上无法区分。诊断的全部价值建立在"读它的人可以相信它"上。替换会把一次泄漏变成一次静默的错——证据被销毁了。而 [#5](https://github.com/FeatherHunter/dsh-plugin-update/issues/5) 的风险顺序把「误导」排在「缺失」前面，替换两头都输：丢了提示看得出，替换了看不出。

占位符只有两个：`<路径>`（[#5](https://github.com/FeatherHunter/dsh-plugin-update/issues/5) 冻结，不动）与 `<脱敏>`（其余全部）。路径是唯一结构上可识别的类别，不值得为每种秘密建一套分类。

### 3. 源信息只给本包认可的源；不给本身是信号

`registryHost` 只给本包认可的源的域名，**不带**账号密码、端口、路径、查询参数。客户端 IP 永不进（[#5](https://github.com/FeatherHunter/dsh-plugin-update/issues/5) 未批准，且对"定位到下一跳"没有帮助）。

不用"内网后缀黑名单"。那份清单会永远漏——真实的内网名有无数种写法——而且清单在，会让人以为已经处理过了，就不再追问。换成"只给认可的源"之后，名单不是新造的长期维护负担，它是"一律官方源"这条既有政策本来就蕴含的一个集合。

**省略本身是信息**：它等价于"这不是官方源"，对上游读者够用，且不泄漏任何东西。注意这条只对程序消费者（面板与测试）自动成立；人读粘贴块读不懂，所以复制渲染有义务把它说成人话（归 #9）。

### 4. 关联编号由本包铸造，形状固定，不做运行时丢格

`requestId` 与 `checkId` 来自同一个生成函数，形状由构造保证、由测试锁死。

这比"校验形状、不合规就不给"好：校验是一条要被维护的缓解措施，铸造是保证——而且**整条校验分支会消失**。

诚实边界：跨宿主那道边的关联只能尽力而为。宿主若用自己生成的编号覆盖 ours，关联就断了——今天也是断的，且不更差。这条不能写成保证。

### 5. 不设运行时扫描，测试当门

产物上做负向断言（"载荷里不得出现秘密形状"）比任何 grep 门禁都强——它验真实产物，不是验某个检查器的意见。grep 门禁因此不建。

## 为什么不是别的做法

| 考虑过 | 为什么否掉 |
| --- | --- |
| 生成完统一扫一遍，违规就遮住 | 同上第 2 条：遮住销毁泄漏证据 |
| 每个字段建一张表，运行时查表 | 枚举、数字、自己生成的编号，类型本身就管住了。为一项自由文本建表是把类型系统做完的事重做一遍 |
| 四层执法（构造器 + 表 + 扫描 + 完备性检查） | 四处都要读、都有各自的错，且最内层经不起推敲（见决策 1） |
| 内网后缀黑名单 | 见决策 3 |
| 自造编号后仍运行时校验 | 校验分支本可整个消失（见决策 4） |

## 后果

**正面**：脱敏规则集中在一处，出问题只有一处可查；"生成属性"这句 [#5](https://github.com/FeatherHunter/dsh-plugin-update/issues/5) 的冻结语在代码里字面为真；没有新增任何一层架构。

**代价**：

- 将来加字段的人必须走同一条出口，靠代码评审保证——这是**用评审换代码量**的自觉取舍，不是遗漏。
- "省略即信号"要求复制渲染配合，否则这条隐私编码对人不可读。这条义务记在 #9。
- 跨宿主关联不是保证，只是尽力。

## 已知未覆盖

- **`file:///tmp/x`** 三斜杠形状会被当成 URL 放过（`file://` 的前置带着冒号）。属同一类泄漏，本轮未实测到具体输入，不在本次修复范围。
- **UNC 反斜杠形状 `\\server\share`** 现有规则接不住，Windows 分支只认盘符形状。POSIX 斜杠形状 `//server/share` 已在本轮修好（见下「修复记录」），反斜杠形状未实测到输入，留给规格阶段连同五条规则一并处理。
- **`manualCommand` 的 registry 原样拼接**（`src/commands.ts:188-207`）：集成方传入的地址未经处理就进到用户要粘到终端、工单、issue 的命令串里。修法里藏着一个未回答的产品问题（带账号密码时整个 `--registry=` 标志不写，还是只写域名？），不是正则问题，留给规格。
- **诊断块的字节上限**：`detail` 300 字在中文下就是 900 字节，离 #5 说的「深证据分界 1KB」只差 100 字节。#5 明写过线要另立电话、另走破冰，而**本票未主动上报 #10，需补报**。

## 与 README 的张力（需产品决定，本票不代决）

`README.md:260` 教用户：`message` 形如 `install-failed: <宿主原话>`，并说「`message` 可能带详情」。

但 #5 冻结的是「`diagnostic` 永指宿主脏原文、永不过边界」，而当前实现里**真实存在的唯一诊断通道恰恰就是宿主原话**（经 `sanitizeDetail` 收过一遍，不是全原样）。

于是有一个问题本票答不了：**README 是在教一个有意保留的逃生口，还是历史遗留？**

- 若是**有意保留**——它必须被登记为一条明确的、有边界有措辞的例外，而不是靠"脱敏兜一下"含糊过去；下游做 `detail` 口径时不能顺手把它收紧。
- 若是**历史遗留**——它与 #5 的冻结口径直接冲突，需要走破冰改 README。

按 `AGENTS.md`，README 是面向集成方的用户手册、不放设计意图，所以本票未改动它。**但这是下游做 `detail` 口径前必须先解开的前置。**

## 修复记录（2026-10-02 本轮）

修 `ABSOLUTE_PATH_RE` 时踩过一个自己挖的坑，记在这里免得重犯：

第一版用 `(?!\/)` 保住 URL，**结果把 UNC 形状 `//server/share` 也放过了——而旧规则本来能掩它**。用「有没有两个斜杠」当判据是错的：URL 的 `://` 和 UNC 的 `//` 在字符上无法区分。

正确判据是**双斜杠出现在什么位置**：行首或空白/括号之后的是 UNC，要掩；前置是冒号（`://`）或字母（`http://a.com/x//y`）的不是。改成按位置判据后，UNC 掩掉、URL 两种形状都原样保留。

**验证方式**：穷举全部前置字符（空白、引号、括号、方括号、逗号、冒号、等号、字母、数字、分号、连字符、全角引号括号逗号冒号、@、>）× 尾部形状，**新规则掩不掉而旧规则能掩的输入为零**，另有 49 种旧规则原本漏掉的组合现被覆盖。

**教训**：收紧一条安全规则时，必须拿新规则去比对**旧规则能覆盖的全部输入**，只测新加的用例会漏掉自己制造的回归。已固化进测试（UNC 行首/空白后两条 + URL 路径内多斜杠一条）。

另外，路径规则里的「不误伤」测试**只管路径规则不越界**，不代表别的秘密形状可以原样通过——带账号密码的 URL 属于待修的五条规则，尚未实现，**没有写进不误伤组**，免得把一个待修的泄漏钉成期望值。

## 术语

本票沉淀的词已进 `CONTEXT.md`，但**只收已定的**：`detail`（人话格，永为字符串）、`diagnostic`（宿主原话，永不过边界）——两者近乎同名，是本 ADR 存在的直接原因；以及「源地址 ≠ `registryHost`」这条纠正。

`诊断块（diag）`、`源主机名（registryHost）`、`动作提示（action）`、`稳定码`、`破冰` **在 `CONTEXT.md` 里明确标注为「待规格确认后补入」**——它们目前是尚未批准的设计，不是仓库的既成语言。**提前把规格写成词表，会让将来的规格改动变成"与仓库说法冲突"，这正是词表要避免的事。**
