## 0. 结论摘要

1. **「从未安装」与「装了但坏」在现有模型里不可区分——都是同一个 `blockedReason: 'invalid-installation'`**。目标目录不存在时 `src/reader.ts:317` 的 `packageAt` 抛（`:37-40` 的 `readFile`），被 `:318-321` 的 catch 一口吞掉，直接 `return result`；而「装了但坏」走 `:345` 的 `!validPackage` 分支，**赋值完全相同**，且没有第二个字段标出「目录压根不在」。证据：`src/reader.ts:37-40`、`:315-321`、`:345`、`src/ports.ts:169-181`（`EnvironmentView` 没有 not-installed / missing 字段）。
2. **`canInstall` 对缺席目标恒假，而且是「多把锁同时锁死」**。`src/service.ts:641-648` 五个与门里 `env.eligible`（`reader` 里由 `eligible = !blockedReason` 算出，`:352`）与 `!blockedReason` 直接为假，`checked?.installationKey === env.installationKey` 也因 `env.installationKey === null`（`reader.ts:293` 初值、`:318-321` 提前 return 未赋值）而为假；`newer` 反而**为真**（`0.3.54 > 0.0.0`，`src/service.ts:631-640`）。所以「比对的是哪个版本」在这里不是卡点。
3. **批量面板的 `invalid-installation` 来自「查」这一步，不是「装」这一步**。`src/host-batch.ts:513-534` 的 `defaultCheck()` 在 `canInstall !== true` 时返回 `{ kind: 'failed', error: blocked }`，`blocked` 就是目标自己的 `blockedReason`；`src/batch-run.ts:162-167` 把它记进账本 `phase: 'failed'`。**安装根本没被提交过**。假设「安装路径把阻塞原因原样抛出」在防线 2 上成立（`src/service.ts:880-882`），但对本现象**不是**成因——它到不了。
4. **`row.error` 的取值域把「查失败」与「装失败」合并了**：`batch-run.ts:163-164`（查失败）与 `:201-202`（装失败）写的是同一个 `phase: 'failed'` + `error: <码>`。所以从账本与面板**无法反推是哪一步失败的**；反过来，`invalid-installation` 这个码**只能**出现在查那一步（装那一步永远拿不到它，见 §4.3 证明）。
5. **`0.0.0` 是消费者常量，不是本包算的**：本仓 `src/` 全树只有测试夹具里出现过 `0.0.0`（`tests/issue-100-prerelease-install.test.mjs:36`、`tests/target-resolution.test.mjs:51`、`tests/issue-98-channel-mismatch.test.mjs:51,246`），源码零命中。真出处是 `D:\ilife\packages\plugin-manager\src\update-batch.ts:13` `export const MISSING_RUNNING_VERSION = '0.0.0' as const;`，经 `:26-29` 与 `:74` 注入每个目标的 `readerOverrides.runningVersion`。面板的 `currentVersionOf` 运行版优先（`src/panel-batch.ts:1349-1357`），于是把 `'0.0.0'` 当成"当前版本"画出来。
6. **`0.0.0` 不只是观感问题：它是合法发行版串**，因而**骗过了通道门**。`src/service.ts:103` 的 `validVersion` 只判三段形状、`:149-151` 的 `isVersionAllowedInChannel`（stable 通道）就是 `validVersion`，所以 `'0.0.0'` 一路为真，`newer` 因此算出真（`:631-640`）。消费者用「读不到就填 0.0.0」把「未知」伪装成了「一个很旧的正常版本」。
7. **真正阻断全新安装的最终一行是 `src/host-batch.ts:531-534`**（批量侧）；单插件侧对应的最终一行是 `src/service.ts:880-882`；两处的**根**都是 `src/reader.ts:317-321` 的提前 return——`readInstalledReal` 在「目标包不在」时**直接把整个环境判死**，后面所有闸门只是转述它的结论。
8. **没装的包不存在任何一条能走通的路径**：`ready` 相位只能由「查成功且 `canInstall === true`」产生（`src/batch-run.ts:181-183`），而 `canInstall` 恒假 ⇒ 安装步骤（`src/batch-run.ts:189-191`）对缺席目标**结构性不可达**。仓内也没有任何「全新装」代码路径（`src/service.ts:865-882` 全程是更新语义）。

## 1. `src/reader.ts`：目标包不存在时 `EnvironmentView` 长什么样

### 1.1 三条读取路径与它们的汇合点

`src/reader.ts:283-321`（`readInstalledReal` 的开头）：

```ts

285:      profileName: null,
286:      environmentKind,
287:      homeDir: null,
288:      profileDir: null,
289:      installedVersion: null,
290:      packageValid: false,
291:      sourceInstall: false,
292:      blockedReason: null,
293:      installationKey: null,
```

`packageAt` 本体（`src/reader.ts:37-40`）：

```ts
37: async function packageAt(directory: string): Promise<{ directory: string; manifest: Record<string, unknown>; contents: string }> {
38:   const contents = await readFile(join(directory, 'package.json'), 'utf8')
39:   return { directory: await realpath(directory), manifest: JSON.parse(contents) as Record<string, unknown>, contents }
40: }
```

抓得住的事实：

- `packageAt` 只做两件事：读 `join(directory, 'package.json')` 与 `realpath(directory)`。目录不存在 ⇒ `readFile` 抛 `ENOENT`；文件存在但 JSON 坏 ⇒ `JSON.parse` 抛 `SyntaxError`；目录在但 `package.json` 缺 ⇒ 也是 `ENOENT`。**三种都被 `:318` 的同一个 catch 接住**，代码里没有任何 `error.code` 判别（对比 `:32` 的 `readOptional` 是判 `ENOENT` 的，说明作者会判别、这里没判）。
- `:317` 的目标目录是 **`join(profileDir, 'node_modules', targetPackageName)`**——按 pnpm `hoisted` 布局直读，**不走 `createRequire`、没有 hoisted 多副本兜底、没有 `targetPackageDir` 回退**（自动解析的那套 `resolveTargetPackage` 在 `:78-89` 注释里写得很清楚，但 `readInstalledReal` 这一处用的是最朴素的直读路径）。

### 1.3 决策梯（`src/reader.ts:342-353`）逐级与缺席目标的关系

```ts
342:    if (boundIdentity !== undefined && boundIdentity !== identity) result.blockedReason = 'installation-changed'
343:    else if (loadedUnresolvable) result.blockedReason = 'unknown-profile'
344:    else if (!sameLoadedPackage && boundIdentity === undefined) result.blockedReason = 'installation-changed'
345:    else if (!result.packageValid) result.blockedReason = 'invalid-installation'
346:    else if (result.sourceInstall) result.blockedReason = 'source-install'
350:    else if (!isVersionAllowedInChannel(result.installedVersion, releaseChannel)) result.blockedReason = 'channel-mismatch'
351:    else if (result.installedVersion !== runningVersion) result.blockedReason = 'pending-restart'
352:    result.eligible = !result.blockedReason
353:    result.blockedReason = result.blockedReason ?? null
```

- 缺席目标**整条梯子都没走**：它在 `:318-321` 就 `return` 了，`:342-353` 一行都不执行。换句话说，梯子上的 `unknown-profile`（定位不到目标包）这一档**是给「包装着、但本包认不出它在哪」准备的**（注释 `:327-328` 写得很明白：「到这里已装包真实存在，是"本包认不出目标"而非"安装位置变了"」）——**「目标压根没装」反而被更早的 catch 抢走了**，落成语义最不贴切的 `invalid-installation`。
- 梯子的顺序意味着：即便让它走完，缺口目标也会连撞两档（`:345` 与 `:350`/`:351`），但只会记第一档。
- `:352` 的 `eligible = !blockedReason` 是**唯一**的 eligible 来源，所以「有阻塞原因」与「不可装」在这个模型里是同义词。

### 1.4 「从未安装」与「装了但坏」可区分吗？

**答：不可区分（No）。** 三条代码事实：

1. `blockedReason` 的落点相同且**无附加标记**：`:319` 与 `:345` 都写 `'invalid-installation'`；`EnvironmentView`（`src/ports.ts:169-181`）里没有 `installed` / `present` / `directoryMissing` 之类的字段，`blockedReason` 的取值域（`src/ports.ts:50-59`）**也没有 `not-installed` 这一档**。
2. 能替它们区分的三个字段各有各的不可靠：`installedVersion`（null 可能是「目录不在」也可能是「清单没版本字段」）、`installationKey`（null 可能是「提前 return」也可能是「sha256 算失败」，见 `:339-341`）、`packageValid`（两者都是 false，且初值本来就是 false）。
3. 面板上的文案也一样：`src/bilingual.ts:383` 的标题 `已安装包结构不完整（包名 / 版本号 / 入口文件异常）` 是这两个状态**唯一**的用户可见说法——对「压根没装」的包说「已安装包结构不完整」，本身就是错位。

> 一句话：今天是「一个笼统的安装不完整」把「缺席」和「损坏」一起装了。

## 2. `src/service.ts`：为什么 `canInstall` 对缺席目标永远不为真

`buildSnapshot()`（`src/service.ts:619-660`）里的 `canInstall` 表达式（`:641-648`）：

```ts
641:    const canInstall = Boolean(
642:      env.eligible &&
643:        !blockedReason &&
644:        !busy &&
645:        fresh &&
646:        checked?.installationKey === env.installationKey &&
647:        newer,
648:    )
```

缺席目标下**逐条**：

| 子式 | 值 | 依据 |
|---|---|---|
| `env.eligible` | **false** | `src/reader.ts:294`/`:352`（提前 return ⇒ 保持初值 false） |
| `!blockedReason` | **false** | `blockedReason = env.blockedReason ?? ...`（`src/service.ts:620`）= `'invalid-installation'` |
| `!busy` | true | `busy = job?.state === 'installing' \|\| 'verifying'`（`:626`），缺席目标没有任务 |
| `fresh` | 取决于有没有查过 | `= checked !== null && checked.checkId !== null && ports.now() < checked.expiresAt`（`:627`） |
| `checked?.installationKey === env.installationKey` | **false（null === null 之外的情况全假）** | `checked.installationKey` 是查那一刻读到的（`:771`）；缺席目标读到的就是 `null`，而 `env.installationKey` 也是 `null` ⇒ **这一条在「查的瞬间也是缺席」时会相等**……但只要 `checked === null` 或 `installationKey` 为 undefined 就假。见下注。 |
| `newer` | **true** | `:631-640` |

> 注（严谨起见）：Python 式地看，`checked?.installationKey === env.installationKey` 在「查时缺席、装时仍缺席」时是 `null === null` ⇒ **真**。所以真正把它按死的是**前两条**（`env.eligible`、`!blockedReason`）。`:646` 这一条只在「查时包在、装时包没了」这类**状态漂移**里起作用——那时它变成 `false` 并抢在 `:880-882` 之前抛 `installation-changed`（见 §3.3）。

`newer` 的来源（`:631-640`）：

```ts
631:    let newer = false
632:    try {
633:      newer =
634:        isVersionAllowedInChannel(runningVersion, releaseChannel) &&
635:        !!checked?.release &&
636:        isVersionAllowedInChannel(checked.release.version, releaseChannel) &&
637:        compareReleaseVersions(checked.release.version, runningVersion) === 1
638:    } catch {
639:      newer = false
640:    }
```

**比对的是「远端发布版 vs 运行版」（不是磁盘版，也不是任何别的版本）**：`runningVersion = ports.readRunningVersion()`（`:628`）。而 `readRunningVersion` 的实现在宿主侧是**消费者注进来的常量**（`src/reader.ts:358` `readRunningVersion: () => runningVersion`，`runningVersion` 来自 `UpdateReaderOptions.runningVersion`，见 `:215`），消费者给的是 `'0.0.0'`（见 §5）⇒ `compareReleaseVersions('0.3.54', '0.0.0') === 1` ⇒ `newer = true`。

**所以对缺席目标，闸门的位置很反直觉**：「有没有新版」这一问答案是"有"，真正卡死的是「这台机器上这份安装是不是完整、能不能动手」（`eligible` / `blockedReason`）。`installedVersion`（磁盘版，`:651` 进快照）在 `newer` 的比较里**根本没参与**——这是本包"更新语义"的核心假设：**运行版就是已装版**。一旦这个假设被消费者的占位值打破（`0.0.0`），「未知」就被读成了「很旧」。

派生影响：`updateCheck` 电话只在 `snapshot.canInstall` 为真时才发凭证（`src/service.ts:786` `return { snapshot, receipt: snapshot.canInstall ? toReceipt() : null }`，同口径 `:750`），所以缺席目标**永远拿不到 checkId**——批量驱动器的 `defaultCheck` 因此在 `defaultInstall` 里还会再失败一次 `check-expired`（`src/host-batch.ts:584-586`），但那条路走不到（见 §4）。

## 3. `src/service.ts`：安装入口与它吐出的错误码

### 3.1 安装入口 `install()`（`src/service.ts:865-894`）的闸门顺序

```ts
865:  async function install(args: { checkId: string; requestId: string; from?: InstallSource }): Promise<UpdateSnapshot> {
866:    const checkId = typeof args?.checkId === 'string' ? args.checkId : ''
867:    const requestId = typeof args?.requestId === 'string' ? args.requestId : ''
868:    if (!checkId || !validRequestId(requestId)) throw updateError('check-expired')
869:    let env = await ports.readInstalled()
870:    let previous = healJob(await loadJob(), env)
872:    if (previous?.requestId === requestId) return buildSnapshot(env, previous)
873:    if (previous?.state === 'installing' || previous?.state === 'verifying' || previous?.state === 'restart-required') {
874:      throw updateError('update-busy')
875:    }
876:    if (!checked || !checked.checkId || checked.checkId !== checkId || ports.now() >= checked.expiresAt) {
877:      throw updateError('check-expired')
878:    }
879:    if (env.installationKey !== checked.installationKey) throw updateError('installation-changed')
880:    if (!buildSnapshot(env, previous).canInstall) {
881:      throw updateError(env.blockedReason ?? checked.blockedReason ?? 'update-busy')
882:    }
```

**用户给的假设，逐字对照 `:881`：成立，但它在链路上是第二道防线。** `:881` 的表达式 `env.blockedReason ?? checked.blockedReason ?? 'update-busy'` 就是「把目标自己的阻塞原因原样抛出」：

- `env.blockedReason`：本次读到的环境（缺席 ⇒ `'invalid-installation'`，`reader.ts:319`）。
- `checked.blockedReason`：**只可能是 `'incompatible-node'` 或 null**——`:766-773` 里它唯一的赋值是 `blockedReason: satisfiesNodeRange(ports.nodeVersion, release.nodeRange) ? null : 'incompatible-node'`。所以这一路**永远不会**给出 `invalid-installation`。
- `'update-busy'`：三者都空时的兜底（`:880` 已判 `canInstall` 为假、又无阻塞原因 ⇒ 只能是「没新版」「不新鲜」「安装指纹变了」这类）。

⇒ 对缺席目标，安装路径**会**抛 `invalid-installation`——**前提是它拿得到一张有效凭证并活到 `:881`**。而它拿不到（`canInstall` 恒假 ⇒ `:786` 不发凭证 ⇒ 批量侧 `defaultCheck` 先失败）。这正是「第一道防线」与「第二道防线」的关系。

### 3.2 装后校验（`src/service.ts:809-863`）与本题的关系

`:813` `await ports.runInstall({ version: job.targetVersion as string, profileName: ..., environmentKind: ..., releaseChannel })` → `:815-817` 记 `verifying` → `:818-819` 重读环境 → `:821-825` 校验磁盘版本、`:826-828` 校验阻塞原因、`:829-830` 记 `restart-required`。失败时 `:839-858` 把 `code: 原话` 拼进 `job.message`（`:846`）。

对缺席目标**这段也到不了**（要先过 `:880`）。但它解释了失败码体系里的另一半：`job.message` 的形状是 `「失败码」或「失败码: 详情」`（消费方按**前缀码**匹配，`README.md` 第 12 节口径，代码注释在 `:843-844`）。

### 3.3 「装那一步给出 `invalid-installation`」可能吗？（用于 §4.3 的反证）

### 4.3 「一行能靠**装**那一步得到 `invalid-installation` 吗？」——反证

**批量侧（`全部更新` 的驱动）**：安装步骤（`src/batch-run.ts:187-191`）只在两种情形下被执行：

- 情形 a：本次 `check` 返回 `kind:'update'` ⇒ `:181` 记 `ready` + `targetVersion` ⇒ `:189-190` 提交安装。而 `kind:'update'` 要求 `canInstall === true`（`host-batch.ts:531` 是必经的反向门）⇒ 缺席目标做不到。
- 情形 b：**从盘上读到的会话里那一行已经是 `ready` 且带 `targetVersion`**（`:154` `let version: string | null = entry.phase === 'ready' && entry.targetVersion ? entry.targetVersion : null` ⇒ 跳过查、直奔 `:189`）。这是「消费者预先喂了 `targetVersion`」在代码里唯一的落点。

对情形 b 追一遍（消费者确实是"先查再全装"的形态：批量面板挂载时 `batchCheck`、点「全部更新」时 `batchInstall`）：

- 若那行是**上一次查成功后**落在盘上的 `ready`，说明当时 `canInstall === true` ⇒ 那次查的时候包是完整的、有版本的 ⇒ 与"从未安装"矛盾。消费者对六家单品的 `runningVersion` 恒为 `'0.0.0'`（§5），也不可能在某次查里变真。
- 假设有人**手改盘上账本**塞一个 `ready` + `targetVersion: '0.3.54'`：`batchInstall` → `driveLocked` → `checkByKey` 被跳过 → `installByKey`（`src/host-batch.ts:1021-1030`）→ `defaultInstall`（`:580-606`）⇒ `rt.receipt` 为 null ⇒ 先 `rt.check` 重查 ⇒ 仍是 `failed` ⇒ `:584` `return { kind: 'failed', error: again.error }` = **`invalid-installation`**……等等，这一条**恰好也能给出同一个码**。

**这里必须诚实**：情形 b 下，`defaultInstall` 的 `:582-586` 会**重查一次**，把 `defaultCheck` 的失败码原样返回：

```ts

584:    if (again.kind !== 'update') return { kind: 'failed', error: again.kind === 'failed' ? again.error : 'check-expired' }
```

⇒ 但请注意：**这个码仍然是从「查」来的**（`:583` 就是 `defaultCheck`），不是从 `service.install()` 来的。所以「装那一步给出 `invalid-installation`」在批量侧**依然不成立**：批量侧得到这个码的**唯一**来源是 `defaultCheck` 的 `:531-534`（或它在 `defaultInstall` 里的重入）。

**单插件侧（被别的调用方直接打 `updateInstall`）**：要过 `service.install()` 的 `:876-878`（凭证）——而 `defaultInstall` 之外的调用方拿到凭证的唯一途径是 `updateCheck` 的 `receipt`，同样要求 `canInstall === true`。⇒ 单插件侧也拿不到「从安装路径吐出的 `invalid-installation`」，除非 §3.3 那个极端巧合。

### 4.4 面板为什么会把「查失败」画成「安装失败」
