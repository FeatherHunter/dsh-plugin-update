## 二、B3 判定：通过

1. **只合并相对 baseline 真变过的行**：`registry.ts:393-412 mergeBatchSessions` —— `395-400` 用**对象引用恒等** `baselineByKey.get(key) !== entry` 求 `changedKeys`；`403-409` 只在 `base.entries` 上替换这些 key，其余行与顺序原样保留；`394` id 不同或 patch 视图为空直接回 `base`；`410` 无实变更回 `base`；`411` `updatedAt` 取两者 max。
2. **引用恒等前提成立**：`src/core/batch/run.ts:198-202` persist 直接 `current = next`；`src/core/batch/model.ts:256-267 markBatchEntry` 用 `[...slice, next, ...slice]` 只替换被改对象，其余 entry 引用不变 → 未动行在 baseline/patch 里恒等。
3. **收尾以合并后的盘上会话重判**：`registry.ts:318-323` save 回调先 `fresh = await task.seat.readSession()`，再 `mergeBatchSessions(fresh, next, baseline)` 落盘；`331` 每步后 `session = await task.seat.readSession()`；`333-334` 重算 `scoped`/`scopeFinished`；`337 mergedStopped`：runBatch 报 `finished`/`stopped-after-failure` 但 scope 未终态时降级为 `max-steps` 继续推（即**不信** runBatch 的收尾结论）；`342-345` `queued` 不计 idle；`347-366` 据此输出 continue/yield/fail/done。
4. **行级 selection 收尾**：同 `333-334`，只按选中范围判，不按整批失败总账判。

实跑证据：

## 五、剩余风险（未覆盖，按担心程度排序）

1. **不是真多进程**：takeover 用 `__resetHubRegistryForTests()` 模拟重启（`tests/hub-takeover.test.mjs:84-87`），死进程只用 pid 999999 同进程模拟；真实「进程被杀 → 另一进程接管」的租约/半写文件时序未验证。
2. **坏进程租约与时钟**：租约过期、进程挂住不释放、系统时钟跳变只靠假时钟 `advance()` 间接覆盖（`tests/hub-takeover.test.mjs:24-60`），真实 5s 心跳时序未压测。
3. **Windows 文件占用/rename 竞争**：`saveSession` 原子写在共享冲突（AV/索引器占用）下的重试路径未压测；本次并发只覆盖「写成功」路径。
4. **合并口径依赖对象引用恒等**：`mergeBatchSessions` 靠 baseline 与 step 视图的 entry 引用比较来判「真变行」；当前 `runBatch`/`markBatchEntry` 保持引用（`run.ts:198-202`、`model.ts:256-267`），但未来若在视图层深拷贝/序列化，会退化成「全行视为变化」→ 静默回到整份覆盖式 B3。建议加一条锁住引用恒等前提的单测（或改成显式 dirty 集合）。
5. **session id 切换**：`registry.ts:394` 遇 `patch.id !== base.id` 直接回 base；若并发写者取消并新开一批，飞在空中的 step 结果被丢弃，此时中枢任务仍在旧 id 上驱动新盘面——行为未定义、未测。
6. **其余未测**：`stopOnFailure=true` × selection 交互；`hub:false` 的 drain 与中枢双驱动（drain 默认关，`fan-out.ts:1173-1218`）；面板忙态文案；真实装包后 `restartRequired` 的重启链路（全部用 fake transport）。
7. **平台**：只在 Windows 实跑；Linux/macOS 的 rename/租约占位语义未验证。
