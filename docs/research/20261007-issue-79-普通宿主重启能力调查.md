# 普通 DSH 宿主重启能力调查（#79）

> 日期：2026-10-07（Asia/Shanghai）｜触发：父图 #75 Destination 决策依赖，本票为 #80 终裁的前置调查（先调查不做实现）。结论先行，证据在后。
> 方法：只认一手来源（本仓源码、宿主生成物行号、第一方 API 形状）；拿不准写“未证实”，不行号编造。宿主取证对象为本机 DSH `0.2.0-rc.2`（`D:/DeepseekHarness/resources/app.asar`，在本机是**目录**不是单文件档案，可直接读）。

## 结论摘要

- **C1 CLI 无重启/重载子命令**：`dsh` 顶层只有 `profile(boot)`、`plugin`、`dump-config`、`dump-config-schema` 四种 mode（bin.js:211-249），`program.command` 只注册过 `plugin`（bin.js:116）。`dsh/lib` 全目录 grep `restart|reload|relaunch` 零重启语义命中，只有进程关闭（shutdown）逻辑。
- **C2 普通宿主“重启整个 DSH”唯一现实路径是进程级重起（re-boot），CLI 内无近路**：`runProfile` 只返回 `{ ctx, shutdown }`（profile-boot-BZ2ZjNWi.js:284-287），`shutdown` 只会退出进程（process-shutdown，5s 宽限，见该文件 :9-30）；桌面宿主 IPC 也只有 `shutdown` / `quit-inspection`，无 restart/relaunch（desktop-host/lib/index.js:263-294）。
- **C3 argv 复用技术上成立、契约上缺件**：本包安装路已证明“当前运行时＋运行时参数＋CLI 入口＋参数数组”形态可跑（src/store.ts:1130-1156，executable 取 `process.execPath`、execArgs 取 `process.execArgv`、entry 靠 `resolveCliEntry(process.argv[1])`，见 :1135-1139）。但重启要的是 **boot 参数**（profile 名、--patch、app args），本包从未捕获（只拼过 `plugin …` 安装参数，见 :1141），且 `subprocess.spawn` 注入形只收 `{ argv, cwd, stdio, graceMs }`（:1142-1151），无 detached/父退子留语义——重起进程能 spawn，**交接（旧进程何时退、新进程 stdio/生命周期谁管）无契约**。
- **C4 profile 重载 ≠ 进程重启，且与普通宿主安装路无关**：进程内重载靠 `hmr` 服务的 `reconcileProfilePatches`（plugin-manager/lib/index.js:2031-2034），无 `hmr` 时 `reload()` 直接返回 `[]` 且 `change()` 默认 `application: 'restart-required'`（:2035-2043）。普通宿主安装走**异进程 pnpm**（cli-process），不经过 `reload()`；官方 `plugin_manager` 工具自述 “Live profiles apply changes immediately; startup profiles require restart”（plugin-manager/lib/types/tools.js:14）——落到 `restart-required` 即等于“请用户重启整个应用”。
- **C5 desktop 禁令不影响普通宿主，但划清了路由边界**：`dsh` 在 boot 与 `plugin` 双处按名（大小写不敏感）拒绝 `--profile desktop`（bin.js:35-37、:112、:119），唯一豁免是桌面自带 CLI 载体 `manageDesktopProfile: true`（desktop-host/lib/cli.js:91-104）。普通 profile 名不受影响；本包出口三因此永不接 `desktop`（docs/host-install-exits.md:61-68，src/host.ts:227-247）。
- **C6 给 #80 的建议：规格先行、提案后行**：规格里把“待重启＝手动重启＋`onRestartRequested` 唯一接缝”定为默认（三路由统一）；提案后行，先提 **CLI 重启说明或宿主侧重启电话**（见 §6）。本票不产交付代码。

## 2 CLI 重启/重载子命令：有无

**结论：无。**

- 顶层 mode 穷举：`runCli` 的 switch 只有 `profile` / `plugin` / `dump-config` / `dump-config-schema`（`D:/DeepseekHarness/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh/lib/bin.js:211-249`），顶层 `program.command()` 只注册 `plugin`（bin.js:116）；`plugin` 的子动作只有 pnpm 透传与 `allow-version/revoke-version/version-exemptions`（plugin-BGnVfe_D.js:14-56），无 restart/reload/relaunch。
- 全目录 grep：对 `…/@deepseek-ai/dsh/lib` 执行 `restart|reload|relaunch|reboot`（大小写不敏感）逐行匹配，命中仅 `profile-boot-BZ2ZjNWi.js` 的进程关闭逻辑（:9-30 `createProcessShutdown`、:244-253 信号处理、:278 `exit`)，**无任何重启语义**。
- 跨包互证：`dsh-desktop-host/lib` 同 pattern 命中仅 `index.js:259-265` 的 `shutdown` 停机握手；宿主 CLI 载体 `desktop-host/lib/cli.js:91-104` 只做 `manageDesktopProfile: true` 豁免透传，无新增命令。
- 复跑（Node，不经 PowerShell——路径含 `@` 时 PowerShell 通配会截断，见本次调查记录）：
  `node -e "const fs=require('fs'),path=require('path');const w=d=>fs.readdirSync(d,{withFileTypes:true}).flatMap(e=>e.isDirectory()?w(path.join(d,e.name)):[/\\.js$/.test(e.name)?path.join(d,e.name):null].filter(Boolean));for(const f of w('D:/DeepseekHarness/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh/lib')){fs.readFileSync(f,'utf8').split('\\n').forEach((l,i)=>{if(/restart|relaunch|reboot/i.test(l))console.log(f+':'+(i+1)+':'+l.trim().slice(0,120))})}"` —— 预期零重启命中（仅 shutdown）。

## 3 进程级重启手段可行性

### 3.1 argv 复用：成立（安装路已实证）

- 本包 cli-process 路即 argv 复用范本：`executable = process.execPath`、`execArgs = process.execArgv`、`entry = resolveCliEntry(process.argv[1])`（src/store.ts:1135-1139），再拼参数数组经注入的 `subprocess.spawn` 起进程（:1141-1151）。同一三元组把 `['plugin','--profile',…]` 换成 **boot 参数**（`--profile <名> [--patch …] [app-args…]`，语义见 bin.js:40-49 HELP_EXAMPLES）即“重启整个 DSH”的形态——**形态成立**。
- 缺件：本包从未捕获 boot 参数（recipe 只存安装用的 `pluginArgs`，见 src/commands.ts:172-178；ExecutorParts 无 bootArgs 零件，见 src/store.ts:900-917）。没有“当初怎么起来的”记录，重启命令拼不出——**需规格新增或宿主回传**。
- 复跑：读 src/store.ts:1130-1156 与 src/commands.ts:127-180；对照 bin.js:40-49 的 boot 示例。

### 3.2 subprocess.spawn 注入约束：能起进程，不能交接

- 注入形钉死：`spawn(opts: { argv: string[]; cwd?: string; stdio: unknown; graceMs: number }) => { done }`（src/store.ts:1142-1144），stdio 实参固定 `INSTALL_STDIO = { stdin:'ignore', stdout:{maxBytes:64k}, stderr:{maxBytes:64k} }`（:783），等待/杀树逻辑在 `awaitOutcome`（:870-896）。
- 推论：spawn 一个**长命的重启后进程**与现有“起 pnpm 短进程、等退出、判 exitCode”（:1153-1155）是两种生命周期。旧进程何时退出、新进程输出接哪、谁负责 detached/orphan、超时杀树会不会误杀新进程——**全部无契约**，强行复用等于把安装执行器当进程守护用。
- 复跑：读 src/store.ts:870-896（awaitOutcome 超时杀整棵树）＋:1146-1155（spawn 调用点）。

### 3.3 Windows/POSIX 差异：安装路无分支，重启路差异未验证

- 安装路注释明示“三系统同一套形态，差异只在可执行文件与入口由适配器提供”（src/store.ts:1172-1176），不按系统分支。
- 但重启涉及的恰是系统相关面：`profile-boot` 只注册 `SIGTERM/SIGINT`（profile-boot-BZ2ZjNWi.js:249-254），Windows 控制台信号另由桌面 CLI 载体经 koffi 补（desktop-host/lib/cli.js:106-110，仅桌面载体）。普通宿主在 Windows 下重起进程的信号/控制台语义——**未证实**（见 §7 U3）。
- 复跑：读 profile-boot-BZ2ZjNWi.js:244-257（信号）与 desktop-host/lib/cli.js:106-113（Windows 信号补丁）。

### 3.4 profile 重载 vs 进程重启：两回事，后者是普通宿主的唯一现实选项

- 进程内重载 `= hmr + reconcileProfilePatches`：`reload(requiredIds)` 无 hmr 时直接 `return []`（plugin-manager/lib/index.js:2031-2034）；`change()` 在无 hmr 时默认 `application: 'restart-required'`（:2035-2043）；`removeBundle` 无 hmr 且 bundle 在用时直接抛 `stop-profile`（:1849）。
- `hmr` 与 `pluginManager` 只在有 `profileContext` 的 profile 内挂载（dsh-base/cordis.patch.yml:22、:30），且 `hmr` 监听的是**配置文件**（hmr/lib/index.js:45-107 watchConfig），不是异进程 pnpm 装进来的 `node_modules`。普通宿主安装路（cli-process）装完后**没有任何 `reload()` 调用**——重载这条路对它不存在，能选的只有进程重启。
- 第一方自述互证：`plugin_manager` 工具描述 “Live profiles apply changes immediately; startup profiles require restart”（plugin-manager/lib/types/tools.js:14）。
- 复跑：读 plugin-manager/lib/index.js:2031-2057（reload＋change）、hmr/lib/index.js:1-107（watchConfig 只看配置文件）、cordis.patch.yml:20-32（挂载条件）。

## 4 desktop 禁令影响

**结论：对普通宿主重启调查无阻断，只划边界。**

- 禁令原文：`rejectElectronProfile` —— `profile.toLowerCase() === "desktop"` 即 `program.error`（bin.js:35-37），boot（:112）与 plugin（:119）双处调用；唯一豁免 `manageDesktopProfile: true` 由桌面自带 CLI 载体传入（desktop-host/lib/cli.js:91-104，含 pnpm 载体与 `ELECTRON_RUN_AS_NODE` 环境）。
- 对本包：出口三对 `desktop` 名“一定失败”（docs/host-install-exits.md:61-68），宿主判定 `cliRefusesProfile` 逐字同判据（src/host.ts:244-247），`detectEnvironmentKind` 顺序固定 desktop → desktop-manager → cli（:227-233）。普通 profile 名（非 desktop）走 cli-process 不受任何影响；重启调查只需覆盖“非 desktop 名”，禁令不缩小结论。
- 复跑：读 bin.js:35-37、:106-127；读 desktop-host/lib/cli.js:91-104；读 src/host.ts:215-247。

## 6 给 #80 的建议：规格先行、提案后行

1. **规格先行（#80 直接可定）**：把“待重启＝手动重启”定为三路由统一默认语义；把 `onRestartRequested`（面板调它，成败都回执；没给就如实提示手动重启——panel.ts:2560-2575、panel-batch.ts:1866-1879）正式定为**唯一的重启接缝**。不新增任何电话/子命令/零件，不碰冻结项。
2. **提案后行（带本调查证据去谈，顺序建议）**：
   - (a) 请 DSH CLI 明确“装完是否需重启”的官方查询方式（例如 `plugin` 结果里带应用态，或文档化 pending-restart 判定），消除本包“靠 `restart-required` 猜”的现状；
   - (b) 请宿主补一个受控重启原语（二选一：CLI 的重起说明，或宿主侧重启电话/进程原语，含 detached 与 stdio 交接语义），普通宿主 cli-process 才有第二条路；
   - (c) 第三方 Desktop 的重启能力问桌面宿主（本包无证据，不代答）。
3. 先提 (a)——纯文档/回包澄清，成本最低且立刻让 #80 的规格有官方落点；(b) 涉及进程生命周期，需宿主设计，排后。
