# 爱生活（D:\ilife）多插件更新能力调查

> 调查时间：2026-10-04 ｜ 调查方式：只读（read / grep / glob / git log / gh issue，未修改 `D:\ilife` 下任何文件）
> 被调查仓 HEAD：`8cec714963c8f8f753eeb9f8286de70061aeb75f`（2026-10-04 00:46 +08:00）
> 触发问题：爱生活插件为「自己 + 旗下 6 个插件」提供更新能力；此前「更新自己」时 UI 消失、更新功能停摆。

## 结论摘要

1. 爱生活总管就是 `dsh-life-pack`（`packages/plugin-manager`）：一个 cordis 插件（host 半 + browser client 半 + `cordis.patch.yml` 装配行），对外只提供一张「爱生活」设置卡，是**一个插件管七个更新目标**的宿主形态。
2. 旗下 6 个插件**不是扫描发现**，而是与总管自己一起写在硬编码清单 `UPDATE_TARGETS` 里（总管排第一，六家按 `nav.ts` 的 `MANAGER_TABS` 顺序拼出）；发现「装没装」另有槽账本一路，但更新动作只认这张清单。
3. 更新能力**不是自研**：总管依赖 `dsh-plugin-update@^0.2.0`，为七个目标各建一套 `createHostUpdate`（各组 `pluginId` 与电话前缀互不相同）；查新版走官方 npm 源 `https://registry.npmjs.org/<包名>/latest`，安装由更新核心按宿主种类选三条出口（桌面服务 / 官方 pluginManager.installBundle / 起子进程跑 `dsh plugin --profile <名> add --save-exact <包>@<版本> --registry=…`）。
4. 「更新自己」与「更新别人」在**更新代码路径上完全同形**（同一张表、同一套电话、同一个串行队列，面板里没有任何针对自己那一行的分支）；唯一的结构性差别是**被替换的那个包正是提供面板 UI（`dist/client.js` 里注册的设置卡 + 更新区）与宿主 RPC 路由（`/api/ilife-manager`）的那个包**——装完磁盘换新、进程仍是旧版（`pending-restart`），再加上 issue #987 记录的「装插件触发 DSH 前端重载」，队列与进度（只活在浏览器 React 内存里）随之丢失。
5. 有排队与互斥，但是两层、且都**不覆盖跨家并发**：面板侧是自己写的串行队列 + 忙守卫（`update-queue.ts`），更新核心里是按 `pluginId` 分开的 `install.lock` 文件锁 + 进程内 `activeJobId`（同一家撞上回 `update-busy`）；跨七家的串行只由面板那条队列保证，宿主侧没有全局锁。

## 4. 「更新自己」与「更新别人」的结构性差异，以及 UI 消失/功能停摆的成因

### 4.1 代码路径：没有差异

**结论**：两条路走**完全相同**的代码——同一张 `UPDATE_TARGETS`、同一套「每目标一组 `createHostUpdate`」、同一条面板串行队列。面板里**没有**任何针对「总管自己那一行」的特殊分支：`MANAGER_TARGET_KEY` 只在 `update-targets.ts:26` 定义、`:30` 使用；全 `src` 检索 `'life-pack'`/`MANAGER_TARGET_KEY` 只有这两处。

**证据**

- 同一循环建七组电话：`update-host.ts:294-329`（见 §3 引文）。
- 面板行表就是宿主回的 `targets`，无按 key 分支：`update-client.ts:110-116` → `update-panel.ts:275-276`；渲染见 `update-panel.ts:609+`（`UpdateResults`）、缺席卡 `update-view.ts:35-53`。
- 七家之间只靠前缀与 pluginId 隔离：`update-targets.ts:4-5`「七组之间靠**各自的前缀**与**各自的插件标识**隔离（更新包 README 第 12 节：前缀相同就是串台）」；实测 `pluginId = 'dsh-life-pack-' + target.key`（`update-host.ts:295`）。

### 4.2 唯一的实质差别：被替换的包正是「面板 + 宿主路由」的提供者

**结论**：六个单品被更新时，被换掉的是**别家**的包（别家的设置页/页面），总管这套更新 UI 与宿主路由不受影响；总管自己被更新时，被换掉的正是**承载更新 UI 与更新宿主的那个包**。这是纯结构事实，不是猜测。

**证据**

- 更新界面住在总管自己的 client 束里：`D:\ilife\packages\plugin-manager\src\client.ts:23` `import { AbsentCard, CheckUpdateButton, UpdateResults, useUpdateRows } from './update-panel.js';`；同一个文件 `client.ts:532-544` 注册「爱生活」设置卡（`id: 'dsh-life-pack'`，`children: { 'ilife.config-tab': … }`）；该束的产物就是包的 `exports['./client'] = ./dist/client.js`（`package.json:10`），浏览器加载它（装配规则见 `package.json:39-44` `"client": { "platform": "web", "inject": [...] }`）。

  面板对这一态的处理只有一句话：`update-view.ts:89-92` `restartLine()` →「磁盘上装的是 X；正在运行的是 Y。重启 DSH（退出后重新打开）后生效。」；`update-contract.ts:91` 同口径文案。

### 4.3 「UI 消失 / 更新功能停了」的成因链（**推断**，逐条标出证据强度）

> 下面 1–2 是代码可证的事实，3–4 是 issue 里记录的现场事实，5–6 是据此给出的机制推断（我没有真机复现，见 §8）。

1. **队列与进度只活在浏览器内存**：`update-panel.ts:274-282`（`targets`/`rows`/`updatingAll` 都是 `React.useState`）、`:283-289`（卸载时 `alive.current = false`）、`:300-309`（卸载清空 `retryTimers`）；串行游标是 `runSerialUpdateAll()` 的函数调用栈（`update-queue.ts:126-187`，由 `update-panel.ts:419-435` 驱动）；收尾观察者只有客户端轮询（`update-client.ts:180-188`）。
2. **持久化一处都没有**：在 `packages/plugin-manager/src` 全量检索 `localStorage` / `sessionStorage` / `indexedDB` / `persist` / `queue.start` / `queue.cancel` → **各 0 命中**（本调查实测，HEAD `8cec7149`）。宿主侧也没有队列电话：`MANAGER_ACTIONS` 只有 `install`/`targets`/`roots` 三条（`update-contract.ts:43-60`）。
3. **装插件会触发 DSH 前端重载**（现场记录）：issue [#987「自动更新队列在 DSH 前端重载后被破坏」](https://github.com/FeatherHunter/ilife/issues/987) 正文
   > `「爱生活」的更新功能有一个更新队列（按队列自动更新插件）。` / `在配置面板完成一个插件的更新后，会触发 DSH 前端的重载（reload）。` / `观察到的现象：这次重载之后，更新队列被破坏，后续按队列的自动更新行为不再继续推进。`
   该票 triage 又写明触发源不在本仓：
   > `E. 触发源是宿主在插件包变化后重载前端（45%，待真机确认）。本仓代码内无 location.reload 式调用（已检索，0 命中），故触发源应在 DSH 宿主行为，不在本仓。`
4. **「列表消失如重载」有独立票**：issue [#980「配置面板「全部更新」：一家装完列表消失如重载，且串行期间结果对话框不可关闭」](https://github.com/FeatherHunter/ilife/issues/980) 正文
   > `点「全部更新」后，6 家进入串行：一家装完才走下一家。` / `一家装完时，当前结果列表消失一次，像重新加载一样，用户失去刚才的进度上下文。`
   修复提交 `1fe5f9dc`（`fix(980): 一键全部更新可关闭且重取不断进度`）只加了**面板内**取数的「空表保旧」（`update-queue.ts:63-94` `shouldKeepTargetsOnReload`/`mergeTargetsOnReload`）；#987 的 triage 明确这两件事不同层：
   > `关键概念澄清：#980 的 reload()（update-panel.ts 内重取目标表…）与本单的 DSH 前端重载是两回事。前者是面板内的数据重取，后者是浏览器侧 JS 上下文整体重建。前者的保旧逻辑保不住后者。`
5. **推断（机制）**：自更新成功那一刻，磁盘上的 `dsh-life-pack` 已换成新版（被换掉的包括 `dist/client.js` 这份更新 UI 与 `dist/index.js` 这份更新宿主），进程里跑的仍是旧版；DSH 因插件包变化重载前端 → 页面重挂、面板回到初始态（`rows = {}`、`updatingAll = false`、进度行消失 = 用户说的「UI 消失」），串行循环与轮询随 JS 上下文一起消失、剩余目标永不被发起（=「更新功能停了」）。这与 #987 的 triage 结论同一条：`队列游标与各行进度全部丢失，剩余任务永远不会被启动。面板看起来回到空闲态。`
6. **推断（次要路径，也会表现为「更新功能停了」）**：若重装配发生在本进程内，旧实例的路由随 `ctx.effect` 清理注销、新实例又因「already registered」退让（`index.ts:81-88`），或面板与宿主半「混版」对不上（t740 证据里记过：`docs/plugins/plugin-manager/t740-证据.md:171`「宿主进程里跑的若还是旧版宿主半…」），面板就会印那句红字——「更新能力没接上：面板连不上总管插件」（`update-contract.ts:102` `manager-unreachable`），即 issue [#982](https://github.com/FeatherHunter/ilife/issues/982) 的现场现象。**这一条我没有拿到与自更新直接对应的日志读数**（见 §8）。

## 5. 排队 / 串行 / 互斥机制

**结论**：有，分两层，但都**不含跨目标的全局锁**。

1. **面板侧（自己写的，纯函数）**：一键串行队列 + 忙守卫。
   - 决议原文：`D:\ilife\packages\plugin-manager\src\update-queue.ts:1-15`（#925 决议，逐条：`一键排队串行…一家收尾才起下一家；失败一家记 failed 继续下一家`、`安装中题头点不得`、`行按钮全局互斥`、`进度各行自显`）。
   - 判据函数：`update-queue.ts:32-37` `hasInstallingRow()`、`:40-42` `updateBusyFailure()`（码与人话都取 `update-busy`）、`:56-58` `shouldBlockBatchStart()`；串行体 `:126-187` `runSerialUpdateAll()`（`for (const target of targets)` 逐家 查→装→收尾）。
   - 接线：`update-panel.ts:383-403` `checkAll`、`:404-436` `updateAll`（`await runSerialUpdateAll(list, {…})`）、`:437-509` `act`（单家，进门先 `batchBlocked()`）。
2. **更新核心里（`dsh-plugin-update`）**：文件锁 + 进程内单任务位，**按 pluginId（即按目标）分开**。
   - 锁文件名：`config.js:9` `const LOCK_FILE = "install.lock";`；落盘按 `updates/<pluginId>/<使用范围指纹>/`（README §3；实测 `~/.dsh/updates/dsh-life-pack-<key>/` 七个目录）。
   - 抢锁/放锁：`store.js:115` `async function tryAcquireLock(lockId)`、`:146` `releaseLock`；进程内单任务：`service.js:159` `let activeJobId = null;`、`:275`/`:301` 置位与清位。
   - 拒绝码：`service.js:312`/`:328` `throw updateError("update-busy")`；人话 `update-contract.ts:100`「同一时间只能安装一个插件。等这次装完，再点「装上更新」。」
3. **没有的**：跨七家的全局互斥。这点由 issue [#923 的决议评论](https://github.com/FeatherHunter/ilife/issues/923) 从代码层给定论：
   > `结论一句话：同一家不能真并行（直接拒绝非排队），跨家核心层无全局互斥但宿主层并行发起会互相踩坏；一键全部更新在宿主层必须串行排队。`
   > `跨家：锁与任务文件按 pluginId 分目录（store.js:24），两家可同时进后台安装；但宿主 reader 缓存是单槽的…`
   即：**跨家串行是面板那条队列（#925/#926）独力保证的**，宿主侧没有第二道保证。
