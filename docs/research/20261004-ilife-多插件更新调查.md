# 爱生活（D:\ilife）多插件更新能力调查

> 时间：2026-10-04 · 只读调查，未修改 `D:\ilife` 下任何文件
> 触发问题：爱生活对旗下 6 个插件提供更新能力；此前"更新自己"时 UI 消失、更新功能停摆。能不能一次检测 7 个、全部丢进更新队列？

## 结论摘要

1. 爱生活的更新能力在 `D:\ilife\packages\plugin-manager`（下称"总管"），**它已经在消费我们的 `dsh-plugin-update`**——不是另一套。
2. 更新目标是**七个**：总管自己 ＋ 六个单品；**总管自己排在第一位**（`UPDATE_TARGETS[0]`）。
3. 因为我们的包"一次只管一个目标包"，总管**建了七组宿主能力、七组电话**（七组前缀互不相同），并在自己的 React 面板里手搓了一整套批量界面与串行队列。
4. 那个 bug 的结构性来源：**承载"全部更新"UI 与串行队列的代码，本身就是第一个被更新的目标**。
5. 我们包里**没有**批量入口、也**没有**队列驱动（drain）——所以"一次查七家、串行装完"这层只能由消费方自己写；总管写了 187 行纯函数 + 一整套面板来补。

## 1. 总管是什么

- 仓库：`D:\ilife`，`"name": "ilife"`，pnpm monorepo，`packages/` 下有 `plugin-manager`、`plugin-calorie`、`plugin-bill-ilife`、`plugin-chef`、`plugin-home-ilife`、`plugin-memo-ilife`、`plugin-schedule-ilife` 等。
- 更新界面源码：`packages/plugin-manager/src/update-panel.ts`（React）。
  文件头自述（`:1`）："爱生活面板的更新界面：检查更新按钮、**七家结果行**、待重启横幅、缺席卡的「装上」。"

## 2. 六个单品怎么被声明（对应问题 2）

`packages/plugin-manager/src/update-targets.ts:1-12` 原文：

> 七个更新目标（总管自己 ＋ 六个单品），以及每个目标的电话名前缀。
> 为什么要这张表：更新包一次只管一个**目标包**（`createHostUpdate` 的 `targetPackageName`），面板的「一个按钮查七家」要七组电话；七组之间靠**各自的前缀**与**各自的插件标识**隔离（更新包 README 第 12 节：前缀相同就是串台）。
> 包名不新开一处定义：六个单品的包名取自 `nav.ts` 的 `MANAGER_TABS`（导航表是唯一真相），总管自己的包名取自 `install.ts` 的 `MANAGER_PACKAGE`。

清单（`update-targets.ts:29-37`）：`UPDATE_TARGETS = [ { key: 'life-pack', title: '爱生活', packageName: MANAGER_PACKAGE, phonePrefix: 'ilife-life-pack' }, ...MANAGER_TABS.map(...) ]`——**硬编码的两源合成**：导航表（六个单品）+ `MANAGER_PACKAGE`（总管自己）。注释 `:28`："七个目标：总管自己在前，六家按导航表顺序。"

## 3. 我们的包是怎么被消费的（对应问题 1、3）

- **宿主侧**：`packages/plugin-manager/src/update-host.ts:139,173` 用 `pluginId: 'dsh-life-pack-' + target.key` 为七个目标各建一份能力；`:258` `assembleTargetRows(UPDATE_TARGETS, facts.profileDir)` 汇总读数。
- 类型声明就放在它源码里：`packages/plugin-manager/src/dsh-plugin-update.d.ts`。
- `packages/plugin-manager/src/update-env.ts:284` 注释："与更新包 `host.ts:102-121` 同一手法"——即它按我们的解析口径自己复刻了一处。
- **面板侧不走我们的组件**：它自己的 React 面板（`update-panel.ts`）。它只用我们的**客户端约定**：`update-client.ts:4-5` 原文——"检查更新：`updateCheck`（第 3 节第 3 步的 `host.call(UPD_CHECK, {})`）；装上更新：`updateCheck` 拿凭证 → `updateInstall` 提交 → **按间隔轮询 `updateStatus`**"。
- 结论：**总管 = 我们"第 3 步自己拼面板"这条路的真实消费方**，而且是七个目标各拼一份。

## 4. 批量能力：他们自己写的（对应问题 5、6）

`packages/plugin-manager/src/update-queue.ts:1-15` 自述（"#925 决议，用户已逐条确认，不可改语义"）：

1. 一键排队串行：按目标顺序逐家 查→装→轮询到收尾，一家收尾才起下一家；失败一家记 failed 继续下一家；单家重试走行按钮 recheck/retry；删并行发起与交叉轮询。
2. 安装中题头点不得：任一行 installing 时题头检查更新禁用；人话沿用 `reasonText('update-busy')` 原句。
3. 行按钮全局互斥：installing 行自锁，其余行禁用不进队列；act 入口有忙拒 `update-busy` 且不改 rows。
4. 进度各行自显：每行各自显示，他行保持 phase；题头不汇总排队数；待重启跳过安装继续下一家。

`#980` 又补了三处：忙判据把 `checking` 也算进去（`shouldBlockBatchStart`，`update-queue.ts:56-58`）、重取目标表时"空表保旧"防整块闪（`shouldKeepTargetsOnReload`/`mergeTargetsOnReload`）、对话框重开绕开忙守卫（`resolveDialogOpen`，注释 `:96-97`："重开只读进度，天生不受忙守卫阻挡"）。

也就是说：**我们缺失的"批量入口 + drain"，被消费方用 187 行纯函数 + 一整套 React 面板补上了。**

## 5. 自更新 bug 的结构性来源（对应问题 4）

- `update-targets.ts:28`：**"总管自己在前"**；`UPDATE_TARGETS[0]` 就是 `MANAGER_PACKAGE`（爱生活自己）。
- `update-panel.ts:404-436` 的 `updateAll`：`const list = targetsRef.current` → `runSerialUpdateAll(list, ...)`，**按目标顺序**逐家执行——于是"全部更新"第一件干的事就是**更新总管自己**。
- 而"检查更新/全部更新"两颗按钮、七家行表、串行队列、忙守卫，全部住在总管自己的 bundle 里（`update-panel.ts` / `update-queue.ts`）。
- ⇒ **正在干活的代码，被自己第一个替换掉。** 装完那一刻：磁盘上是新版、进程里跑的还是旧版；宿主一重启，面板与队列就整体换成新的一份（用户看到的"UI 消失/功能停了"）。串行循环也随进程一起没了，后面六家不会再被推进。

这正是我们包**不会**犯的错：我们的装包由**宿主进程**经三条出口执行（`docs/host-install-exits.md`），更新能力住在宿主 + 这个独立包里，不在被更新的目标包内；面板卸载只停轮询（`src/panel.ts` 的 `unmount` 注释）。
