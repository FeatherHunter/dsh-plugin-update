# 不覆盖实证：真机双插件 × 三场景 ＋ 预算断言实测（票 #125 · 图 #117）

一句话：**三个隔离场景全部通过**（两棵目录各写各的、同 pluginId 两份副本只出一个写者、跨进程不覆写也不丢字节）；
**预算断言里的「轮询噪声」两条实测不达标** —— 600 次真电话 `updateStatus` 落了 600 行，外推 24h ≈ 86400 行
（预算 ≤ 50/天）。那条不是本票的活，归属见 §4，装置已经把数字量好了。

- 2026-10-14 · git `24c3a46` · node v24.19.0 / win32-x64 · 用时 14s（跑动期间 `dist` 未被改写）
- 被测字节：`dsh-plugin-update@0.16.0` 的 `dist`（66 文件，sha256 `6478d6c6fdc2c6b94fa76a61fdd74a6f0e17f6a08bb28513b191ea1a26c5dd86`）
  ＋ `dsh-log@0.3.1`。快照成两份逐字节相同的副本再跑，跑前跑后都核对了指纹。
- 装置：`.tmp/log-verify/`（gitignored）。本记录是耐久产物，装置可重建；重建后复跑一条命令：

```
node .tmp/log-verify/run.mjs            # 全跑：s1 s2 s3 budget
node .tmp/log-verify/run.mjs budget     # 只复跑预算断言（#124 落地后要看的就是这条）
```

装置不是模仿内核：两个假插件的 host 半区都走**真电话**（`createHostUpdate` → `<prefix>.updateStatus`）、
**真落点**（`acquireOwnLog` → `dsh-log/node` 真落盘）、**真清单**（随包 `event-list.update.json`），
父进程读的是**文件字节**（`v === 3` 五键行逐行 JSON.parse）。

## 1. 场景 1：同副本、不同 pluginId —— 后注册的 A 不夺 B 的行

同进程同一份 `dist`（hoist 模拟），先建 `verify-b` 的 host 半区，**再建** `verify-a`（旧实现里这一步会把
模块级落点改写成 A 的），然后交错调真电话：A 4 次、B 3 次。

| 目录 | 文件 | 行数 | 构成 | foreign-write | 丢弃 |
| --- | --- | --- | --- | --- | --- |
| `<home>/logs/verify-a/` | `2026-10-14.log` | 5 | `update.wire.ready` 1 ＋ `host.call` 4 | 无（`lastPersistFail = null`） | 0 |
| `<home>/logs/verify-b/` | `2026-10-14.log` | 4 | `update.wire.ready` 1 ＋ `host.call` 3 | 无 | 0 |

- **行数 = 发射数**：A 目录 4 次调用 → 4 行，B 目录 3 次调用 → 3 行，多一行少一行都没有。
- **零串台**：A 目录里没有 `pluginId=verify-b` / `method=vb.*` 的行，反向也没有。
- **零半行**：两棵树 `bad = 0`。
- 登记表里两棵树的句柄各自独立（`verify-a` / `verify-b` 各 refs=1、各一份 `lastPersistFail = null`）。
- 9/9 条断言通过（`out/scenario1.json`）。

## 2. 场景 2：同 pluginId、两份模块副本 —— 只出一个写者

前提先钉住：副本 A = 现场 `dist`；副本 B = `.tmp/log-verify/hoist/node_modules/dsh-plugin-update/`，
**并且自带一份 `node_modules/dsh-log`**（两份 dsh-log 解析到两个不同文件：
`…\node_modules\dsh-log\dist\node.js` ≠ `…\.tmp\log-verify\hoist\node_modules\dsh-log\dist\node.js`）。
这一步是关键：dsh-log 的目录租约表是**模块副本级**的，不让两份副本各拿一份 dsh-log 模块，测到的就不是本包登记表的功劳。

| 量 | 结果 |
| --- | --- |
| 同目录第二次取库（副本 B 跨副本取副本 A 建的目录） | `reused = true`、**同一个句柄对象**、refs=2、登记表 size=1 |
| 两个 host 半区（同 pluginId `verify-same`） | 共用 1 个句柄（refs ≥ 2），登记表里只有这一棵树 |
| 6 次真电话（两半区各 3 次） | 同一个文件里 **6 行 `host.call`**，另加 2 行 `update.wire.ready`（各半区一条） |
| 半行 / foreign-write | `bad = 0`；`lastPersistFail = null`；`log.persist.fail(foreign-write)` 0 条 |
| 9/9 条断言通过（`out/scenario2.json`） | 是 |

### 负对照 A：绕开登记表、保留追加能力（装置有没有分辨力？）

两份副本各自直接 `createNodeHostLog` 同一目录（dsh-log 自己**两个都放行** —— 模块副本级租约表看不见对方），
交错写 20 行：**两个写者共存（装置能看见「双写者」）**，但 20 行**一行不少、0 条半行、无 foreign-write**。

结论（如实说）：在本机（`dsh-log/node`，`appendText` 可用）下，同目录两个写者**退化成交错追加**，不吃行。
登记表在本机挡住的不是「丢行」，而是「两个写者 + 相互看不见」这件事本身。

### 负对照 B：绕开登记表、拿掉追加能力（丢行到底长什么样）

把 `dsh-log/node` 的文件服务里的 `appendText` 摘掉 → 引擎退回「读旧文 ＋ 拼新行 ＋ 全文覆写」通道
（`canAppend()` 判的就是 `typeof fs.appendText === 'function'`）。两份副本各 5 行、5 轮、同时刷：

| 轮 | 发出 | 文件里当轮标记数 |
| --- | --- | --- |
| 1–5 | 每轮 10 行 | **5/10**、5/10、5/10、5/10、5/10 |

**共发 50 行 → 文件里只剩 25 个不同标记，25 行被对方吃掉**（读改写通道下后写者整篇覆盖）。
这正是 #121 注释里「10 行剩 9 行」的同一族现象，也是 `globalThis` 登记表存在的理由 ——
它在**同进程**把所有副本收敛到一个句柄，从源头取消了这个形态。
（DSH 桌面宿主的文件服务若没有 `appendText`，走的就正是这条读改写通道，所以这不是假想风险。）

## 3. 场景 3：跨进程 —— 承诺「不覆写」，边界在 4KB

两个**真子进程**（副本 A 与副本 B 各一份模块副本），发令文件一齐开写，各写 20 行；
大行变体每行各自刷一次（`--flush-each`）并跑多轮，让两个进程的追加真的在时间上重叠。

| 变体 | 行 ≈ | 轮 × 每轮行数 | 发出总行 | 可读 | 不可读（半行） | 标记 A / B |
| --- | --- | --- | --- | --- | --- | --- |
| small | 260 B | 2 × 40 | 80 | 80 | **0** | 40 / 40 |
| near4k | 3.9 KB | 2 × 40 | 80 | 80 | **0** | 40 / 40 |
| over4k | 8.1 KB | 5 × 40 | 200 | 200 | **0** | 100 / 100 |
| huge | 64 KB | 5 × 40 | 200 | 200 | **0** | 100 / 100 |

- **不覆写**：每个变体里 A、B 的标记一个不少（字节级：连被吃掉的行都没有）；两个子进程的丢弃计数都是 0。
- **4KB 边界的事实形状**：`splitForAppend` 在**行边界**上切块，块 ≤ `APPEND_ATOMIC_MAX = 4096`；
  **单行自己超过 4096 时不再切**（实测 8001 字节的行 → 1 块 8001 字节；64001 字节的行 → 1 块 64001 字节），
  即「整行一笔写下去」，而 `O_APPEND` 的大块写不保证原子（上游 `dist/engine/io.js:5-12` 记的实测：
  两个真子进程、各 20 行 × 64KB → 40 行里 2 行读不出来）。
- **如实说没复现**：本机 200 次重叠的 8KB/64KB 单行追加里，**一条半行都没出现**。
  所以「40 行里可能有不可读行」在本机是**理论残留风险**，不是本机现象 —— 上游那 2/40 是别的环境下量的。
  谁要拿这一条做承诺，请照本装置在目标环境（尤其是宿主自己的文件服务）复量一次。
- 21/21 条断言通过（`out/scenario3.json`）。

## 4. 预算断言：内核守得住，轮询路径没守住

| 层 | 断言 | 实测 | 判定 |
| --- | --- | --- | --- |
| A · 内核边沿守卫（真落点、真清单） | 86400 次同状态 `update.status.changed` → 磁盘几行 | **1 行**（`suppressed = 86399`） | ✅ |
| A · 同上 | 86400 次同相位 `update.queue.transition` → 磁盘几行 | **1 行** | ✅ |
| A · 内核稳态 | 24h 常驻行 ≤ 50 | **2 行** | ✅ |
| B · **真机轮询路径** | N 次轮询零常驻行 | 600 次 `updateStatus` → **600 行 `host.call`**（一行不少全进盘） | ❌ |
| B · 稳态 | 24h 常驻行 ≤ 50 | 按实测外推 **≈ 86400 行/天**（1s 一拍） | ❌ |
| C · 安装/批量当天（事件面模型） | ≤ 500 | **37 行**（20 类事件逐个按目录发射） | ✅ |
| C · 加上实测轮询噪声 | ≤ 500 | 37 ＋ 86400 = **86437 行** | ❌ |
| D · 按需档 | 开关关着时 ondemand info 不落盘 | 50 次 `update.poll` → 磁盘 0 行（`skipped = 50`，不算丢） | ✅ |

**机制（读代码定位，不是猜）**：`src/host.ts:796`（变更日志电话在 `:898`）在电话成功时**无条件**发 `host.call`；
清单里 `host.call` 的 guard 写的是「一次电话一条；**成功且状态未变时轮询不发**」，
但 `src/log/manifest.ts:96-103` 的 `isEdgeEvent` 只认 guard 文本里带「边沿触发」四个字的事件
（只有 `update.status.changed` / `update.queue.transition` 命中），宿主侧也没有实现「状态未变就不发」。
于是 1s 一拍的 `updateStatus` = 86400 行/天 —— 与研究票 #126 量的现场（99.3% 行是轮询噪声）同因。

**归属**：这是 **#124（宿主侧接线：轮询噪声治理）** 的验收项，本票不越界改 `src/`。
#124 的验收里写的就是「成功轮询 `updateStatus` 且状态未变 → 不发」「稳态 24h 常驻行 ≤ 50；安装/批量当天 ≤ 500」；
它落地后复跑 `node .tmp/log-verify/run.mjs budget`，B/C 两条应转绿 —— 那两行就是它的现成证据。

## 5. 这套装置测不到什么（边界，别过度引用）

- **跨进程没有协调**，这是设计承诺（ADR-0005）：两个进程同写一棵目录只保证「交错、不整篇覆写」，
  不保证行序、不保证去重；本机连半行都没出现，但引擎自己在单行 > 4096 时留了理论口子（§3）。
- **没有 `appendText` 的写者**（宿主文件服务/别的平台）走读改写通道：同进程靠登记表兜住，
  **跨进程兜不住** —— 负对照 B 量的 50→25 就是这个形态；跨进程遇这种宿主应当避开同目录。
- 预算断言里的「安装/批量当天」是**事件面模型**（按事件目录逐个发射），不是真跑一次安装；
  真安装路径的行数由 #124 的真机验收覆盖。
- 轮询外推按 1s 一拍、24h 连续；面板不常开时实际值会低，但每拍一行这件事是实测的。
- 装置与产物都在 `.tmp/log-verify/`（gitignored）：仓库里耐久留下的只有本记录。
