## 0. 结论摘要（10 条）

1. **单插件链路**只有一个入口：`createHostUpdate(deps, configInput)`（`src/host/factory.ts:270`），挂 6 通电话
   （`src/host/factory.ts:656-684`），电话名由调用方给的前缀拼成 `<prefix>.<action>`（`src/shared/config.ts:165`）。
   本包**不是 DSH 插件**：`package.json` 没有 `dsh` 清单字段，只导出库入口（`. /panel /client /batch …`）。
2. **「共享」目前只发生在磁盘层**：同一个使用范围（`homeDir` × `profileDir`）下所有插件共用
   `<home>/update-queue/<短指纹>/{queue.json,global.lock}`（`src/core/queue/ports.ts:30-42`、`:55-58`）；
   进程内**更新**状态一律不共享（见第 6 节：单例 reader、失败锁存、驱动标志都是各副本自己的模块级变量）；
   进程内唯一跨副本共享的是日志写者租约表（`src/log/registry.ts:4-8`、`:24`），与更新语义无关。
3. **同一台机器上本来就住着多份本包**：文件头自述「使用范围级一份（hoisted），消费方插件各自 `node_modules` 里还可能有嵌套的一份」
   （`src/shared/self.ts:4-7`，层级判据 `:38-44`）。真机证据：profile 级 `dsh-plugin-update@0.18.38`，
   而 `dsh-im-companion` 内嵌 `0.18.39`（`E`）。
4. **队列语义是「同一使用范围内的跨插件单队列 + 单全局锁」**，不是跨进程协调：锁里记了 `pid`（`src/core/queue/ports.ts:318`），
   但回收判据只有**年龄**（陈旧阈值默认 = 安装时限 15 分钟，`:42`），全仓 `src/` 没有任何 pid 存活探测（`C`：grep `process.kill|isAlive` 无命中）。
   进程崩溃留下锁 → 最长 15 分钟内所有插件的安装都会被立刻拒成 `update-busy`。
5. **公平门是「排队即拒」而不是「排队等待」**：非队首的安装请求直接抛 `updateBusyError()`（`src/host/factory.ts:521` 起），
   仓库里**没有**任何守护进程/定时器去推进队列（`src/` 的 `setInterval` 只出现在面板与入口件：`src/panel/mount.ts:76`、
   `src/panel/batch/mount.ts:220`）⇒ 后来者必须由人（或面板轮询）再次发起。
6. **批量失败隔离的基本盘是好的**：`runBatch` 的 check/install 失败只在 `stopOnFailure` 为真时才中止，否则继续下一家
   （`src/core/batch/run.ts:229`、`:281`），而 `stopOnFailure` 默认 `false`（`src/core/batch/model.ts:166`、`:180`）。
   宿主的安装公平门被撞到时也只记 `{kind:'queued'}` 相位退回 `ready`（`src/core/batch/run.ts:270-276`）。
7. **自更新才是断点**：更新一个已装包时走宿主 two-step「先移除、再装」（`src/core/executor.ts:1027-1031`、`:1147-1153`），
   而宿主 `removeBundle` 对在册 bundle 的动作是「先 `selectBundle(name,false)` 立即写盘、再 reload 卸载」
   （`docs/host-install-exits.md:108-110`）——**被执行移除的正是提供面板 UI 与批量执行者的那个包**。
   真机盘面与之一致：`life/batch.json` 停在 `life-pack:current`，其余五家 `ready`（`E`）。
8. **装完之后没有任何「重启自己」的能力**：宿主没有重启电话，本包只留一个 `onRestartRequested` 接缝
   （`README.md:158`、`src/panel/mount.ts:336`、`:1696-1700`、`src/panel/render.ts:803`）；
   `application:'restart-required'` 是宿主出口的真值之一（`docs/host-install-exits.md:30-54`）。
9. **常驻 UI 在宿主侧是存在的，在本包侧是零**：宿主是槽位系统，`shell.overlay` 是 root 作用域的 list 槽，
   宿主自述「要做浮在整页之上的自有表面，注册到 `shell.overlay`」（`asar:…/dsh-cordis-client-runner/lib/client.js`）；
   而本包 `src/` 里没有任何 `ctx.slots` 注册（命中的 8 处 `slots` 全是 `src/core/service.ts` 的 `fallbackSlots` 回退缓存），
   面板只接受调用方给的 DOM 容器与 `embedded|dialog` 两种摆放（`src/panel/mount.ts:148`、`:239-244`）。
10. **面板是客户端驱动**：单面板 1s 轮询（`src/shared/config.ts:47` `DEFAULT_PANEL_POLL_MS=1_000`，
    `src/panel/mount.ts:225`），批量面板同样 `setInterval`（`src/panel/batch/mount.ts:1702`），
    自动续跑只在挂载时试一次（`mount.ts:383`、`:1553`、`:1563`）⇒ 客户端一 reload，进度推进就失去了消费者。

### 3.5 失败时继续还是中止

| 情形 | 行为 | 证据 |
|---|---|---|
| check 失败 | `stopOnFailure=true` → `stopped-after-failure`；否则继续下一家 | `run.ts:225-231` |

## 4. 队列与锁（C）

### 4.1 语义

`src/core/queue/ports.ts:30-37` 的注释就是权威表述：

> 归属：按使用范围共享——同一 `(homeDir, profileDir)` 的全部插件共用同一目录，不同使用范围各用各的、可并行。
> 文件：`queue.json`（owner + waiting，快照式整写）、`global.lock`（执行互斥，抢到才许装，一次只装一个）。

落盘形状 `UpdateQueueState = { version:1, owner: QueueOwner|null, waiting: QueuedEntry[] }`（`src/core/queue/model.ts:52-57`）——
**没有版本、没有参与者名单、没有进度**，它只是「谁在装 + 谁在等」。

- `QUEUE_INTENT_TTL_MS = 10min`（`:26`）；`QUEUE_INTENT_STALE_MS = 30s`（`:33`），只在 `owner === null` 时缩短
  （`:118-130`，即 #217 的僵尸意向清理）。
- 纯函数：`enqueueInQueue:137`（`(pluginId,requestId)` 幂等）、`cancelEnqueuedInQueue:161`（只能撤自己）、
  `releaseOwnerInQueue:178`（`pluginId + jobId` 双对）、`isHeadOfQueue:253`（队空时人人队首）、
  `visibleQueueFor:296`（`showOthers=false` 时他人 owner 折成 `{pluginId:null,busy:true}`）。
- 读坏一律回空队列、写失败吞掉：「队列坏了不能挡安装」（`model.ts:72-73`、`src/host/capabilities.ts:200-202`）。

### 4.2 锁：谁持有、崩溃后怎么办

| 问题 | 现状 | 证据 |
|---|---|---|
| 锁文件 | `<home>/update-queue/<指纹>/global.lock` | `src/core/queue/ports.ts:40`、`:55-58` |
| 内容 | `{id, pluginId, pid, startedAt}` | `src/core/queue/ports.ts:318` |
| 陈旧阈值 | `QUEUE_LOCK_STALE_MS = DEFAULT_INSTALL_TIMEOUT_MS`（15 分钟） | `:42`；`src/shared/config.ts:44-46` |
| 抢不到 | **只 probe 一次**：新鲜 → 记 `busy-owner` 立即返回 false（不等待、不重试）；陈旧 → 二次核对 generation → unlink → 重抢 | `ports.ts:323` 起；`src/core/store-base.ts:57-60` |
| 释放 | 只按锁内 `id` 匹配，pid/pluginId 不参与判定 | `ports.ts:381` 起 |
| 进程死亡 | **没有 pid 存活探测**（`src/` grep `process.kill|isAlive` 无命中）⇒ 只能等年龄过期 | `C` |
| 组合顺序 | 先抢全局（跨插件一次只装一个），再抢自家；自家没抢到就把全局放掉 | `src/host/capabilities.ts:239-240`、`:258-273` |
| 写者协调 | README 明说「同一日志目录同时只许一个写者」「不设跨进程锁」 | `README.md:873` |

> 没有任何一方在等待或重试。

## 5. 自更新与宿主安装退出（D）

### 5.1 三条安装出口（宿主契约）

`docs/host-install-exits.md`：第三方 Desktop 走 `desktopPnpm.runPlugin(...)`（`:15-28`）；官方桌面版走 in-process
`pluginManager.installBundle(spec, {...})`，回 `ChangeResult{application: applied|restart-required|overridden|failed|cancelled}`
（`:30-54`），**预期失败不 reject**；普通宿主自起 CLI（`:165-183`）。
`application:'restart-required'` 是宿主出口的真值——本包能做的只有把「待重启」如实报出来。

### 5.2 更新「已装包」= 先把自己摘掉

`src/core/executor.ts:1027-1031` 的注释把宿主的 two-step 配方说得很清楚：

> 更新一个已在册的包要按宿主自己的 two-step 配方走：HMR 宿主里 `installBundle` 对已装包在跑 pnpm 之前就同步拒绝
> `already-installed`…所以命中这个拒绝时先按包名 `removeBundle`，再带新 `requestId` 装一次。

代码路径：第一次 `installOnce`（`:1114-1117`、`:1147`）→ 不在 `MANAGER_OK` 且宿主说 `already-installed`（`:1149-1153`）→
探拓扑 `probeManagerTopology`（`:1160`）→ `not-removable` 直接诚实失败（`:1163-1165`）→ 未在册先 `setBundleEnabled(name,true)`（`:1166-1189`）
→ `removeBundle(name)`（`:1203-1207`）→ 再装。

而宿主的 `removeBundle` 对在册 bundle 的动作是（`docs/host-install-exits.md:108-110`）：

> 先 `selectBundle(name,false)`（立即写盘）再 reload 卸载；卸载不掉抛 `bundle-in-use` 时，那次取消在册没有回滚
> （`change()` 只把结果标 `failed`），于是本包拿到失败时插件已经装着、却不在 `dsh.profile.bundles` 里
>（插件页显示关闭、重启不加载）。

⇒ **「更新自己」与「更新别人」在代码路径上完全同形，但物理后果不同**：被执行 `removeBundle` 的包正是
提供面板 UI（`dist/client.js`）与批量执行者（host 闭包）的那一个（`docs/research/20261004-ilife-多插件更新调查.md:12`、`:168-186` 的结论在此仍成立）。

### 5.3 为什么「自身消失」、为什么要重启才能续跑

| 环节 | 事实 | 证据 |
|---|---|---|
| 面板归属 | 本包是库，面板画在**调用方插件的客户端模块**里；爱生活把批量面板挂在 `settings.section` 槽（真机 `dsh-life-pack/dist/client.js` 只 `slots.inject("settings.section")`） | `E` |
| 卸载 | 自更新走到 `removeBundle(自己)`，宿主的语义是「取消在册 + reload 卸载」 | `docs/host-install-exits.md:108-110` |
| 无守护 | 批量驱动在宿主闭包里，但**只在面板/电话发起时存在**（无进程级定时器；`drain` 默认关：`fan-out.ts:1050`） | `A` |
| 账本留存 | `batch.json` 是 durable 的（ADR-0003），所以「重启后重开面板」能看见半截 | `src/core/disk.ts:442-447` |
| 续推 | 面板 `autoResume` 只在挂载时试一次（`mount.ts:1563-1606`） | `A` |

> 真机现场正是这个形状（`E`）：`~/.dsh/update-queue/7ece…/life/batch.json` → `id:'mvfgcdpz-nn3vkswkof'`、
> `selfKey:'life-pack'`、`stopOnFailure:false`、`order` 七家且 `life-pack` 第一，`life-pack:current`、
> `bill:done(0.3.85,restartRequired:true)`、`calorie:done + error:'recovery-required'`、`memo/schedule/home/chef:ready`。

### 5.4 重启能力

- 宿主没有「重启自己」的电话：`README.md:158`、`src/panel/render.ts:803` 的注释、`docs/research/20261007-issue-79-普通宿主重启能力调查.md`
  的 C1–C5（CLI 只有 profile/plugin/dump-config 四种 mode；`runProfile` 只回 `{ctx, shutdown}`；profile 重载 ≠ 进程重启）。
- 本包只留 `onRestartRequested` 接缝（`src/panel/mount.ts:336`、`:1696-1700`）——**调用方给与不给决定用户看到「重启」还是「请手动重启」**。
- `application:'restart-required'` 之后的「装完了但要重启」状态由 reader/service 判（`src/core/reader.ts:434`、
  注释 `:431`；`src/core/service.ts:443` `blockedReason = 'pending-restart'`）。

### 6.1 代码不共享，磁盘共享

| 层 | 是否共享 | 证据 |

### 6.2 批量总账在哪、谁能读

- 路径：`<home>/update-queue/<shortHash(profileDir)>/<owner>/{batch.json,inventory.json,prefs.json}`（`src/core/disk.ts:442-447`），
  `owner` 由 `sanitizeBatchOwner` 收窄成 `[A-Za-z0-9_-]{1,64}`（`:428`）。

  `batchStatus` 只回本实例的目标集（`fan-out.ts:652-656` 的 `statusPhone` → `table(await readSession())`）。
- 无属主（老形状）的 `batch.json` 不读不删不接管（`docs/adr/0003-batch-knowledge-vs-round.md`）。
