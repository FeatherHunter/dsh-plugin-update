## 0. 一句话结论

**已决（2026-11-01 人类确认）：采纳 S2。** N=3 的推荐不变，但对抗式自审（§10）把理由从「E 强制」改写成「角色等价类覆盖」：夹具要能同时提供三类物理身份——自更新发起方（批量集成方 A）、第二个可发起安装的更新方（B）、非集成方纯消费者（C）；N=2 只能覆盖两类。E 的 own/foreign 判别力（`ownCount` 恒为 1，见 `src/host/batch/log.ts:145-157`、`tests/batch-log.test.mjs:53-94`）是既有测试门槛与 #260 已接受的口径，但字段断言在单测层即可完成，不单独构成 N=3 的硬理由。F 的 gate 逻辑已在 L1 证明，真双更新方要证的是并发收敛不变量；G 的跨属主 FIFO/租约需要 2 个属主，即 2 个 hub 执行席，但同 scope 仍只有一条中枢任务表。故推荐形状：**3 个夹具包 = A、B 两个批量集成方 + C 纯目标；2 个执行席/属主，C 不建 hub**。该推荐已于 2026-11-01 由人类确认采纳（#258 结论评论、#256 Decisions so far）。

## 2. 第一性原理：什么时候一个包不够

更新链每一步是「读本机（装了没/哪版/在册）→ 查远端 → 判 → 宿主安装 → 再读验证 → 讲清楚」。只有一条链时，一个包就能自证其正确。需要 N≥2 的不是「链路本身」，而是**同一份队列/账本/中枢里出现第二个可区分的身份**：

1. 批量计数：own（自己那家）与 foreign（其余）要能分开断言 → 需要 `selfKey` 那家 + 至少 2 家别的。
2. 队列互斥：全局锁要能「被第二家撞上」→ 需要两个**能发起安装**的身份。
3. 中枢：单写者/FIFO/租约/孤儿接管都是「同一使用范围里有两个推进者/两个属主」时的边界 → 需要一个属主 + 剩余目标，或两个属主。
4. 日志归属：「坏了的是哪一份」要按 pluginId 隔离 → 需要两个不同 pluginId 的目标。
5. 自更新断链：发起方自己就是被替换那家时，剩余目标要能续推 → 一个属主 + 至少 1 个剩余目标。

关键区分：**「目标包身份」≠「更新方身份」**。目标包只需可安装（三件套齐）；更新方必须挂 `createHostUpdate` / `createMultiHostUpdate` 并登记电话。F/G 要的第二个身份是更新方身份，不是目标身份——这是 #260「F=2 包」与 selftest README「N=2 够」口径差的根源。

## 4. 「N=2」与「N=3」的冲突怎么读

两者数的不是同一样东西，不矛盾：

- `selftest/README.md:6-10` 的 N=2：**目标包**两个、宿主由 `FakeHostInstallPort` 扮演。批量账本/队列互斥/中枢租约/日志隔离这些相互作用由假件制造第二个身份，所以「第三包不增加新等价类」在这个口径下成立。
- #260 的 N=3：**可安装的真插件夹具**（含更新方接线）。同理，第三包不是给「假件能造的东西」加等价类，而是给「必须由真插件身份产生的相互作用」加等价类：E 的 own/foreign 判别、F 的两个真更新方、G 的第二属主、J 的第三命名空间。

所以地图 Destination 写「2–3 个自测插件」、而本票要定 N：定的是**在真插件层要覆盖到哪一档**。若人类接受 F/G 的跨身份场景只由假宿主单测覆盖（#260 允许的做法），N=2 目标 + 1 集成方也自洽；本笔记推荐把 F/G 拉到真插件层，因为地图 Destination 要求「覆盖更新系统全功能全场景」。

旁证：同地图 #261 的并行取证测得 L3（真机/真 registry）全仓为零，E/F/G 的门槛目前只在 L1 真盘 + 假网/假时钟上验证（`docs/research/20261031-selftest-coverage-evidence.md:316-317,333`）。夹具包正是把 E/F/G/C 从 L1 抬到 L3 的载体；把 F/G 的真更新方/第二属主放进夹具，才让「抬到 L3」在包层面可执行（真 registry 步骤本身属发布/验收范围，不在本票定）。

## 10. 对抗式自审（2026-11-01）

目标：故意攻击本笔记的推荐，把「想当然」降级。结论：S2 不变，但理由、边界与实施风险要改写如下。

### 10.1 已推翻或降级的说法

1. **「E 强制 N=3」→ 降级为「角色等价类覆盖」**。ownCount 恒为 1 确实让 N=2 时 own/foreign 不可区分，但单测可直接断言字段/数组形状，不必靠真包数量；N=3 的不可替代理由是三类物理身份（自更新发起方 / 第二更新方 / 纯消费者）在真插件层只能由三个包承担。仓内 E 的「3 包」是假执行器 L1 惯例（tests/batch-e2e.test.mjs:220-300 的 pkg-a/b/c），不是真包证据。
2. **「F 要两个真更新方」→ 弱化为「并发收敛不变量」**。gate 的 update-busy/公平门逻辑已由 tests/queue.test.mjs:397-432,434-460 在 L1 证明；真双更新方的价值是验证同 scope 两个真实安装方并发时「不重复完成、租约唯一、状态从盘聚合可信」，而不是「一定撞锁」——撞不撞取决于时序，断言必须是指标性的（not exercised 要如实标）。
3. **术语纠正：2 个席位 ≠ 2 个中枢槽**。S2 的「2 个 hub 席位」= 2 个属主/2 份方案（A、B 各一份）；同一使用范围仍只有一条中枢任务表（hubSlotCountForTests()===1，tests/hub-process.test.mjs:95-143）。
4. **B 必须批量，不是为 F，而是为 G**。F 只需「两个能发起安装的身份」（单插件接线即可）；跨属主 FIFO/单任务表/租约让位要两个属主方案，故 B 用 createMultiHostUpdate。
5. **跨属主接管不成立**（src/host/batch/fan-out.ts:1237 只接自己属主）。A 自更新后继续推进的是**中枢**（内存席位 + 盘上方案），不是 B 的席位去接管 A 的方案；场景断言按实现写。

### 10.2 现有 selftest/ 骨架的真实状态（关键新证据，推翻「迁移=加一个 slot」）

selftest/target-scaffold/scaffold-target-package.ts 生成的包清单只有 name/version/description/license/type/main=index.js；注释明写「不带 dsh 关键字、不带 dsh.plugin 入口：靶子不是真插件，防被误装」，且 writeTargetPackageFiles 只允许顶层三个文件。即：

- 当前夹具**不是可安装插件**（无 exports['./client']、无 dsh.bundle.patch），B 档靠 FakeHostInstallPort 模拟安装与版本落盘；
- src/core/reader.ts:186-220 的「完好包」要求 main + exports['./client'] + dsh.bundle.patch 三件套真实存在；真插件夹具层是**全新代码**，不是加一个 slot；
- 「纯目标 C」也要有三件套与可加载的 client 入口——纯目标 = 不接更新系统，不是没有插件代码。

### 10.3 真安装链路带来的实施约束（P1 必须照此设计）

1. 官方桌面版更新已装包是 **remove→install 两步**：HMR 宿主上已装包不许再 add，先 removeBundle(name)（收名字，先 listBundles 探 removable/enabled）再以新 requestId installBundle(包名@精确版)；成败按 application: applied|restart-required|overridden|failed|cancelled 判，overridden 算成功，预期失败 resolve 不 reject（docs/host-install-exits.md）。
2. 自更新 A 就是 remove A→install A 两步：remove 期间 A 的 fiber 被杀，但中枢席位按 ADR-0008 §8（dispose 不是关停）继续推进 B/C；A 重新加载后同前缀新 fiber 与旧中枢实例共存——场景要断言「不重复开批次、不双写账本、hubStatus 从盘聚合可信」。
3. installBundle 的 spec 是单字符串（包名@精确版，不接受开关），但 options 带 registry；**本地私有 registry 是可选的减污染中间层**（夹具发到本地 registry，而非 npmjs），是否采用留给 P1 决策；#262 的命名/0.0.x 解耦照旧适用。
4. dsh.bundle.patch 是宿主可装的 cordis patch yml（真插件例：D:/dsh-plugin/dsh-opencode-palette/cordis.patch.yml 的 - insert: - id/name/config；仓内假目标也按 dsh:{bundle:{patch:'./patch.js'}} 造，见 tests/target-resolution.test.mjs:33-45）。夹具三件套要造出**宿主真能加载**的最小 bundle，而不只是让 reader 校验通过——这是 P1 最大的一处不确定。
5. 版本耦合：集成方夹具依赖已发布（或本地 registry 上的）dsh-plugin-update；FIXTURE_VERSION_SEQUENCE 0.0.x 只解耦夹具自身版本，解耦不了「夹具测的是哪一版更新系统」，发布顺序与兼容窗口要在 P1 写清。
6. 门禁分层：真安装/竞态用例不进每提交 npm run check；本地 tarball/本地 registry 的 L2 可做定向批次，真机/真 registry（C/H/I）手动或夜间；用例要按 #261 的分层记录声明证据级别。

### 10.4 收敛答案（对 #258 正文的 Q1–Q4）

- **Q1 = S2**：3 包 = A（批量集成方，targets [A,B,C]，selfKey A，selfOrder first，自更新先换自己再续推）+ B（批量集成方，targets [B,C]，selfKey B，缺省 selfOrder last）+ C（纯目标，不接更新、不建 hub）；2 个属主/执行席，同 scope 一条中枢任务表。
- **Q2 = 默认不重叠 + 1 个专门重叠场景**：断言不变量（租约唯一、任务表一条、不重复完成、hubStatus 可信），不赌撞锁。
- **Q3 = 单模板 + 薄身份包装**：集成方模板 1 份、纯目标模板 1 份；发布单元仍 3 个各自自包含包（各有 package.json/dist 三件套）。
- **Q4 = 迁移并扩展**：保留现 hermetic 层（假宿主 + 假目标 + B 档 tsc 门禁）作每提交回归；新增真插件夹具生成层与 F/G/J 真接线场景；真 registry e2e 仍归 C 档。
- **Q5** 仍留给 P1（token 脚本位置）。

### 10.5 剩余风险（不阻塞 G1，但要在 P1 首日验证）

- 宿主能否加载「最小三件套」夹具（patch yml 正确性、client 入口加载）——P1 先做一次真机 spike。
- 本地 registry vs npmjs 的取舍与发布白名单。
- 双集成方夹具对同一已发布 dsh-plugin-update 的版本锁定/升级窗口。
- 竞态用例的可重复性（时序敏感 → 不变量断言 + not exercised 标记）。
