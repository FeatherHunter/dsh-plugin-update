# 2026-10-17 更新系统对抗式审查：失效面、分期修复与用户自助路径

> 缘起：真机连续两次 `[update-diag] install-failed`（dsh-opencode-palette 2.0.28→2.1.0、dsh-prompt 0.4.29→0.4.30，摘要均为 `already-installed`），
> 以及用户要求「从第一性原理出发，对抗式审查当前整个更新系统，不能再出现第三方插件用我们的更新系统结果更新功能都是损坏的」。
> 本报告只记录结论与证据索引；审查期间的原始探针、假件与日志在 `.tmp/audit/`（不入库）。
> 地图票 #178，子票 #179-#197。本文件是**审查**报告，不是用户手册；用户手册仍是 `README.md`。

## 0. 一句话结论

更新系统的**安装/更新主链是可用的**（第 0 层：宿主通告、取数、决策、路由、日志都有回归测试），但 2026-10-17 的真机上同时存在
**「宿主 HMR 守卫必然拒绝已装包」**（0.18.8 已修）、**「scoped 包与默认目标通道永远检查失败」**（0.18.9 已修）、
**「状态/锁/装后核实三处 S0 级不可靠」**（已立票，#179/#180/#181）和**「同机四代更新器副本偏斜」**（已立票，#196）四类问题。
前三类是代码缺陷，第四类是**结构性问题**：它决定了「即使修好，老副本用户的更新功能仍然是坏的」。

## 2. 用户主诉的直接回答：为什么会「第三方插件用我们更新系统，更新功能反而损坏」

真机上「更新」这一个按钮背后实际有**三种身份**（A 线 §3），用户完全无法辨别：

| 身份 | 用户观感 | 实际发生 |
|---|---|---|
| 目标已在 profile `dependencies`（HMR 宿主 + 0.18.7 及更早） | 2-6ms 失败 `already-installed` | 宿主守卫在 pnpm 之前拒绝；旧码当终局报错 |
| 目标不在 `dependencies`（如 dsh-chef / dsh-home-ilife） | 5-12s「成功/待重启」 | 其实是**新增依赖**，不是换版；verify 只比磁盘副本版本 |
| 0.18.8 以上、目标在册 | 先移除再装（2 次调用） | 正常；但若移除后重装失败，详情不说明「包已不在册」（#168） |

也就是说：**失败是大声的（好消息：不是静默损坏），但「成功」也可以是假的（#180：重启后不加载也报 restart-required），而且部署偏斜让修好的版本到不了用户（#196）。**

### 2.1 真机证据（两条原始通知 + 同一批 7 行批量更新）

- 第一条：`dsh-opencode-palette 2.0.28→2.1.0`，`摘要=already-installed`；palette 用的是**自己嵌套的 0.13.0 副本**（`palette@2.0.28` 声明 `dsh-plugin-update: ^0.13.0`）⇒ 0.18.8 的修复到不了它。
- 第二条：`dsh-prompt 0.4.29→0.4.30`，同样 `already-installed`；dsh-prompt 没有嵌套副本，按 Node 解析落到 profile 级 0.18.6 ⇒ 同样没有两步法。
- 同一批 7 个目标（`from:"batch"`，20:03:14–20:04:19）：**5 行 2-6ms 被拒**（life-bill / calorie / life-pack / memo / schedule，`exitCode:null`），**2 行真跑 pnpm 成功**（life-chef 5364ms、life-home 12354ms）——后者其实是「新增顶层依赖」（`before.json` 快照里没有它们），且 `runningVersion` 被上游伪造成 `0.0.0`（#182）。

## 3. 六层失效模型

| 层 | 内容 | 主要失效 |
|---|---|---|
| L1 副本层 | 同一台机器上装载的更新器副本 | 四代同堂（0.13.0 / 0.18.6 / 0.18.7 + 修好的新版），能力矩阵不一致（#196） |
| L2 取数层 | registry 取数、版本文档、通道、源地址 | scoped 包全灭（R1，已修）、包文档 256KB 墙（R3，已修）、源地址拼接（R5，已修）、stable+预发布 latest（#183，已部分修） |
| L3 决策层 | 当前版本、通道、node/dsh 引擎、身份判定 | 运行版未知被伪造成 `0.0.0`（#182）、只读 `engines.node`（#195）、同一按钮三身份不可辨别（#197） |
| L4 路由层 | 三条安装出口（desktop-manager / desktopPnpm / cli） | 出口一无安装时限（#193）、CLI 超时杀进程却不报超时（#185） |
| L5 宿主能力层 | 宿主拒绝码、pendingBuilds、HMR 守卫、removeBundle | 拒绝码只回裸码（已修）、pendingBuilds 通道没接（#194）、超时语义不诚实（#184） |
| L6 状态/诊断层 | job / 锁 / before.json / 装后核实 / 诊断复制 | job 只在内存（#179）、锁双向失灵（#181）、装后核实不查在册（#180）、旧副本 diag 缩水（#196） |

## 6. 用户自助路径（当前这台机器）

**结论：0.18.8/0.18.9 发布后，先用面板更新「更新器自己」，再让各插件面板走新码；palette 必须另走一次非面板通道。**

1. **先发版**（人工侧窗口，Agent 不发布）：`0.18.9` 已提交在仓库（见 CHANGELOG），发布后 npm 上才有新版。
2. **让 profile 级副本升到 0.18.9**：`dsh-plugin-update` **不在** profile `dependencies` 键里（它是 palette/life-pack/deck 的传递依赖），所以天然绕过 HMR 守卫；在任一使用 profile 级副本的面板（dsh-prompt / life-pack / mattpocock-skills-deck）点更新即可。
3. **palette 是例外**：它嵌套自己的 0.13.0 副本、声明 `^0.13.0`，面板更新永远走老码。两条出路：
   - 用**载体 CLI**（实测可执行，见 `docs/host-install-exits.md`）：
     `dsh plugin --profile desktop add --save-exact dsh-opencode-palette@<新版本>`，然后**重启桌面宿主**（载体 CLI 不经过宿主的 reload）。
   - 或等 palette 发一个把 `dsh-plugin-update` 范围升到 `^0.18.6` 的版本（发布侧依赖治理，#196）。
4. **更新器自己也可以走载体 CLI**（面板都不灵时的兜底）：
   `dsh plugin --profile desktop add --save-exact dsh-plugin-update@0.18.9` → 重启桌面宿主。
   注意：这条命令是独立进程（无 HMR），**绕过**宿主的三道门（not-bundle / incompatible-version / stale-approval），只对「确认包名与版本」的救急场景用。
5. **验收信号**：panel 诊断里能看到「本面板运行版本」与两秒退化的 diag 字段（0.18.7+ 才有 failedJobDiagOf）；再次点更新应看到 2-12s 的成功耗时或如实的宿主拒绝码 + 中文下一步。

## 7. 确定性分档（诚实清单）

- **证实**：宿主 HMR 守卫在 pnpm 之前按名字拒绝（`asar:…/dsh-plugin-manager/lib/index.js:1991`）+ `specPackageName` 只取包名（`:1373-1379`）+ 4ms/exitCode null/无 pnpm operation 的真机三证；scoped/通道/字节墙/源拼接四条均可黑箱复现；五条不稳定（#179/#180/#181/#184/#193）均探针可爆；载体 CLI 实测可执行；四代副本偏斜为真机直读。
- **推断（强）**：批量 5 行失败码 = `already-installed`（无落盘，但 2-6ms/exitCode null/旧版无任何处理/守卫位置全部吻合）；dsh-prompt 解析到 profile 级 0.18.6（无嵌套副本 + 日志口径 `源=未声明` 与 0.18.4+ 一致）。
- **未证**：真机点过 remove→install 的端到端成功（需用户侧发版后验证）；重复 requestId 的宿主行为（asar 只有 `installs.set`）；那次全量门禁 `fail 1`（未复现）；`engines.dsh` 拒绝未真实触发；私有源自定义 tarball 路径未实测。
