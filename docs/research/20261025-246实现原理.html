更新中枢：把一次更新，从页面里搬进进程里

不谈 API 清单，先问一个更根本的问题：更新为什么需要“中枢”？把这个问题拆到不能再拆，答案会自己长出来。

01

先问对问题：更新到底难在哪？

一次更新，本质上不是“调用一个安装函数”，而是一段可能持续几分钟、会中途卸载自己、会跨页面、跨进程、跨重启的副作用序列。所以真正要设计的不是“怎么装得更快”，而是：当执行者消失时，事实和所有权怎么不消失。

把“更新”拆到第一性，会看到四个躲不掉的硬约束。它们不是实现细节，是问题本身的性质。后面的所有设计，都只是对这四条的回答。

约束 A
A

安装很慢，而且不可“假装没发生”

一次安装可能跑几十秒到几分钟，单步上限是 15 分钟；装到一半失败会留下半装、锁、待重启状态。它不是一个可以随手重试的纯函数。

约束 B
B

发起更新的页面，随时会消失

关面板、切页面、刷新、宿主重载，甚至更新器自己更新自己——承载“执行循环”的插件页面或 fiber 会先被卸载。执行者不能住在会被卸载的东西里。

约束 C
C

同一个使用范围，不能两个人同时装

两个进程同时推进同一个批次，会重复安装、互相覆盖账本、抢同一把全局安装锁。必须有一个“现在谁在开车”的裁判。

约束 D
D

任何时候都要有人能回答“到哪了”

用户切回页面、另一个插件、甚至中枢不在的时候，都要能看到进度。观察者不能依赖“执行者还活着”，也不能自己动手改状态。

从四条约束，直接推出四个设计承诺

约束必须做到对应承诺
A · 慢且不可逆把“要做什么”和“做到哪”持久化，每一步都能从盘上恢复方案（plan）+ 账本（ledger）落盘，单步推进
B · 执行者会消失执行权不能属于某个插件页面，要属于进程；页面没了，泵还在进程级注册表 + 进程级单泵
C · 不能双写同一使用范围同一时刻只允许一个驾驶者，且旧驾驶者写回要被认出租约（lease）+ 代次（generation）
D · 随时可观察观察者只读盘、不算账、不推进；没有中枢也能回答只读进度电话 + 盘上聚合快照
02

六个部件：每个都对应一条约束

把这四条承诺落到代码，就是六个互相咬合的部件。它们不是“功能列表”，而是一组职责分离：意图、事实、所有权、执行、观察、展示，各归各的层。

01

方案 Plan

只写意图。装什么、装到哪个使用范围、从哪个源查、对应哪份账本。它是“任务书”，不是进度条。

02

账本 Ledger

唯一进度真相。每一行的阶段、版本、错误、请求编号都在这里；中枢、面板、取消、重试都读写它。

03

租约 Lease

驾驶位。谁在推、第几代、心跳到什么时候；它不保护文件内容，只决定“谁有资格写”。

04

单泵 Runner

执行循环。每轮只推一步，落盘、心跳、判定；然后决定继续、让位、收尾还是报错。

05

只读电话

观察窗。从盘上聚合方案、账本、清单、租约，回一份快照；不执行、不修改、不依赖中枢活着。

06

常驻进度坞 Dock

可选展示。纯渲染 + 轮询；页面隐藏时暂停，容器释放时停掉。它不参与正确性。

03

架构总览：一条电话线，把页面和进程分开

插件页面不再自己“跑安装循环”。它只做三件事：查、提交、观察。真正的推进发生在 DSH 进程里的中枢；中枢只认盘上的方案、账本和租约。

虚线关系：任何还活着的集成方都能用 updateHubStatus 读这三份事实；它不需要先“拿到中枢”，也不需要中枢进程还活着。

为什么是“进程级”，不是“插件级”

插件 fiber 会死，进程不会因为一次卸载而死

DSH 的插件运行在 fiber 里。面板关闭、插件重载、自更新都会销毁 fiber；如果把执行循环放在 fiber 的闭包里，循环就跟着消失。把状态和任务表放到 globalThis 的 Symbol 槽里，进程内所有副本共享同一份；fiber 销毁不影响它。

但“进程级”不等于“全局随便写”

注册表按 (homeDir, profileDir) 分槽。desktop 和 web 两个 profile 即使在同一台机器、同一个进程里，也各自有槽；同一个槽里再靠租约决定谁开车。层级是：进程 → 使用范围 → 驾驶位。

注册表与槽键（src/host/hub/registry.ts:37-141，节选）

const REGISTRY_KEY = Symbol.for('dsh-plugin-update:update-hub:registry')

04

一次更新的一生：从点击到收尾

下面把一次批量更新拆成七个阶段。注意每个阶段的“事实”落在哪里——这是理解整套实现最省力的线索。

阶段 1 · 用户点击

插件电话只负责“表达意图”

面板调用 installPhone。它先看自己是不是已经在驱动（driveActive）；如果是，就把这次点击的行并进当前任务，而不是另起一个驱动。单插件链路（没有宿主上下文）则退回原来的 fiber 内驱动。

为什么：同一个页面里的重复点击不能变成两个执行者；这是“单泵”的第一道门。
阶段 2 · 预查

先把选中行查成 ready，再谈安装

precheckSelectedToReady 对选中的 key 逐个查新版，把结果写进账本。两段式是批量更新的基础：查和装分开，装阶段才能复用已查到的版本，不重复查。

为什么：安装是最贵、最容易失败的一步；先把“值不值得装”确定下来，后面每一步才有明确目标。
阶段 3 · 冻结执行席

把“怎么执行”打包成一个 HubSeat

执行席里冻结了：属主、方案、读写账本、查、装、日志、行序、进入/退出驱动的回调。它是一组能力，不是数据；交给中枢之后，页面即使卸载，这些能力仍由宿主根服务持有。

为什么：执行者不能依赖“页面还活着”；把能力冻结后交给进程，才有“页面消失、泵继续”的可能。
阶段 4 · 提交

先写方案，再入任务表

submitHubTask 第一件事是 await writeHubPlan(...)：把目标、使用范围、会话编号写到盘上。写成功后才把任务放进槽里的任务表。任务键是 owner + ':' + sessionId，同一批次重复提交会合并，而不是排两个。

为什么先写盘：如果进程在提交后立刻消失，下一次装载至少能从盘上知道“本来要做什么”。方案是给后来者的任务书。
阶段 5 · 取驾驶位

ensureLease：读盘 → 判决 → 写盘 → 读回确认

中枢先读 hub/lease.json，根据“有没有租约、是不是我的、进程死没死、心跳是否过期”判一个动作：acquire / renew / takeover / wait。拿不到就回 queued，退避重试，而不是报错。

为什么不是内存锁：同一台机器可能有多个 DSH 进程（不同 profile、不同窗口）共用同一个使用范围；只有盘上的租约能跨进程裁判。
阶段 6 · 单泵推进

每轮只走一步：runBatch(maxSteps: 1)

推进循环每一轮：复核驾驶位 → 取账本底稿 → 执行一步查/装 → 写回账本 → 心跳 → 判下一步。一步一落盘，是“崩了也能从这里继续”的最小单位。

为什么不是一口气跑完：跑得越久，崩溃时丢的越多；一步一落盘，最坏只丢当前这一步，而当前这一步本来就要靠幂等请求编号兜底。
阶段 7 · 收尾 / 让位 / 观察

四种判决，而不是“成功/失败”两种

一轮停下后，decideHubCycleVerdict 只给四种判决：continue（预算用完，再跑一轮）、yield（队列忙/暂时排不上，让位）、settle（真的走完）、fail（驱动器自身出错或无进展太久）。收尾时释放租约；只读电话随时可以从盘上聚合进度。

为什么“排队”不能算失败：更新锁被另一家占着是正常状态，报失败会让用户误以为坏了，也会让队列被错误地清空。
05

七个关键机制，逐个拆开

5.1方案 Plan：先写“要做什么”，再动手

类比：出门前先写好任务书，而不是边走边忘

hub/plans/<owner>.json 只回答“要做什么”：对应的会话编号、属主、目标清单（key、包名、插件标识、电话前缀、可选的使用范围覆盖）、使用范围、排序意图、是否失败即停、创建/更新时间。

它刻意不写进度。进度只有一个真相——各属主的 batch.json。方案是索引，账本是事实。这样设计的好处是：重启后不需要从方案“恢复进度”，只需要用它找到账本、重建执行席；也不会出现“方案说 done、账本说 failed”的双重真相。

方案按属主命名，同一属主同时只有一份；读到坏方案按“没写过”处理，绝不挡安装。写盘是“临时文件 + rename”的原子整写，进程崩溃最多留下一个旧版本，不会留下半个 JSON。

5.2账本 Ledger：进度唯一真相，按行合并

类比：不是“总进度条”，而是一张逐行记账的流水

batch.json 里的每一行有 key、阶段（pending / checking / ready / installing / done / failed / skipped / current 等）、目标版本、请求编号、错误、是否待重启。中枢每推进一步就落盘，并且保存时先读回盘上最新，再只合并自己这一步真变过的行，其余行以盘上为准。

这样做的原因是并发写者不止一个：面板可能刚点了重试、取消可能刚清了账本、另一个进程可能刚改过行。如果整份覆盖，旧快照会把别人的新事实吃掉。行级合并是“单写者”之外的第二个保护层。

注意：当前实现的行级合并仍不是 CAS，且 save 不校验租约代次；这是报告里明确指出的已知缺口，不是“设计意图”。

5.3租约 Lease：不是锁，是“驾驶位”

类比：车只有一把钥匙，但钥匙可以换手；每换一次手，车上贴的代次号 +1

hub/lease.json 记录：谁（driverId）、哪个插件、哪个 pid、什么时候上任、最后一次心跳、第几代。默认心跳 5 秒，超过 20 秒没心跳视为失联。判决是一个纯函数，不读盘也不读钟：

decideHubLease 的四种判决（src/core/hub/lease-policy.ts:124-140，简化）
if (没有租约)                  return acquire(generation = 1)
if (租约是我的)                return renew
if (原进程已死)                return takeover(generation + 1)
if (心跳已超过 20 秒)          return takeover(generation + 1)
return wait
判决什么时候后果
acquire盘上还没有人开车上任，代次 1
renew租约还是我的，且我还活着续任，代次不变
takeover原驾驶者死了，或心跳陈旧（哪怕 pid 还活着）代次 +1，旧驾驶者之后的写回应被判非属主
wait原驾驶者心跳还新鲜什么都不做，排队等

代次是整套设计的“防双写开关”：旧驾驶者如果醒来，看到盘上是 gen 2，就应该知道自己已不是属主。但“代次”要真正生效，需要每一个写盘路径都校验它——这正是当前实现没完全做到的地方（见第 8 节）。

5.4单泵 Runner：为什么“一步一停”反而更快

类比：接力赛，不是一个人跑完全程；每一棒都要把棒交稳

中枢每轮复用批量层的 runBatch，但把 maxSteps 设为 1。每一步结束就保存账本，然后心跳、判决。这样做的直接收益是：

  • 崩溃可恢复：最坏丢当前步，前面的行已经是盘上事实；
  • 可让位：队列忙时在步与步之间 yield，不会抱着锁空转；
  • 可观测：观察者随时能看到“已经到第几行”；
  • 可失败隔离：一行失败不必让整个批次无声挂死，判决会给出失败或继续。

判决表看起来简单，但它把“正常排队”和“真的坏了”分开：queued / empty 走 yield，不报错；max-steps 走 continue；finished / stopped-after-failure 走 settle；未知值和连续 10 步无进展走 fail。这个区分是“用户看到的是排队，不是失败”的关键。

5.5只读电话：为什么“中枢不在”也能回答

类比：看仪表盘不需要发动机先同意

<prefix>.updateHubStatus 不推进任何任务，只做一件事：从盘上聚合。它先按方案收集“认领过的批次”，再把队列目录里“有账本但没有方案”的属主补进来（旧版本 / hub:false 留下的批次），再读租约判断“谁在装”，最后投影成快照。

快照有明确上限：最多 8 个会话、每个会话 20 行；状态按 running / waiting / missing / finished 排序。这样任何集成方都能在常数级内存里渲染，不会因为账本很大而拖垮页面。

关键取舍：观察者不允许“顺手推进”。如果只读电话也去拿租约、跑一步，它就不再是观察者，而会变成第二个执行者。所有写操作仍然只走中枢。

5.6常驻进度坞：UI 是外壳，不是正确性

类比：后视镜不参与驾驶，但让你知道后面发生了什么

mountHubProgressDock(container, options) 是一个叶子组件：纯渲染 + 轮询 updateHubStatus，支持右下角、底部条、内联三种挂载方式。页面隐藏时暂停轮询，空闲时隐藏，dispose() 时停表、摘监听、移除节点。

它被刻意设计成“可选”：不挂 dock，更新照常进行；dock 崩了，也不该影响中枢。这就是“展示层”和“执行层”分开的价值——UI 可以随时换、随时关，正确性不依赖它。

5.7孤儿接管：重启后，谁来接这单？

类比：交接班时，下一班先看任务书，再核对账本编号

批量宿主入口装载时，会扫自己属主名下的方案：如果方案还没收尾、对应的账本会话编号对得上，就把它重新包成执行席，提交给中枢续跑。这就是“重启 DSH 后不用重开面板”的代码路径。

边界：当前实现只接“自己属主”的方案（plan.owner === prefix），而规格 US31 / ADR-0008 写的是“任一存活的集成方都能接管”。这是一个已知偏差，不是设计本意；报告里把它列为 P1。

07

取舍：每个设计选择都付了代价

目标选择代价 / 边界
页面消失也不断执行权放进程级注册表，不放 fiber 闭包依赖宿主根服务在 bundle 卸载后仍可用；这条只在假 transport 测试过，真机未验证
跨进程单写者文件租约 + 心跳 + 代次文件没有 CAS；读-判-写之间可能被并发接管；代次需要所有写路径校验才真正生效
崩溃可恢复方案 + 账本每一步落盘每步一次 I/O；大账本要控制上限；原子写是 tmp+rename，Windows 上仍可能遇到文件占用
随时可观察只读电话从盘上聚合，不依赖中枢聚合有 8×20 上限；旧账本/坏文件按缺失处理；观察者看到的是“最后落盘事实”，不是内存实时值
不新增依赖JSON 文件 + 既有批量层 + 原生定时器没有数据库的事务/索引；并发控制要自己写，也更容易漏掉边界
旧路径可回退hub:false 回原来的 fiber 内驱动回退批次没有方案，只能走旧逻辑；孤儿接管、全局进度都不适用

原理讲完，必须把“设计意图”和“已验证事实”分开。下面这张表来自 2026-10-25 的功能完整性调查；详细证据在 调查报告。

已证可用 实测

单插件基础链路（check → install → verify → restart）真机有成功记录；批量默认回退、hub:false 登记只读电话、8×20 截断、运行中取消回 update-busy、行级选择视图都有测试或探针支撑。

部分成立 有缺口

单写者方向正确，但长步骤心跳只在步后写（20s 窗 < 15min 安装上限）；租约读-判-写无 CAS；账本 save 无代次栅栏；取消后的空账本幽灵任务约 24 秒内阻塞同槽；旧任务不校验 sessionId，可能驱动新会话。

尚未证明 真机 0 次

“跨 fiber 宿主引用在 bundle 卸载后仍可用”只在假 transport 测试过；自更新不断链、重载/重启续跑、常驻 UI、真实多进程接管，均未在真机执行。0.18.40 未发布，两 profile 仍是 0.18.38。

所以，这套实现现在到底是什么？

一句话：方向自洽、骨架完整、单进程测试通过；但“生产可用”还没有被证明，且单写者的护栏没有焊死。它不是一个“全坏的功能”，也不是一个“可以对外宣称已支持自更新不断链”的完成品。更准确的定位是：一个把问题拆对了、但还需要补关键防线和真机证据的系统。

09

一句话总结

把一次更新，从“页面里的一个函数调用”，变成盘上的一份意图 + 一个进程级的驾驶位 + 一本逐步落盘的账本。这样页面可以消失、进程可以重启、别家插件可以观察，但事实和所有权不会丢。

这次 #246 最值钱的地方，不是多了一个“后台任务”，而是把更新拆成了四个可独立演进的层：意图、事实、执行、观察。剩下的工作，是把“单写者”的每一道缝焊死，然后在真机上跑一遍——在那之前，它只能算“解释得通”，还不能算“担保得住”。
