同一个包，两种角色

角色谁提供 pluginId有没有"自己的开关"
作为插件被独立安装（DSH 里直接装 dsh-plugin-update）它自己 src/entry.ts:362-366有。此时它扮演的是"宿主插件"

不是这样

是这样

为什么这个语义是故意的

如果本包另开一份开关，宿主插件打开调试后会发现"我开了开关，可这个插件的日志还是不出来" —— 用户眼里的"这个插件的日志"就被劈成两棵树、两个开关。ADR-0005 的判据正对着这件事：同一日志目录同时只许一个写者，本包永远只当第二个人，不当第二个主人。

03隔离的三道闸

闸一 · 目录派生

无损分支是单射：合法标识原样通过，不同 raw 标识不共目录。有损分支是概率性的：靠 24 位 slug 前缀 + 6 位 sha256 指纹区分，理论上可撞（该口径已写进 src/log/namespace.ts:9-12）。

闸二 · 进程内登记表

挂在 globalThis 上的 Map<目录 realpath, LogHandle> + 引用计数：同目录复用同一个句柄，归零才释放。Windows 下目录键折叠大小写，否则 Logs 与 logs 会拿到两个句柄、两个写者又回来了。src/log/registry.ts:142-155

闸三 · 路由表

一个 pluginId 一个落点；取不到就回 null，发射口按"丢弃并计数"处理，绝不回退到别人的 sink。src/log/router.ts:56

闸三的判据

串台比丢行更坏：丢行看得出来，串台看不出来。

改造前这里是模块级 let phoneLogCtx：谁最后调一次建库函数就覆盖谁（单向、不清零）。同一份 DSH 里装两个用本更新系统的插件时，后装的那个会把前一个的日志行一并收走 —— 日志互相覆盖的根因在这里，不在文件格式。

#本包提供的语义翻译了什么
1位置语义DSH_HOME → <homeDir>/logs。dsh-log 不知道 DSH_HOME 是什么，它要同时跑在 DSH 宿主与独立 Node 程序里，猜路径在两边都错 —— 所以它故意不猜

5降级语义建库失败 → no-op 落点，绝不外抛。引擎在这两种情况下是抛错的，把"日志坏了不能挡住更新"翻译成降级是本包的事
6内容语义行只承载稳定码 + 字段白名单 + 写前脱敏 + 准入短路 + 预算守卫

05两个租约键与那个冲突

dsh-log 的排他判定有两个键，任一同名即判冲突。而这两个键的默认派生源是同一个 pluginId：

dsh-log 0.3.1 · dist/config/resolve.js:20-29
const logDirName = input.logDirName !== undefined
    ? input.logDirName
    : pluginId === 'wf' ? LEGACY_LOG_DIR_NAME : LEGACY_LOG_DIR_NAME + '-' + pluginId;   // logs-<id>
const switchFileName = input.switchFileName !== undefined
    ? input.switchFileName
    : pluginId === 'wf' ? LEGACY_SWITCH_FILE_NAME : 'log-switch-' + pluginId + '.json';

开关文件写在 cacheDir 根目录下，是日志目录的兄弟而不是孩子：

dsh-log 0.3.1 · dist/node.js
// 目录先建好：开关文件直接写在根目录下，包不建它的父目录。
await mkdir(cacheDir, { recursive: true });

于是出现这一整类问题：两个目录不同，却被同一个开关文件判成冲突

场景：宿主插件自己建了引擎实例（pluginId: 'b'，目录默认 logs-b），又集成了本包但没把实例传进来（未传 logCtx）。本包自建时用覆盖后的目录名 b，开关名仍从同一个 pluginId 派生。

实测：三种组合
B 建库成功（默认 logDirName = logs-b，switch = log-switch-b.json）

A: logDirName=b,      switch=log-switch-a.json

第 1 行 · 关键
目录 logs-b 与 b 根本不同，但开关文件同名 → 照样撞。撞的可以只是开关文件。
第 2 行 · 出路
只换开关名 → 建库成功。冲突不是"两个写者必然存在"，只是命名撞了。
引擎侧的接口瑕疵

租约有两个键（目录 + 开关文件），两个键的默认派生源却是同一个 pluginId，又各自允许被覆盖 —— 于是覆盖了目录的人，会被没覆盖的开关文件撞上。

07兼容的三层方案

第一层 · 让它可见（零风险）

  • 把"你自己也接了 dsh-log 就必须传 logCtx"从一个选项提成前置条件。
  • 把 lastOwnLogDegraded() 接到面板"复制诊断"、日志路牌、快照只读字段。

收益：冲突从"没人知道"变成"面板上写着原因"。风险：零（新增只读字段走破冰）。

第二层 · 冲突时回退到自有开关（小改动，需一次破冰）

  1. 先按对齐命名试 log-switch-<ns>.json（这样宿主插件的开关能管本包）；
  2. 若抛的是开关文件占用 → 换 log-switch-<ns>-update.json 再试一次；
  3. 若连目录也被占 → 再用 <ns>-update + 同名开关。

第 2 步的可行性已被第 5 节的实测第 2 行证明。效果：从"一行都不写"变成"照写，只是开关独立"。

代价说明
位置不再唯一确定冲突情形下目录/开关变成第二套。缓解：面板路牌给实际路径（已有"挂载项 logDir 直通错误章"的测试）
按需事件等于长期关闭回退形态下宿主插件的开关管不到本包，而本包没有翻转开关的电话。对照现状（零行）仍是净赚
需破冰update.wire.ready 的 logSink 要加枚举值（如 'self-fallback'）并在清单里声明

第三层 · 向上游提两个需求（本包一行不改）

  1. 开关文件应该跟着日志目录走（放进目录内，或键里带上 logDirName），而不是只跟 pluginId 走。这样"目录不同、开关同名相撞"这一整类问题从根上消失。
  2. 给一个"按目录查活跃实例"的只读出口。有了它，本包在冲突时可以直接复用宿主插件的实例（当客人，不建第二个写者），冲突彻底消解，宿主插件一行代码都不用改。已确认 dsh-log/node 的导出面只有 createNodeFileService / createNodeTimer / createNodeHostLog / createQuickLog —— 没有这类出口。

第 2 条的精确边界见 8.6：它只在两个插件派生出同一个目录时生效，不会让本包找到宿主插件。

另有现成做法：给本包一个不同的 pluginId（副作用超出日志）

宿主插件可以传 pluginId: 'b-update' 而 prefix 仍传 'b' —— 本包立刻有了独立目录与独立开关，零代码改动。但 pluginId 管的不只是日志：它还是事件清单的标识、安装锁的持有者记录、跳过盘的路径组成。拿它当"日志开关旋钮"是用大锤敲小钉子。

08开关归属：为什么是一个，而不是两个

这一节回答两个问题：上游把开关改成跟着目录走、再加一个"按目录查活跃实例"的只读出口之后，能不能保证"B 的日志和 A 的日志两种都在，且 B 两种都看得到"；以及 A 没有自己的开关时，B 该怎么控制 A 的啰嗦程度。答案要从开关到底是什么开始。

8.1 前提纠正：开关不是日志的总闸

引擎的准入判定只有三句话（dsh-log 0.3.1 · dist/engine/pipeline.js:192-198）：

function isEnabled(level, event) {
  if (isUrgentLevel(level)) return true;                                    // error/warn 恒放行
  if (typeof event === 'string' && RESIDENT_EVENTS.has(event)) return true;  // 常驻恒放行
  return getSwitchEnabled() === true;                                       // 其余才看开关
}

三个分类：紧急（error/warn）、常驻（kind === 'resident'）、残差（其余）。开关只管第三类。常驻名单是「引擎固定 43 条 ∪ 调用方清单里标了 resident 的事件」（pipeline.js:182-188）—— 这正是本包那 18 条 resident 声明的意义：不必为了几行轨迹去打开全局开关。

本包 26 个事件按这套判定落下去：

分类条数受开关管是哪些
紧急级别7否host.call.fail update.batch.entry.fail update.check.fail update.lock.anomaly update.panel.render.fail update.store.fail update.log.degraded
常驻 info12否host.call update.wire.ready update.queue.transition update.status.changed update.install.request update.install.exec update.install.verify update.check.done update.batch.entry.request update.batch.summary update.panel.mount update.panel.action
残差 info7是update.poll update.registry.fetch update.check.start update.changelog.parse update.channel.decide update.lang.applied update.panel.state

所以"A 没有开关 → 低级别日志打不出来"的真实含义是：A 的 7 条噪音不打。诊断一次更新失败要看的证据行（check.fail、install.verify、store.fail、lock.anomaly、queue.transition、panel.render.fail）全在恒放行的 19 条里。啰嗦程度与可观测性不是同一个旋钮 —— 引擎把证据类做成级别与常驻属性，把体积类留给开关，这是有意的分工。

if (wantPlugin !== config.pluginId)
    return { ok: true, entries: [], denied: true };

一个 logQuery 只读自己的桶，问别的插件标识得到的是空集 + denied。跨桶唯一的路是 aggregateLogQuery(requester, sources, grants, args)（dist/host/aggregate.js:13）：自己搭 sources 清单、自己授权、自己知道对方的标识与目录。人（终端）两条都看得到 —— dsh-log <logsRoot> 往下探一层，把每个目录都列出来。

8.4 两个开关不是"多一个控制"，是"少一条读取路径"

自有目录形态下，B 拿到独立开关的代价是：B 自己的 logQuery 对 A 返回 denied，B 必须另建一套聚合接线才能看见 A。独立性不是白拿的，它把"一条读取路径"换成了"一套跨桶读取"。所以"B 要 2 个开关还是一个"这个问题问反了 —— 该问的是"B 要几条读取路径"。

8.5 三个实测硬边界：决定"能不能真的拧到"

01
开关是实例级闩锁。每个实例一辈子只从盘上读一次开关（switch-file.js:25-28）：if (switchLoaded) return getSwitchState()。所以改 JSON 文件是重启级旋钮，对活着的实例无效；运行期只有一条路 —— setSwitch()（switch-file.js:83），对外就是 logSetSwitch 电话。
02
本包一个电话都没注册。grep "logSetSwitch|logGetSwitch|logQuery|registerHostLogPhones" src/ → 无匹配。dsh-log 0.3.1 有六个宿主日志电话（dist/host.d.ts:22）：logBatch / logExport / logClear / logGetSwitch / logSetSwitch / logQuery；本包走的是 dsh-log/node 的 createNodeHostLog，那个入口明说"不注册电话"（dist/node.d.ts:42）。所以今天 B 没有任何程序化旋钮：既开不了 A 的开关，也查不到 A 的行。这是比"两个还是一个"更前置的缺口 —— 开关存在，但没有人能拧它。
03
客人模式走的是集成方那台引擎。本包调的是 logCtx.fire(...) 而不是 store.log(...)，isEnabled 也取自那台引擎（src/log/sink.ts:47-48）；本包只把闸的判断原样委托出去（src/log/emit.ts:172-174），自己不做任何级别过滤。"一个开关"的机制来源就在这里。

8.6 上游那两点修好，保证什么、不保证什么

上游改动保证到不保证
开关文件跟着日志目录走不互相覆盖。两个 sink 各自独立、各自有开关，"目录不同、开关同名相撞"这一整类问题消失不改变拓扑：A 仍可能在自己的目录里，B 仍看不到它
按目录查活跃实例同目录相撞时不再抛错，改为复用（从硬失败变成当客人）不会让 A 找到 B。A 知道的是共享根和自己的目录名（由自己的 pluginId 派生），不知道 B 的目录名

第 2 条的边界要说清：它只在 A、B 恰好派生出同一个目录时生效 —— 那取决于 B 是否按现场惯例把 logDirName 覆盖成裸名（logs/<插件名>/），而不是用引擎默认的 logs-<id>。两种情况都存在，所以它是有用的兜底，但不是发现机制。

安全 ≠ 可见

两点修好买到的是「不互相覆盖 + 谁都不会静默变成零行」，不是"B 看得到 A"。可见性是读侧的事，读侧要的是「A 写进 B 的桶」或「B 搭聚合」—— 与那两点无关。

8.7 结论：一个开关，而且是免费的

  • 客人模式 = 1 个 sink = 1 个开关 = 1 条读取路径。A 的 21 条证据行不受开关管，B 永远拿得到；A 的 7 条噪音与 B 自己的残差行同闸 —— 而噪音本来就按体积分类，不分属主。
  • 所以"B 既看得到 A，又管得住 A 的啰嗦程度"的正确形状就是客人模式 + 一个开关。两个开关的形态会自动丢掉"一个视角"。
  • 还有一条死角（第 6 节已说）：最该被看见的那行是 update.log.degraded，而它记的正是"本包建库失败"—— 建库失败意味着没有 sink，这行哪儿都写不进去（src/host.ts:779 的注释自己承认了）。保证 B 看得到 A 的最有效办法，是保证 A 有一个能用的 sink。上游那两点对这件事的真正价值在这里。
要的是契约，不是巧合

"A 写进 B 的 sink"今天取决于 B 是否记得把 logCtx 交给 A。要让它从巧合变成保证，只有一条路：把"你也有 dsh-log 就必须给 logCtx"提成前置条件（第 7 节第一层），并在建库失败时把 lastOwnLogDegraded() 露到面板上。

9.1 常驻表不是白名单，是例外放行

一个具体的困惑值得当场跑一遍：我想打一行 debug，结果被无视了 —— 是因为它不在常驻表里吗？不是。是因为开关默认是关的。下面是实测（一个自建 dsh-log 实例，清单里只声明了一条常驻事件）：

开关初始状态: {"enabled":false}

--- isEnabled 逐个问（开关关着）---
  isEnabled(error, demo.err)           = true
  isEnabled(warn,  demo.warn)          = true
  isEnabled(info,  demo.normal.info)   = false
  isEnabled(debug, demo.normal.info)   = false
  isEnabled(info,  demo.resident.info) = true
  isEnabled(debug, demo.resident.info) = true

--- 开关关着时逐条写 ---
  error/demo.err           → queued
  warn/demo.warn           → queued
  info/demo.normal.info    → skipped      ← 被无视
  debug/demo.normal.info   → skipped      ← 被无视
  info/demo.resident.info  → queued
  debug/demo.resident.info → queued
丢弃计数 getDroppedCount() = 0

磁盘上只有 4 行：error / warn / info(常驻) / debug(常驻)
打开开关后同样 6 条全部 queued，文件变 10 行
要点一
常驻表只能加权限，不能减。不在表里 ≠ 被拦；真正的拦是开关。表是开关的例外名单。
要点二
常驻按事件名，不按级别。标了常驻的事件连 debug 都照落 —— 实测 isEnabled 对 debug 级别的常驻事件仍返 true。
要点三
被无视是静默的：getDroppedCount() = 0。skip 不算丢行 —— 你写了、磁盘上没有、也没有任何计数提示。

9.2 那为什么还要有常驻表

引擎有两个互相打架的职责：证据要够 与 盘不能爆。最钝的工具是全局开关 —— 开＝全落，关＝只剩 error/warn。但两头都不对：关着的时候你仍然需要那几行关键轨迹，否则事后无从复盘。于是需要一个中间类：按体积算不值、按证据算值的行。

为什么按事件名
体积是事件的属性，不是级别的属性。update.poll 一秒一行（体积大、证据少）；update.install.verify 一次安装一行（体积小、证据大）。两条都是 info —— 级别分不开它们，事件名能。
为什么必须事先登记
"这几行一定在"是对读日志的人的承诺。承诺只能写在事前清单上 —— 这就是 resident 的语义，也是它为什么是清单而不是运行时判断。
代价
判断权在生产者的清单里，且在运行期之前。忘了登记 → 那条就落进开关管辖。本包那 7 条就是这么落进去的（见 8.1）。

9.3 两种落法：日志本归谁

A 的行必须落到某个文件里。B 已经有一本日志本（B 自己建的 dsh-log 实例），于是只有两种落法：

落法一 · 用 B 那本（客人模式）

<homeDir>/logs/
├── log-switch-b.json        ← 唯一的开关
└── logs-b/
    └── 2026-10-15.log       ← B 的行 + A 的行
                                 混在同一个文件里

B 的面板读的就是这个文件 → 两种都在，一次看全。开关只有一个 → B 一按，B 的啰嗦行和 A 的啰嗦行一起开关。

落法二 · 自己再开一本（自有目录）

<homeDir>/logs/
├── log-switch-b.json        ← B 的开关
├── log-switch-a.json        ← A 的开关
├── logs-b/
│   └── 2026-10-15.log       ← 只有 B 的行
└── a/
    └── 2026-10-15.log       ← 只有 A 的行

B 的面板只读 logs-b/ → 看不到 A。要看到，B 得另用 aggregateLogQuery 同时读两本，还得知道 A 的目录名 —— 这就叫"接线"。

9.4 谁决定用哪种？—— logCtx 递不递

logCtx 是什么
一个对象，有 fire(level, event, fields) 方法 —— 就是集成方手里那支"写日志的笔"（src/log/sink.ts:42-50）
可不可选
createHostUpdate(deps: { …, logCtx?: LogCtx, … }) —— 可选（src/host.ts:1011）

不递 → 本包自己开一本 → 自有目录
今天的默认

默认形态是自有目录。所以"B 看得到 A"今天不是保证，取决于 B 有没有递笔。

怎么知道自己处在哪种形态：update.wire.ready 这行常驻 info 带着 logSink 字段，三种取值（src/host.ts:766 / 785 / 790）：

这行是"接线一次一条"的常驻事件，不受开关管 —— 也就是说：无论开关什么状态，你都能从日志里读出这台实例处在哪种形态。

10.2 会增长，但不会"额外"维护 —— 而且判据是一条规则

先消除最坏的那个想象：不需要动 dsh-log。加一条常驻事件 = 改本包自己的清单一个字段 + 发本包一个版本。

再消除"忘了更新"：kind 是清单的必填项，漏了当场抛错。实测四种残缺清单：

缺 kind     → 抛错  [dsh-log] 事件清单 eventList 非法：事件 a.b 的 kind 只许 resident、ondemand、selfmon
kind 写错    → 抛错  [dsh-log] 事件清单 eventList 非法：事件 a.b 的 kind 只许 resident、ondemand、selfmon
缺 level     → 抛错  [dsh-log] 事件清单 eventList 非法：事件 a.b 的 level 只许 error、warn、info、debug
缺 fields    → 抛错  [dsh-log] 事件清单 eventList 非法：事件 a.b 的 fields 必须是字符串数组

所以在字段层面，"忘了更新常驻表"不可能发生 —— 建库直接拒绝启动（dist/config/event-list.js:90-91）。

判据也不是感觉，是一条硬规则（docs/research/20261014-log-event-catalog.md §0:12-15）：

resident
调试开关关着也落盘，因此必须边沿触发（不变量，铁律）
ondemand
开关打开才落盘，可以逐次打点
selfmon
本包日志接线自身的降级，永不外抛
翻译成人话

加事件时问一句："它会不会重复发？" 会（轮询／逐帧／每次调用都发）→ 只能是 ondemand；只在状态真变了、或一次操作一次 → 才可以 resident。

这就是为什么 update.poll 是 ondemand 而 update.status.changed 是 resident —— 两条都是 info、都跟轮询有关，但一条逐次打点、一条只发边沿。

结论

11.0 审查怎么做的

对每一条问三个问题：

  1. 现象是真的吗？ 重跑，不看注释看行为。
  2. 这是引擎的缺陷，还是它明确的设计选择？ 去读它自己写的注释。

教训

第一版的四条全部来自读代码时的偶遇（注释与代码不一致、门闩、租约），没有一条来自目的地的反推。偶遇发现的缺陷看起来"实在"，但往往既不是最贵的、也不是最该由上游修的。

11.1 撤下①：跨进程租约 —— 我的证据是错的

上一版写的是「跨进程拦不住 → 越过封存线会丢批 → 另一方毫无感知」。重跑之后，三条全错：

我上一版的主张实测反证
越过封存线会丢批两个进程各发 1200 条，落盘 2400 条一条不少（父 1200 + 子 1200）。写盘失败会进重试位，退避后再来
失败只躺在一份没人读的 ready 回执里引擎自己写了一条 warn 自监控行，就在同一个日志文件里：{"level":"warn","event":"log.persist.fail","fields":{"pluginId":"shared","op":"writeBatch","reason":"foreign-write","dirHash":"ea82f282"}}
引擎对跨进程没有机制它主动检测：自己上次写完的长度与读回来的长度对不上，就判定"有别的写者动过这份文件"

它自己的代码注释写得很清楚（dist/engine/pipeline.js:740-744）：

// 跨进程可观测：读回来的长度与我们自己上次写完的长度对不上 → 有别的写者动过这份文件。
// 读失败（readOk 为假）不算：那是读不出来，不是被人改过。
if (readOk && fileName === expectedFileName && expectedFileBytes >= 0 && existingBytes !== expectedFileBytes) {
    notePersistFail('writeBatch', 'foreign-write', logDir);
}

重试位那段注释同样是明写的：

// 写盘失败（重试 1 次后仍失败）：这批行**不丢**——放回重试位，退避后再来（#23 审查必改 R2）。
// 只有撑到内存上限才丢最旧的普通行，且那一次要响（计数 + onDrop）。
判决：撤下

引擎对跨进程的态度是容忍 + 观测 + 重试 + 计数，不是"忘了加锁" —— 那四个字「跨进程可观测」就是它替这件事写的注释。要求它改成文件系统级互斥，等于要求它推翻一个它明确写下来的设计选择，而且我们自己的 ADR-0005 早就把跨进程划到承诺之外。这一条不该提。

11.2 降级②：tail 子命令 —— 真，但该我们自己改

现象仍然成立（dsh-log tail <dir> 会多吐一句 没找到日志目录：tail，日志照常输出）。但对抗式一问"该谁付钱"，结论变了：

开发前开发后
dsh-log 的解析器任何非 - 开头的词都当路径 → tail 被当成一个不存在的目录忽略前导 tail；代价：一个真名叫 tail 的目录从此扫不到
它的 USAGE写 dsh-log tail <目录...>，与解析器不一致改成 dsh-log <目录...> 即与代码一致
我们的文档README §11 四个例子、面板路牌全带 tail → 用户看到警告去掉 tail 三个字 → 今天就干净（0.16.3 已改）
判决：我们改，不是它改 —— 已执行

把 tail 从我们的文档里删掉，是一行改动、零风险、立刻生效，而且两种上游修法它都兼容（它忽略 tail 也好、改 USAGE 也好，我们不带 tail 的写法都对）。要求上游改而自己不改，是让用户替我们的等待付时间。上游那条只作为"文档与实现对齐"的顺手一提，不值得单独排期。0.16.3 已落地：面板路牌与 README §11 的命令一律写成 npx dsh-log <目录>，并在 README §11 与本节写明「为什么不要写 tail」。

11.3 降级③：开关热更新 —— 在要一个我们说过不要的能力

现象成立（switchLoaded 一次性门闩，运行中改开关文件不生效）。但这条在要的东西和我们的 ADR 直接冲突：

  • 受益的唯一路径是「第三方在运行中打开另一个实例的日志」—— 那正是"第二个主人"的行为，ADR-0005 明确写了本包永远只当客人。
  • 它自己的设计说明也把开关定为宿主权威：dist/engine/switch-file.js:21-22「开关从盘上读回…重启后保持，对账以宿主为准」。让文件变成活通道，等于给它造出第二个权威。
  • 我们支持的路径（B 把自己的 logCtx 传给 A）不受影响 —— 开关在 B 建库时读，B 自己的开关照常即时生效。
开发前开发后
第三方打开别人实例的 info必须重启对方不用重启
这条能力我们想要吗不想要 —— 它是"第二个主人"，我们拒绝过的耦合
我们真正需要的不知道"改开关要重启"把这句写进 README 即可，无需上游改动
判决：降为文档事实

不是缺口，是边界。我们自己把它写清楚（"开关改动需重启实例"），比要求上游拆掉门闩更对。

11.4 撤下④：清单合并上游化 —— 不该替所有人定策略

引擎刻意把 eventList 当成一份普通数据输入（一个实例一份清单），合并是策略问题：同名事件谁的 level 说了算？谁的 kind 说了算？我们的答案（"字段取并集，级别与归类按声明方"）只是我们这一家的答案。推到上游等于要求它替所有人裁一次，是范围蔓延。

而且我们本来就需要它 —— mergeUpdateEvents 留在包内即可，第三方集成时用得上，用不上也不欠谁的。

判决：撤下

11.5 真正该提的两条：从目的地反推

目的地是三件事：每个环节可交日志、多插件不覆盖、第三方一条命令把日志交给我们。拿它当尺子量一遍，缺口只有两处 —— 都在"读"这一侧。

① 宿主侧写入路径拿不到 trace 上下文（追链只对客户端行有效）

这不是"我们忘了传参"，是结构上没有位置：

  • 宿主侧行构造是 buildRowText(level, event, fields)（dist/core/row.js:16）—— 三个参数，没有 trace 槽。
  • store 的写入面是 log(level, event, fields)（dist/store.d.ts:23）—— 同样三个。
  • 建链只长在客户端写入路径里：ensureTraceForLevel(level) → ensureSpanId() → out.traceId / out.spanId（dist/client/write.js:110-123）。

后果正好打在价值最高的地方：本包多步链全在宿主侧（查 → 判 → 装 → 验），而它们一条都追不了；--trace 只对面板侧那 5 个客户端事件有效。

开发前开发后
宿主侧的行只有 ts + 事件名 + 字段，无法把"一次用户意图"串起来带 traceId/spanId，与客户端行同一套链
dsh-log --trace <id>只命中面板那 5 个事件能命中 update.check.start → …done → install.request → install.exec → restart.outcome 整条链
我们要写的东西每次操作在日志里按时间窗+事件名人工筛一条命令看完整条链
要什么

让宿主侧写入路径也能带 trace 上下文 —— 形式随它（store.log 收一个可选的 trace 参数、或提供一个 withTrace() 包装）。这是目的地"每个环节可交日志"里唯一还没闭环的一环。

② 打包导出只能在宿主里做，读侧拿不到（"交日志"少一件最好的产物）

引擎已经有一份理想的交接产物：handleLogExport()（dist/store.d.ts:63-105）产出的是自包含文本 + 摘要 —— 摘要里带 pluginVersion、os、cwd、logSwitch、启动头（pid / startedAt / dir）。这正是"把日志交给我们"最需要的东西：对方不用解释环境，我们不用猜。

但它是 store 的方法，而 CLI 是纯读侧（它的承诺原话：「本命令不写、不改、不删任何文件（包括不写缓存与状态）」），所以手里只有一个日志目录的第三方，拿不到这份产物 —— 只能 --json 倒原始行。

开发前开发后
第三方交日志--json > update.log，没有环境上下文（版本、系统、开关状态、启动头都要人另说）一条命令产出自包含卷宗，环境信息随包走
我们收到的工单一堆裸行 + 来回追问"你什么版本、什么系统、开关开了吗"打开就有答案
前置条件必须有人在宿主里把 logExport 电话接上只有目录也能产出
要什么

让读侧也能产出 handleLogExport 那种带摘要的自包含导出（dsh-log export <dir>，或把摘要能力暴露成纯读函数）。代码已经写好了，缺的只是到达路径。
