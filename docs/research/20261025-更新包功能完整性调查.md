## 0. 结论摘要

**一句话：这轮升级的「设计」是自洽的；但「生产可用」没有被证明，且「单写者」这条关键不变量在代码层面就不成立。基础更新链路不是全坏——真机有成功记录；但同进程多插件会互踩检查凭证、入口件能在未检查时宣称「已最新」（§2.5），中枢链路则在真机跑了 0 次、测试全部是假 transport，取消/队列路径另有实测缺陷。因此规格 #246 不能关，0.18.40 也不该以「已支持自更新不断链」的说法直接发布。**

分三层看：

| 层 | 实际状态 | 判断 |
|---|---|---|
| 单插件 / 批量基础更新 | 真机有 `completed` 记录（palette 自更新、im-companion、skills-deck、life-pack），也有 5 家 `failed`（bundle-in-use，要求重启后手动重试）；同进程多实例会互踩检查凭证（§2.5） | **可用，但不完全可靠**；失败路径是人工兜底 |
| 中枢（本次升级的核心） | 两份真机 profile 都还跑 0.18.38；盘上没有 `update-queue/*/hub/`；日志 0 条中枢事件；单写者与取消/队列路径另有实测缺陷（§4、§5.4） | **未投产**；全部「断链续跑 / 全局进度 / 重启续跑」只有单进程假测试 |
| 验证与交付 | 门禁绿；12 项必测 8 covered / 4 partial；真机 5 项 0 执行；#249 修复已合 master 但未发布 | **实验室绿，生产未证** |

不是「整个更新器都是坏的」。日常更新大多数能装，真机证据支持这一点。坏的是：**这轮升级最核心的承诺（自更新不断链、重启续跑、单写者）在被真机验证之前，就被当成「实现完成」记到了票上。**

## 1. 这次升级到底改了什么（功能层）

把批量更新的「执行者」从发起它的插件页面，搬进 DSH 进程：

1. **进程级单泵**：`createMultiHostUpdate` 把执行席（属主、方案、读写会话、查/装、日志、收尾回调）交给 `globalThis` 上按 `(homeDir, profileDir)` 分槽的注册表；fiber 销毁后泵仍能跑。
2. **盘上两份文件**：`<queue>/hub/plans/<owner>.json` 方案（只写意图）+ `hub/lease.json` 租约（心跳 5s、陈旧 20s、代次 +1、释放只认自己）。
3. **只读全局进度电话**：`<prefix>.updateHubStatus`，从盘上聚合方案 + 各属主账本 + 清单 + 租约，回快照（8 会话 × 20 行上限）。
4. **可选常驻进度坞**：`mountHubProgressDock(container, …)`，1s 轮询、页面隐藏暂停、空闲隐藏、`dispose()` 只停轮询。

对应 ADR-0008、规格 #246 与实施票 #247–#252。设计目标本身没有明显错误；问题出在实现与验证。

## 2. 基础链路：真机实际做到了什么、坏在哪

### 2.1 成功面（E 级）

从 `~/.dsh/updates/<pluginId>/<scopeHash>/state.json` 读到的真机终态：

| 范围 | 插件 | 状态 | 目标版本 |
|---|---|---|---|
| desktop | dsh-opencode-palette | completed（自更新，2.1.7→2.1.10） | 2.1.10 |
| desktop | dsh-im-companion | completed | 0.2.25 |
| desktop | dsh-mattpocock-skills-deck | completed | 1.9.0-beta.17 |
| desktop | life-life-pack | completed | 0.3.85 |
| desktop | life-bill / life-calorie | restart-required | 0.3.85 |

这些说明 **check → install → 宿主应用** 的基本链路在真机是工作的，不是「连装都装不上」。

### 2.2 失败面：bundle-in-use（E 级）

2026-10-24 那轮 life 批量更新里，4 家失败状态是同一类：

```text
install-failed: bundle-in-use；可能已被宿主移出在册名单；请重启 DSH 后重试更新，
若插件页显示关闭请重新启用 (dsh plugin --profile desktop add --save-exact
life-chef@0.3.85 …)；宿主在移除步骤里已把这个插件移出在册名单，本次已恢复在册；
更新未完成，重启 DSH 后可重试
```

同一批的 `life-chef`、`life-home`、`life-memo`、`life-schedule` 都是这个结果（盘上仍在册，旧版本继续运行）。另有 `dsh-prompt 0.4.38` 从 2026-10-20 起一直 failed，也是 bundle-in-use，只是措辞是旧版「请先在宿主插件页停用后再更新」。

这是宿主 `removeBundle` 的既有边界，不是这轮升级引入的回归：正在运行的插件 bundle 不能被自己卸载。但**更新器在失败后没有自动恢复编排**——账本只留 failed，用户必须重启 DSH、再手动点重试。新中枢本应兜住「重启后继续」，但它没在真机跑过（见 §3），旧的无方案批次又不接管（规格 L103），所以现状就是人工重启 + 人工重试。

### 2.3 账本字段存在自相矛盾的样本（E 级，0.18.38 产物）

desktop 的 `life/batch.json` 里有一行：

```json
{ "key": "calorie", "phase": "done", "error": "recovery-required" }
```

而同一插件同一轮的 `state.json` 是 `restart-required`。「完成」的行上挂着错误码，任何按行渲染的面板/报表都可能把它显示成失败。这不是本轮新增（0.18.38 盘面），当前 master 的 `BatchEntry` 仍允许 `error` 与 `phase:'done'` 并存；没有用例断言「done 时 error 必须为空」。属 P2 数据语义问题。

另外 web profile 有 5 个 `interrupted / installation-changed` 从 2026-10-21 一直留到现在（5 天），说明**旧失败/中断账本没有自动清理**；面板能展示，但不会自己消化。

### 2.4 小结

- 基础更新：**能用**；不是「功能全坏」。
- 主要缺口：运行中插件更新必然失败（宿主限制），失败后没有自动续跑；账本可能留下 done+error 的混合态；同进程多实例还会互踩检查凭证、入口件可能在未检查时宣称「已最新」（§2.5）。
- 这两点都不是中枢能自动解决的——中枢只负责「谁推进」，不改变宿主「不能卸载使用中的 bundle」这一事实。

### 2.5 单插件基础链路自己的四处缺陷（A 组实测，非中枢引入）

A 组用真 `dist` + 假 npm 源/假桌面管理器跑了 14 个探针（`.tmp/research/single-host/`）。README 三步接入、already-installed 两步、装完重启 `completed`、dev-source 拦截、prerelease、`minimumReleaseAge` 退回落合规版、排队/陈旧锁、幂等重试、changelog/logAppend 都实测可用。另发现四处：

1. **同进程两套更新器会互相挤掉检查凭证（P1）。** `src/host/capabilities.ts:52-53` 是模块级**单槽** `sharedReader`；:193-194 的 key 含 pluginId/prefix/profileDir 等，第二家任一电话即按新 key 重建并覆盖唯一槽（:390、:425），旧 reader 连同 `src/core/service.ts:310` 的 `checked` 一起丢，:1064 于是抛 `check-expired`。A 组探针 `p10-interference.mjs`（Lead 已重跑）：A.check→A.install 成功；B.check 后，A 用**自己仍有效**的 checkId 装 → `{ok:false,error:'check-expired'}`，manager 0 次，日志 `update.install.fail{stage:'gate',code:'check-expired'}`；2 秒内重查也不命中缓存。`p11` 用两套不同 home/profile 复验仍如此（排除 pluginId 串号）。README:18/66 写「多插件不串内存状态」与此不符；批量与面板有「遇 check-expired 重查」兜底（`phones.ts:388-414`、`mount.ts:1356-1401`），README 教接入方直接用的裸电话没有。
2. **入口件没联网就宣称「已是最新 X.Y.Z」（P1）。** 默认 `autoCheck='mount'` 只调 `updateStatus`、不联网（`src/panel/entry.ts:557-568`、:763-764）；`upToDateVersionOf`（:157-161）只要求 `hasUpdateOf` 为假，而 `latestVersion=null` 同样为假，idle 分支（:474-477）直接拿 runningVersion 断言「已最新」。A 组 `p15-entry-mount-state.mjs`（Lead 已重跑）：真远端 2.0.0、挂载前 `latest=null`，挂载后按钮显示「已是最新 1.0.0」；点击后才变「有新版本 2.0.0」。:49-50 的类型注释写「联网一次」，与实现相反。
3. **面板把 owner 行渲染成「排队第 0 位 / 前方还有 -1 项」（P2，纯展示）。** `src/panel/render.ts:948-950` 只特判 `pos===1`，`pos=0`（自家正在装）落入 else；:956 又不区分 `aboutSelf`，恒显示「安装完成后自动轮到你」。A 组 `p13-panel-e2e.mjs` 复现。
4. **manager 抛异常时 `update.install.fail.reason='unknown'`（P2，诊断口径）。** 结构化 `failed` 回包记 `host-rejected`，throw 路径没有分类；`job.message` 仍有宿主原话（A 组 `p5-failure.mjs`）。

## 3. 中枢：真机 0 次运行（P0 证据缺口）

3. 遍历 `~/.dsh/logs/**/*.log`，对 `updateHubStatus|hub.plan|hub/adopt|hub.lease|hub.takeover|hub.activate` 的匹配数为 **0**。
4. 之前的发布与计划核对：npm `latest=0.18.39`，无 `v0.18.40` tag；`npm run release` 计划模式也只是计划（写了一个 `.scratch/release-0.18.40.log`，没有执行发版）。

### 3.2 这意味着什么

规格 #246 的四条 Solution、三条真机验证、五条真机验收，全部只存在于：

- 单进程内的 `tests/hub-*.test.mjs`（`fakeTransport` + 注入的 `hubIsProcessAlive`）；
- `dispose()` 模拟 fiber 销毁，而不是真实 bundle 卸载；
- 纯逻辑函数测试。

**没有任何一条证据来自「真实宿主 + 真实安装 + 真实自更新」的组合。** 因此当前能说的最强结论是「设计完成 + 单进程测试通过」，不能说「已支持自更新不断链」。

## 4. 中枢「单写者」不成立（P0，代码 + 复现）

### 4.1 五个代码级缺口（A 级）

1. **心跳窗口 20s，而一个安装步上限 15min。**
   `src/core/hub/lease-policy.ts:5` `HUB_LEASE_STALE_MS = 20_000`；`src/shared/commands.ts:39` `INSTALL_TIMEOUT_MS = 15*60_000`。心跳只在每步之后写（`src/host/hub/registry.ts:346`），单步安装过程中没有任何心跳。合法安装超过 20s 时，另一个进程就能依据「心跳陈旧」接管；这与规格 US21「崩溃或卡死后最多一个心跳窗口接管」看似一致，却把「正在正常安装」也当成了「卡死」。
2. **租约缺失时心跳会把旧代次写回去（复活）。**
   `registry.ts:472-486`：`heartbeat` 读到 `current === null` 时不会判 lost，而是继续 `writeHubLease({...lease, heartbeatAt: now})`。若新驾驶位已经释放租约，旧驱动下一次心跳会把**旧 generation 的租约重新写回盘上**，造成代次倒退/所有权翻转。
3. **租约读-判-写没有 CAS。**
   `ensureLease`（`registry.ts:437-453`）是 read → decide → write → read 确认；两个进程可以同时读到「无租约」，各自写 gen1，最后一次写赢，但先写者可能在自己的 read 确认里看到自己的租约而短暂认为也是 owner。`releaseIfOwner`（`:488-493`）同样是读后 unlink 的 TOCTOU。
4. **预查在驾驶位之外写账本。** `src/host/batch/fan-out.ts:1090` 先 `precheckSelectedToReady`（会把 `installing` 退回 `pending` 再写成 `ready`）才 `submitHubTask`；中枢只冻结「装阶段」，预查不受租约保护。B 组探针实测：A 正在 install 时，B 的 `installPhone` 预查直接把 A 的 `installing` 行写回 `pending→ready`，然后才去接管租约。
5. **账本写回没有代次栅栏。**
   `driveTask` 的 `save`（`registry.ts:318-323`）只做「读盘最新 → 行级合并 → 覆盖」，不校验自己是否仍持有当前 generation；而「是否仍持有」的检查在保存之后（`:346-349`）。因此旧驱动可以在被接管后仍然写账本。`stillOwnsLease`（`:460-466`）在「读不到租约」时返回 `true`（把自己当属主），进一步放宽了窗口。

### 4.2 跨进程复现（C 级）

脚本：`.tmp/research/lead-repro/run-repro.mjs` + `worker.mjs`；两个 node 进程共用临时 home/profile；直接使用 production `dist/host/hub/registry.js` 的 `submitHubTask`。A 进程的 `seat.install` 睡 25s 后返回 failed；B 进程在 t≈21.5s 提交同一 owner/session。

实测：

- A、B 都进入 install（两条 `install-start`，pid=35460 / 65684）→ 租约层双驱动；
- B 在 21.85s 把行写为 done；
- A 在 25.12s 写 failed，覆盖 B 的 done；
- 最终 `batch.json` entry = `failed / install-failed`；两个 submit 都收到 `'done'`；最终 `lease = null`。

B 组在同一装置上又跑了一遍（单进程、两个中枢槽，`02-long-step-double-install.mjs`，Lead 已重跑复现）：A 的 install 挂起 26 假秒（A 进程仍存活），B 以 generation=2 接管；事件里**同一 key 出现两次 install**（A@1e6、B@1.026e6）；B 把 `a` 写成 `done` 后，A 的迟到结果把 `a` 覆盖成 `failed`（1 ms 采样 `done -> failed`），落盘时 B 正持 g2；B 释放租约后，A 的心跳把已删除的 g1 租约写回（`leaseAfterLateWrite={driverId:'dsh-hub:67032:proc-A',generation:1}`）。

**限制（必须写清）**：`seat.install` 是替身，绕过了真实的队列 `global.lock`。真实安装路径下，B 的安装会在全局锁上得到 `update-busy → queued`，所以「两个进程同时真的装」不一定发生。这个复现证明的是**租约/写回层没有代次栅栏**；不是「生产必现双安装」。但第 4.1 条的 1–4 都是生产代码路径，且真实世界的慢安装（>20s）完全常见，所以规格 US19–21、必测第 6 项要求的「单写者/旧代次写回被判非属主」在实现上不成立。

### 4.3 后果（按可能性排序）

- **必然**：任何超过 20s 的安装步，都会让另一进程/另一实例认为驾驶位陈旧，从而接管、代次 +1；
- **高**：新驾驶位在自己的步骤里被队列锁挡回 queued，让位并释放租约；旧驱动随后心跳时可能把旧代次租约写回（复活），两边来回「接管—复活」，租约抖动；
- **中**：旧驱动在接管后完成保存，把新驾驶位的账本行覆盖（复现已示）；两个调用方对同一批更新收到不同结果（done / queued / failed）；
- **低但非零**：两个进程同时真正执行安装（需要刚好绕过/绕过锁的路径），造成宿主层重复动作。

测试没有覆盖这些：`tests/hub-process.test.mjs` 用 `fakeTransport`（:97）并显式传 `hubIsProcessAlive: () => true`（:254/:294）；没有任何真实多进程用例。#249 修的「活进程+心跳陈旧可接管」只是让这个缺陷更容易发生，并没有修代次栅栏。

## 5. 其余承诺与实现的偏差

### 5.1 自更新不断链：前提未真机验证（P0 证据缺口）

ADR-0008:24 断言「宿主根服务不随某个 bundle 卸载而失效，所以 fiber 销毁后这些引用仍可调用」；同文件 :76 自己写「『跨 fiber 调用宿主对象』需要真机验证（桌面 pluginManager 引用在 bundle 卸载后仍可调用）」。规格 #246 风险 1 也说否则回退 `hub: false`。

现有测试用 `dispose()` 和假 transport 模拟，**不是**卸载真实 bundle。因此这条旗舰承诺（US1「自更新后剩余继续」）的成立与否，目前无法判断；真机 5 项 0 执行也证实了这一点。

### 5.2 孤儿接管只认原属主（P1，与 ADR/规格冲突）

ADR-0008:32 与规格 US31 写「任一使用本包的插件在挂载时……按通用席位接管续跑」；实现 `src/host/batch/fan-out.ts:1232-1260 adoptOrphanSessions` 第一行过滤 `if (plan.owner !== prefix) continue`（:1243），只接自己属主。重启后如果原插件不重新加载，孤儿方案不会被别的集成方接走。测试 `tests/hub-takeover.test.mjs:181` 还把「只接自己属主」断言成正确行为——**实现与测试一起偏离了 ADR**。

### 5.3 协议版本换代：直接换 state，不是「只观察」（P1）

ADR-0008:20：「版本不一致时后来者只观察、不接管」。实现 `src/host/hub/registry.ts:83-89`：版本不等就新建 fresh state 覆盖 `globalThis` 槽，注释 :86 写「协议换代：旧任务表不再被读」。同进程两个不同版本副本并存时，旧泵还在旧槽跑、新实例看不到旧任务；规格的「同进程多副本共用」与这条行为相反，可能造成双驱动或任务丢失。

### 5.4 取消、任务归属与队列公平（P1，实测）

B 组的四个探针（`.tmp/research/hub-runtime/{03-cancel-hub,03b-cancel-long,04-hol,06-hubstatus}.mjs`，Lead 已重跑确认；除 check/install 用假 transport 外，任务表、租约、账本、合并、队列都是 production `dist`）：

1. **让位空档取消 → 空账本幽灵任务，同槽停摆约 24 秒。** 安装返回 `queued`、任务让位（`lease=null`）后，`batchCancel` 返回 `ok:true` 并清空账本；但中枢里的任务还留在队列。它下一轮读到空账本，`runBatch` 返回 `stoppedBecause='empty'`，`drive-policy` 判 `yield`，任务回队；`hubBusyForScope` 持续 `true`，租约以约 1 秒周期 acquire/release，直到连续 10 次无进展（`HUB_MAX_IDLE_STEPS`）才在约 24 假秒后收尾。窗口内同槽后续任务与 drain 全部停摆。测试盲区：`batch-host.test.mjs` 只测「运行中取消回 `update-busy`」，没有测「已让位任务被取消」。
2. **旧任务会驱动一份新会话。** `driveTask` 每轮 `readSession()` 后只消费内容，不校验 `session.id === plan.sessionId`（`registry.ts:302-303`；对比 `snapshot.ts:200-242` 读快照时才校验 id）。探针 03 S3：取消后向同属主目录写入 `id='brand-new-session'` 的新账本（`b2=pending`），幽灵任务随后对它 `check b2`（t=+2s）、`install b2`（t=+5s）——旧 plan / 旧 selection 驱动了从未提交给它的新会话。
3. **队头阻塞（FIFO 无公平/超时）。** `pumpSlot` 只取数组第一个 `queued`；`04-hol.mjs` 两属主同槽，队头任务持续 `queued` 的 6 假秒内，队头 install 重试 2 次、后来属主 `install('c1')` **0 次**，释放后才开始。真实场景里另一家 pnpm 安装占锁数分钟，后来属主会整体饿死。
4. **`activeInstall.pluginId` 与 `plan.targets[].pluginId` 永不相等。** `src/host/hub/aggregate.ts:132-136` 用 `lease.pluginId`，而租约由 `ensureLease(slot, task.owner)` 写入 **owner 前缀**；`src/core/hub/snapshot.ts:262-271` 却拿 `plan.targets[].pluginId` 比对。`06-hubstatus.mjs`：新鲜租约 + 方案 target=`plugin-a` 时回 `activeInstall={pluginId:'own0'}`、该会话 `state='waiting'`。集成方按 pluginId 永远匹配不上，README:437 的 running/waiting 语义被污染。

## 附录 A：desktop profile 与 web profile 是否独立、会不会互相影响

**结论：安装状态基本独立；日志目录按插件 ID 共享，可能影响排障与健康读数，但不影响安装结果。**

- **使用范围键**：`(homeDir, profileDir)` 二元组。desktop = `C:/Users/辰辰洋洋/.dsh/profiles/desktop`，web = `…/profiles/web`；路径哈希后分别落到 `~/.dsh/updates/<plugin>/<hash>/state.json` 与 `~/.dsh/update-queue/<hash>/`。
- **独立部分**：
  - 两份 profile 的 npm 安装目录互不共享，`node_modules` 各装各的；更新一个 profile 不会改另一个的 `node_modules`。
  - 队列全局锁按 scope 分开（`src/core/queue/ports.ts:32-33` 明确「不同使用范围各用各的、可并行」）；desktop 的安装不会阻塞 web，hub 租约也按 scope 分槽，互不接管。
  - `updateHubStatus` 只读自己 scope 的队列目录；web 看不到 desktop 的进度，反之亦然。
  - 跨 scope 目标在批量层会被拒绝（cross-scope 检查）。
- **共享部分**：
  - 日志目录按 pluginId 派生、不含 profile（`src/host/environment.ts:229/239`）：`~/.dsh/logs/<pluginId>/`。实测 `~/.dsh/logs/dsh-opencode-palette/2026-10-25.log` 混有 `hostKind=cli` 与 desktop-manager 行；同一插件在两个 profile 的记录会落到同一目录。这只影响日志排障、健康判断，不影响安装状态。
  - npm registry / pnpm 缓存、磁盘空间共享；并发安装可能互相拖慢，但不会写错目标目录。
- **宿主进程层面**：当前 web GUI 端口 49681 的属主 pid 67068 是 DeepSeek Harness desktop host，命令行显式带 `--profile …/desktop`，所以**当前会话跑在 desktop profile 里**；web profile 当前没有进程。两个 profile 各自启动自己的 DSH 进程，插件运行实例也各在各的进程里；一个进程里的插件崩溃/重启不会影响另一个进程，但同一插件在两 profile 各装一份时，版本可以不同步（各装各的）。
- **更新含义**：在 desktop 更新一个插件，不会让 web 里的同名插件升级；需要分别更新。反过来，两个 profile 同时更新不同插件不会因为队列锁互相阻塞，但会争 npm/pnpm 磁盘与网络。
