## 1. 阻断项

### B1 行级选择（keys）被中枢整批驱动吞掉 —— 既有电话契约回归

**症状**：`hub:true`（有 `input.ctx` 时缺省即开）下，面板行内「装这家/重试」发 `{ keys: [key] }`（`src/panel/batch/mount.ts:1018-1021`），中枢按整份 session 推进，未选中的行也被 check + install。CHANGELOG 称「七个批量电话与回包形状一字不变」，与行为不符。

**证据**：
- 契约：`src/host-batch.ts:11-12`「`<p>.batchInstall { keys?: string[] }`：不给 keys 即全部提交；给了 keys 只推那几家（行内「装这家」/「重试」用）」。
- 中枢分支完全不看 `selected`：`src/host/batch/fan-out.ts:1079-1087`
  ```ts
  const seat = hubSeatFor(session)                 // 1079：方案/顺序取整份 session
  if (seat && hubScope) {
    const outcome = await submitHubTask(hubScope, seat, hubDeps)   // 1082
    driven = await readSession()                                   // 1083
  } else {
    driven = await driveLocked(session, selected, Infinity)        // 1087：旧路径才过滤
  }
  ```
  旧路径的过滤在 `src/host/batch/fan-out.ts:681-688`（`order: full.order.filter((key) => selected.has(key))`）；中枢 seat 的顺序是整份会话：`src/host/batch/fan-out.ts:606-627`（`const order = [...session.order]`）。
- `precheckSelectedToReady(session, selected)`（fan-out.ts:1078）只把选中行查成 ready，随后中枢仍会驱动其余 pending 行。

**复现**（`hub:true`，targets `[a,b]`，`batchInstall({keys:['b']})`）：
```js
// 输出（dist/host-batch.js + tests/helpers/batch-log-harness.mjs 的 mkScope/mkTarget）
{"hub":true, "calls":["check:b","check:a","install:a","install:b"], "phases":"a:done,b:done"}
{"hub":false,"calls":["check:b","install:b"],                       "phases":"a:pending,b:done"}
```
同一脚本 `hub:false` 行为正确（只装 b、a 保持 pending）——即回归由中枢分支引入。

**影响**：用户点「装这家」会顺带升级全部可更新插件；点「重试某一行」会把整批重推一遍。违背已承诺的电话契约与最小动作原则。
**修复方向**：HubSeat 携带 `selected`，由 `driveTask` 每轮构造过滤视图（与 `driveLocked` 的 view 同口径）；或 hub 分支只提交选中行视图。注意 `indexOf` 仍应取整批顺序（fan-out.ts:703-704 已处理）。

### B2 「queued 让位」累计 10 次被看门狗误判 failed

**症状**：另一插件正在装、`install` 返回 `{kind:'queued'}` 让位时，中枢任务在约 10 个退避周期（生产 1000ms × 10 ≈ 10s）后被判 `failed`，`noteRunOutcome` 写一条失败总账；账本仍停在 ready，用户看到失败但实际未失败。

**证据**：
- `src/core/hub/drive-policy.ts:59`：`if (idle >= maxIdle) return 'fail'` 位于 `switch (stoppedBecause)` 之前；`queued` 本应走 `:60-65` 的 `'queued' -> 'yield'`。文件头注释（`drive-policy.ts:21-22`）自称「让位不算失败」，与实现矛盾。
- 计数与判定：`src/host/hub/registry.ts:313` `task.idleSteps = progressSignature(session) === before ? task.idleSteps + 1 : 0`；`:316-321` 传入 `consecutiveNoProgress: task.idleSteps`。
- 失败码被改写：`registry.ts:324-333` 非 `finished`/`stopped-after-failure` 一律 `stoppedBecause: 'error'`。
- 收尾写失败日志：`registry.ts:339-348 settleTask` → `seat.onSettled` → `src/host/batch/fan-out.ts:643-648 noteRunOutcome`。

**复现**（真实定时器，`hubRetryMs:5`，transport.install 恒回 `{kind:'queued'}`）：
```json
{"firstOk":true,"attempts":10,"lastRun":{"stoppedBecause":"error","steps":10},"phase":"ready","busy":false}
```
生产缺省 `hubRetryMs = HUB_RETRY_INTERVAL_MS = 1000`（`src/host/hub/protocol.ts`），即「被别家安装占锁约 10 秒」就会误报。孤儿接管、自更新排队场景很容易命中；旧路径（hub:false + drain）只会停在 ready 继续重试，不会报失败。
**修复方向**：让 `queued`/`empty` 让位不累加 `idleSteps`（或在 `decideHubCycleVerdict` 里把 `yield` 分支置于 `idle >= maxIdle` 之前），看门狗只惩罚「有步骤但无进展」；同时失败码别丢原始 `stoppedBecause`。

### B3 中枢驱动期间并发「重试/入队」被整份回写覆盖

**症状**：中枢推进中用户点某失败行的「重试」（`batchInstall({keys:[row]})`，`driveActive=true` 走 `joinWhileBusy`）→ 回包 table 显示 `pending`，但中枢下一轮 `saveSession` 用自己内存里的旧 session 整份覆盖，`pending` 又变回 `failed`，意图静默丢失。这是 #25「忙时入队不丢意图」的回归。

**证据**：
- 中枢 driveTask 持有内存 `session`，落盘是整份直写、无磁盘合并：`src/host/hub/registry.ts:285`（`let session = sessionOf() ...`）、`:298-301`
  ```ts
  save: async (next: BatchSession) => { session = next; await task.seat.saveSession(next) }
  ```
  且 `runTask` 只在任务开始时 `readSession()` 一次（registry.ts:249），推进循环内不重读磁盘。
- 旧路径正是靠每轮合并解决此问题，注释也明说「驱动不会再把它覆盖掉」：`src/host/batch/fan-out.ts:671-672,678-680,694-700`。
- 忙时入队写的是 `liveSession`（`fan-out.ts:890-915`），中枢链路从不读/更新它。

**复现**（真实定时器：a 立即失败，b 挂起等外部 release；b 安装中点击重试 a）：
```json
{"before":"failed","inReply":"pending","after":"failed"}
```
**影响**：并发点击的重试/入队被静默回滚，面板先显示 pending 再跳回 failed；极端情况下中枢覆盖掉 `joinWhileBusy` 新增的 keys（#25 语义丢失）。
**修复方向**：中枢每轮落盘前与磁盘 session 合并（等价 `mergeInto`）；或 `HubSeat.saveSession` 改为「读-合并-写」（注意与 B2 的写次数/心跳配合）。

## 2. 建议项（按优先级）

1. **S1 中枢失败回包丢错误码**：hub outcome `failed` 时 `installPhone` 直接 `throw batchFail('install-failed')`（`fan-out.ts:1084`），旧路径 `errorPayloadOf` 的原始错误码丢失；面板只能看到泛化失败。（低风险，影响排障）
2. **S2 租约写失败静默降级**：`ensureLease`（`registry.ts:359-375`）写失败（`wrote=false`）跳过读回、仍 `slot.lease = lease` 继续单进程推进——只读/不可写目录下跨进程互斥静默失效（代码注释有意为之，但 README/CHANGELOG 未提示）。心跳写失败也被忽略（`registry.ts:390-398` 先更新 `slot.lease` 再写、不检查返回值），极端下别的进程会按陈旧租约接管。建议：至少打一行日志/在状态快照里暴露「租约不可写」。
3. **S3 租约 TOCTOU**：`registry.ts:362-372` 读→判→写→读回无锁，同机两进程同抢有极小双属主窗口（新加的 `stillOwnsLease` 每轮复核已显著收窄；安装另有 queue.json+global.lock 兜底，故降为建议）。可考虑租约目录 flock/独占创建（Windows 下 rename 独占写）彻底消除。

5. **S5 无任何测试覆盖「有 ctx 缺省开」**：所有单测显式传 `hub:true`；默认开逻辑在 `fan-out.ts:203`，README:402/466 承诺「接入方不用改代码」。建议补 `ctx:{}` 用例。

## 3. 已确认无问题（按维度，附证据）

**正确性 / 自更新断链救援**：方案落盘（`plan-store.ts:70-78` 原子写、失败不抛）→ 泵（`registry.ts`）→ 接管（`fan-out.ts:1217-1245 adoptOrphanSessions`，装载末尾 `:1344` 触发）链路完整；`hub-takeover` 覆盖「发起方消失后新实例按盘上方案接着推完、session.id 不变、已收尾不重装、只接自己属主」。FIFO：`hub-process` 覆盖 A 阻塞时 B 回 queued、A 收尾后 B 自动 done。失败隔离：单任务失败不影响后续任务（`runBatch` 的 `stopped-after-failure`/`continue` 语义 + hub settle 后泵继续）。

### B3：仍存（整份快照覆盖未根治，阻断级）
`mergeBatchSessions` 确实先读盘再写，但合并口径是「runBatch 返回的整份 patch 覆盖 base 所有同名行」（registry.ts:309-314,376-388），只有 patch 里**没有**的新行会被保住；`runBatch` 的 patch 含全量 entries，因此并发改写既有行（重试把 failed→pending）仍会被中枢内存里的旧值覆盖回去。
复现（§1 B3 脚本改「a 首次失败、第二次成功」以便区分重试是否被执行）：① 首批 a failed、b 挂起；② b 安装中调 `batchInstall({keys:['a']})`；③ 释放 b → `{"before":"failed","inReply":"pending","afterA":"failed","afterB":"done","aAttempts":1}`：重试回包显示 pending，实际中枢一次都没重试 a（attempts 仍 1），意图被静默覆盖。
另外，新增的 B3 回归用例（tests/hub-process.test.mjs:331-369）断言是空转：并发写者把 a 写成 `done`，而中枢内存里 a 本来就已是 `done`（a 先装完才轮到 b），旧代码整份写回同样得到 `done`，断言无法区分是否覆盖。建议改成写**不同的值**（例如 failed→pending 或 pending→done）才能作为有效回归。
**修复方向**：save 回调只合并「本步真正动过的行」——用 runBatch 的 `steps` 键（或 save 前保存 `before` 快照、逐行比较 phase 差异）构造 patch，而不是整份 session；否则 `joinWhileBusy`/另一进程对既有行的写入必然被覆盖。
