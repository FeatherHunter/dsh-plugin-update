## 0. 一页结论

**判定：不满足。** 按用户给定的标准（"用户侧出现安装失败、UI 问题、功能问题时，日志里有必要的、能用于定位的信息"），当前更新系统**不达标**。问题不是"日志太少"，而是失败现场的三类必需证据在日志里系统性缺失：

1. **原因缺失**：安装失败在持久日志里只剩"结果"（`ok:false` / `result:'failed'`），代码里已经算出的失败分型（超时 / 崩溃 / 非零退出 / 起进程失败 / 终止失败 / 版本未达标 / 未在册 / 环境阻拦 / 闸门拒绝）一个都不落盘；
2. **发生缺失**：单面板点击安装、渲染挂死、批量面板点击、更新说明空白这些用户动作，默认配置下在日志里**零行或近零行**；"日志里没有"无法区分"用户没点 / 点了被静默 / 日志没接上 / 日志被丢"；
3. **日志自身健康缺失**：日志没接上、写失败、客户端队列丢行、宿主拒收行，全部只在内存或临时回包里，**不落盘、不上屏、不进诊断副本**——于是"日志目录是空的"这一工单，维护者无法自证原因。

**5 条 S1（高频高严重且无替代证据）：**

| # | 缺口 | 用户工单式症状 | 关键证据 |
|---|---|---|---|
| S1-1 | 安装失败原因链断裂：exec 失败分型、verify 失败子类、闸门拒绝决策输入均不落盘；失败行是 `info` 级 | "更新失败 / 装完还是旧版 / 点了安装没反应" | `src/store.ts:1375-1394`、`:2330-2362`；`src/service.ts:715-739`、`:855-929`；`src/host.ts:950-953` |
| S1-2 | 单面板 UI 故障近零证据：通道在校验之后才建、动作行无结果、渲染失败无类别/去重、客户端丢行无出口、`dispose` 丢缓冲行 | "面板一打开就空白 / 白块 / 一直正在读取 / 点按钮没反应 / 日志里啥也没有" | `src/panel.ts:2351-2406`、`:3017-3025`、`:3312-3340`；`src/log/client-queue.ts:176-196`、`:393-412` |
| S1-3 | 批量更新（面板 + 驱动）零/近零现场证据 | "批量面板空白 / 全部更新一直转圈 / 某行失败不知道为什么" | `src/entry-batch.ts:531-552`；`src/panel-batch.ts` 全文零日志；`src/host-batch.ts:857-893` |
| S1-4 | 日志管道自故障与"无日志"不可判定 | "日志目录是空的 / 没有这个目录 / 只有一两行 / 日志写到一半停了" | `src/host.ts:806-845`（off 行解绑后必丢）、`src/log/emit.ts:134-152`（no-sink 降级自吞）、`src/host.ts:1294-1352`、`src/log/client-queue.ts` |
| S1-5 | 更新说明链路（取不到/作者没写/缓存/解析）无 resident 证据 | "有新版但更新说明空白 / 截断 / 乱" | `src/changelog.ts`（取数失败全回 `null`）；`update.changelog.parse` 仅 ondemand；`src/service.ts` check 成功不落说明结论 |

**三条结构性根因**（不是逐点补丁能解决的）：

- **R1 唯一证据通道 + 失败原因消费链断裂**：ADR-0005 已证明宿主没有日志位（插件 stdout 丢弃、`ctx.logger` 只在内存环形、stderr 64KiB 混合且仅非零退出时附带），dsh-log 行是唯一事后证据；但失败原因在代码里只流向 `job.message`（内存，见 #179）、电话回包（临时）和面板文案（用户不一定复制）。
- **R2 客户端→宿主桥只传"动作发生"，不传"动作结果/日志健康"**：桥的白名单只有 5 个客户端事件，且桥自身丢弃的行没有任何持久出口；`logAppend` 协议拒绝的行也只回一个数字给内存。
- **R3 最有价值的诊断对象 `diag`（19 键：stage/route/httpStatus/exitCode/detail/causeKind/requestId/…）只存在于电话失败回包和复制文本里，从不落盘**——即"现场最该留下的东西，被设计成了最留不下的东西"。

**建议动作（详见 §9）：** P0 共 9 项——新增 1 个 resident warn 事件 `update.install.fail` 覆盖"闸门/执行/校验"三阶段失败原因；把 `update.changelog.parse` 升常驻并补 `status` 字段；修客户端通道建立顺序与动作结果字段；把客户端丢弃计数与宿主拒收变成 `update.log.degraded` 行；诊断副本补"日志健康"段。事件数 26→27（`changelog.parse` 不增数），字段扩展 16 个事件（约 35 个字段），噪声增量 < 20 行/操作日，测试新增约 14 项。P0 落地后，用户报"安装失败/UI 白/功能不更新"时，仅凭一个日志目录即可在 10 分钟内定位到**环节 + 原因 + 是否日志自身故障**。

**现状中做对了、不要在下一轮改坏的部分**：`host.call` / `host.call.fail` 常驻且 warn 恒落；轮询成功行抑制（5309 行/天 → 0）；`check.done` 带 latest/channel/source/latency；`install.exec` 带 route/ok/exitCode/durationMs；`store.fail` / `queue.transition` / `lock.anomaly` 的去重与边沿；引擎 14 天保留 + error/warn 不丢 + resident 名单机制；ADR-0006 的"行只存稳定码"纪律；README §10 的诚实边界（跨进程不承诺/开关只管制 ondemand/回包不带路径）。完整清单见 §7。

## 1. 审查口径：从第一性原理定义"必要日志"

### 1.1 为什么"日志"是唯一的第一性证据

更新系统的事后定位只有三条信息路：**用户口述**、**诊断副本**、**dsh-log 行**。其中前两条都依赖用户配合且内容可被截断/省略，只有 dsh-log 行是落了盘的。ADR-0005（`docs/adr/0005-dsh-log-as-first-runtime-dependency.md`）给的事实是决定性的：

- 宿主不为插件提供日志管道：`ctx.logger` 默认不输出（仅 1000 条内存环形）；插件 stdout 在 GUI 下被丢弃；stderr 是 64KiB 环形、多插件混合、无前缀、仅在非零退出时附到错误消息；
- 不存在 `DSH_LOG*` / `LOG_LEVEL` 一类环境开关。

因此本文的审查对象不是"打点密度"，而是：**当用户报障后，维护者仅凭一个日志目录（加上用户提供的版本/时间窗）能否回答下面四问**：

| 问 | 要回答什么 | 对应公理 |
|---|---|---|
| Q0 关联 | 这些行是不是同一个用户动作/同一次安装？ | X5 |
| Q1 发生 | 这一刻到底有没有发生（点了没有、查了没有、装了没有）？ | X1/X2 |
| Q2 环节 | 卡在哪一段（取数/决策/锁/执行/校验/渲染/投递）？ | X3 |
| Q3 原因 | 为什么（失败分型、拒绝码、决策输入、未知值）？ | X3/X4/X6 |
| Q4 下一步与影响面 | 能否给出下一步动作/是否需要更多信息/是不是日志自身坏了？ | X7/X10 |

### 1.2 十条公理（判定"必要"的尺子）

| 编号 | 公理 | 反例（本仓库里真实存在的形态） |
|---|---|---|
| X1 | **故障路径覆盖**：用户可感知的每种失败，必须至少有一条能落盘的证据行 | 面板挂载前四种校验失败时日志通道还没建（`src/panel.ts:2351-2406`） |
| X2 | **常驻优先**：默认开关关闭时 ondemand 行等于不存在；现场必要的结论必须走 resident | 通道决策/取数/更新说明解析默认不落盘 |
| X3 | **定位力**：行必须能区分"哪一段 + 哪一类原因"，不能只有一个 `failed` | `update.install.verify{result:'failed'}` 无任何原因字段（`src/service.ts:735-739`） |
| X4 | **决策上下文**：拒绝/灰按钮必须能还原输入（哪个版本、哪个通道、哪个阻挡原因） | 闸门拒绝只有 `host.call.fail{error,errorHash}`（`src/host.ts:950-953`） |
| X5 | **关联**：一次用户动作跨电话/跨异步/跨进程可追 | `install.request`/`exec`/`verify` 无 requestId；外部落点无 trace |
| X6 | **未知即记录**：探测失败/版本未知要显式记为 unknown，不能用"省略字段"表达 | 运行版未知时 `check.done.current` 被省略；`status.changed{kind:'unknown'}` 三因合流 |
| X7 | **记录器故障可观测**：日志没接上/写失败/丢行，本身必须留下证据或上屏 | `wire.ready{logSink:'off'}` 在解绑后发出必丢（`src/host.ts:841-843`） |
| X8 | **到达时机**：行要能活到用户报障之后（保留期、防抖、进程生命周期） | 短命 CLI 进程的 info 行可能因 1s 防抖丢失；进程被杀丢缓冲 |
| X9 | **生命周期/多进程**：多副本、多宿主、重启后仍可判读 | 同机四代更新器副本（#196）行内无更新器版本/副本层级 |
| X10 | **可交付性**：用户能拿到日志位置/健康并能安全发出来 | 面板只在调用方传 `logDir` 时给实路径；复制诊断不含日志目录/健康 |
| X11 | **ADR-0006 信息天花板**：不允许自由文本落盘，必须在发射点收敛为稳定码/枚举/派生量 | 宿主原话、路径、URL、错误 message 只能进 `diagnostic`/`detail`，不得进行 |
| X12 | **噪声预算**：稳态 ≤ 50 行/天/插件，操作日 ≤ 500 行 | 现网曾出现 934 KB/天（5309 行轮询），已由轮询抑制修掉 |

### 1.3 判定词与严重度

- 判定词：`COVERED` / `PARTIAL` / `ONDEMAND_ONLY`（默认关时等于没有）/ `MISSING` / `BLIND`（连"有没有发生"都不可判）/ `MISLEADING`（行存在但会把人引向错误结论）/ `NOT_NEEDED`。
- 严重度：`S1` 高频或高严重用户故障在该场景完全无法定位且无替代证据；`S2` 能定位到环节但原因不足、需追问/复现；`S3` 诊断力增强或长尾。

### 1.4 方法与局限

- 静态直读 `src/` 全部日志相关文件 + `event-list.update.json` + README §10/§11 + ADR-0005/0006 + 测试；对关键机制用 `.tmp` 下的独立探针复跑（client-queue 丢弃、logAppend 回执、HTTP 网关、面板挂载 0 次电话等）。
- **不做真机验收**：本轮无宿主 GUI 现场，真机回放清单见 §10.2。
- dsh-log 行为以 `node_modules/dsh-log@0.3.4` 的 `dist` 为准；宿主自带另一份 dsh-log 副本、以及"现场实际运行的是哪一份更新器副本"属于 **U**（无法判定），已在 §8.4/§10.1 标注。
- 事件契约以 HEAD 的 `event-list.update.json` 为唯一真值；文档漂移单独在 §8.3 列出，不混入缺口计数。

### 1.5 与既有审查文档的关系

- `docs/research/20261014-log-event-catalog.md`（事件目录）：本文**不复述**其 26 事件字段表，只在修正处引用（§8.3 共 5 处）；
- `docs/research/20261014-log-integration-review.md`：作为历史快照（HEAD `798e2ec`、28 事件时代），本文不重复其 D1–D13；
- `docs/research/20261017-更新系统对抗审查.md`：其列出的 S0/S1 缺陷（#179 任务状态只在内存、#180 装后核实判据、#181 锁双向失灵、#196 部署偏斜等）是本文的背景放大器——**既有缺陷让日志成为唯一持久证据，因此日志缺口的实际严重度高于"缺几条日志"**。本文只按 HEAD 代码事实断言，不复核那些票的修复状态。

## 2. 事实底座：更新系统当前能提供什么日志

### 2.1 管道拓扑（HEAD）

```
                 ┌──────────── 宿主进程（同一插件一次接线） ────────────┐
 面板/安装按钮/   │  createHostUpdate()                                 │
 批量面板/HTTP ──┼─→ wireUpdateLog() ── external logCtx? ──→ 集成方 sink │
 （client-queue） │        │                  │ self                  │
   ring 200       │        │                  └→ acquireOwnLog(异步)   │
   batch 50/1s    │        │                       └→ dsh-log NodeHostLog
   retry 2        │        └→ router（pluginId → sink）                │
        │         │              ↑ 唯一发射口 src/log/emit.ts           │
        └─ logAppend 电话 ──────┘  （白名单 5 事件、校验、丢弃只回数字） │
                 └─────────────────────────────────────────────────────┘
 落盘：<homeDir>/logs/<派生命名空间>/   （homeDir = 显式 > DSH_HOME > ~/.dsh）
 开关：<homeDir>/logs/log-switch-<派生命名空间>.json（默认 enabled:false，启动时缓存，需重启宿主）
 保留：14 天；单文件 5MB 滚动；error/warn 不丢；resident info 不丢；ondemand info 受开关
```

> 读法：19 条恒落（18 resident + 1 selfmon），7 条 ondemand 仅开关打开时落盘。**"默认现场"= 19 条常驻事件**，这是评估必要日志的现实基数。

### 2.3 引擎行为（dsh-log 0.3.4 dist）

- 准入：error/warn 恒收；resident 事件 info 恒收；其余 info 看开关；队列满时普通行丢并计数，error/warn 绝不丢（病态上限才挤最旧）。
- 持久：1s 防抖批量写（`LOG_DEBOUNCE_MS=1000`）；单文件 5MB 滚动；保留 14 天（含当日）；`audit.json`/开关文件不删。
- 自监控：引擎自己有 `log.persist.fail` / `log.rotate.*` / `log.retain.evict` 等行（不在本包 26 事件契约内，见 §10.1-U）。
- 短命进程：info 行有 1s 防抖，`beforeExit` 不阻塞 → 若存在"加载后很快退出"的一次性 CLI 进程，可能丢 info 行；error/warn 直通。

### 2.4 客户端通道（面板侧唯一出口，#122）

- 白名单只允许 5 个客户端事件：`update.panel.mount` / `action` / `render.fail` / `state` / `lang.applied`；
- 环 200、批 50、flush 1s、重试 2（共 3 次，退避 250/1000ms）、单次 5s 超时；页面 hidden 时 flush；
- 丢弃原因：`no-channel` / `overflow` / `host-refused` / `send-failed` / `disposed`；**全部只累加内存计数**（`pending()/dropped()/sent()/enabled()`），可选 `onDrop` 在本包内**没有任何调用点接线**；`dispose()` 清空待发行且**不做最后一次 flush**；
- 宿主的 `logAppend` 协议（`src/host.ts:1294-1352`）：最多 200 行/次、单字段 4096 字符、ts 不早于 10 分钟、白名单事件、按清单校验字段；拒绝只回 `dropped` 数字，**不落任何行，也不产 `host.call`**（注释明确）。

### 2.5 批量面

- 每个目标插件各自 `createHostUpdate()`，**各自 wire 自己的日志目录**；批量级三事件落 `selfKey` 那家的目录；`selfKey` 缺失 → 批量级事件一行不发；单项失败 `update.batch.entry.fail` 落**目标插件自己的目录**；
- 三事件无 `sessionHash`/批序号/阶段；`entry.request` 每会话一次（按 targets 指纹去重），`summary` 只在 finished 边沿发；
- 批量面板（`src/panel-batch.ts`）全文件**零日志发射**，入口（`src/entry-batch.ts:531-552`）挂载时不传 `clientLog` → 批量面板 UI 故障在客户端侧零行。

### 2.6 诊断对象 `diag`

- `src/diag.ts`：`DIAG_VERSION=1`，6 个 stage（read-installed/fetch-release/validate-release/preflight/exec/verify）、4 个 action（retry/manual/contact/restart）、19 个键（v/stage/route/method/httpStatus/exitCode/latencyMs/detail/targetPackageName/runningVersion/latestVersion/environmentKind/requestId/checkId/registryHost/action/causeKind/causePackage/causeUnlockAt）；
- 只在三处产生：`host.ts` 电话失败回包（`:962`）、`readStatus` 对 failed job 的补挂（`:696`，把 `job.message` 拆成 code+detail）、changelog 电话失败回包（`:1065`）；
- **从不 emit 到 dsh-log**；且不含 logDir/logDirHash/日志健康/registered/identity/installedVersion。

### 2.7 链路 trace 真值（本次裁决，修正旧文档）

- 一次电话 = 一条链：`withLogTrace(sinkForPhone(), runPhone)`（`src/host.ts:895-907`、`:1019-1021`），链挂在**该插件路由表落点**上，对象同一性防串台；
- **自建落点**上，电话内的行（包括电话返回后才完成的安装异步链）共享 `traceId`、`spanId`、`seq`：`void runBackground(...)`（`src/service.ts:833`、`:927`）在 `withLogTrace` 的异步上下文里派生，ALS 语义跨 `await`/detached promise 保留；`tests/log-trace.test.mjs:245-272` 用"并发两条链 await 后仍各带各的 traceId"锁住了这一点；
- **外部 logCtx 落点没有 trace**（`sinkFromLogCtx` 只接 fire/isEnabled，`src/log/sink.ts:59-67`）；
- **客户端行没有 trace**：`logAppend` 不经 `loggedPhone`、也不在 `withLogTrace` 内（`src/host.ts:1298-1300`）；
- dsh-log < 0.3.3、旧副本（#196）、以及重启后补记的 `interrupted` 行（新电话链）没有原链。
- 结论：*"安装链完全无法关联"是错的；"外部落点/客户端行/旧副本/重启场景无法关联"是对的*。见 §8.3 修正项 ③。

### 2.8 用户交付面

- README §10：日志落点、开关、保留、CLI（`npx dsh-log <dir>`、`--since`、`--level`、`--trace`、`--json`）、工单四件套（版本、pluginId+目录、时间窗、复制诊断）；
- 面板"日志路牌"仅在集成方传 `logDir` 时给实路径，否则给算式模板；电话回包不带路径；
- 复制诊断文本（`src/panel-copy.ts:414-533`）**不含**日志目录/hash/丢弃计数/接线状态。

## 4. S1 逐条：用户现场与最小修法

> 每条按同一模板：**用户工单式症状 → 维护者四问现状 → 现证据 → 为何不够 → 替代证据 → 最小提案 → 噪声与验收 → 置信度**。提案字段一律遵守 ADR-0006（扁平、只允许版本号/枚举/派生量；不写自由文本、路径、URL、宿主原话）。

### 4.1 S1-1 安装失败原因链断裂

**症状（工单式）**

- "更新失败，重试几次都一样"；复制诊断里只有 `install-failed: <宿主原话>`，日志里 `install.exec ok:false, exitCode:null`，然后 `install.verify result:'failed'`——**看不出是超时、崩溃、宿主拒绝、构建待批、版本没变还是未在册**。
- "点了安装没反应"：面板短暂 toast 后恢复按钮，日志里连一行失败都没有（闸门拒绝走 `host.call.fail`，`errorHash` 不可逆）。
- "装完提示完成，重启后还是旧版"：`install.verify result:'completed'` 与实际加载不符时，没有任何字段记录"磁盘版本 vs 在册 vs 运行版"三者差异。

**四问现状**：Q0 关联差（无 intentHash，外部落点无 trace）；Q1 发生可判（exec/verify 有行但 info 级）；Q2 环节只能猜到 `exec`；Q3 原因**不可回答**；Q4 下一步不可给出。

**现证据与机制**

| 事实 | 位置 |
|---|---|
| 执行器失败分型算完即弃：`TIMEOUT`/`late`/`terminated`/`terminateFailed`/`crashed`/非零退出/超时提示/输出摘录只进 `error.detail` | `src/store.ts:2287-2307`（CLI）、`:1457-1475`（桌面服务） |
| 统一包成 `fail('install-failed')`，`emitInstall` 只落 `route/ok/exitCode/durationMs/pluginId` | `src/store.ts:2330-2362`、`:1375-1394`、`:2351/:2353`、`:41` |
| 装后校验失败只落 `result:'failed'`，无子类/无 detail；detail 文案（磁盘版本不符/未在册/环境阻拦）只写 `job.message` | `src/service.ts:690-707`、`:720-739`（emit 在 `:735-739`） |
| 成功校验行也是 info，且 `pendingRestart` 之外无"在册/运行版"字段 | `src/service.ts:715-719` |
| 闸门拒绝全部 throw 稳定码：`check-expired`/`installation-changed`/`update-busy`/`blockedReason`；#202 noop 与 installationKey 变化同码 | `src/service.ts:855-929`、`:847-853` |
| 闸门拒绝只在电话层留 `host.call.fail{error, errorHash}`，`errorHash=hash8(message)` 不可逆 | `src/host.ts:950-953` |
| 最有价值的 `diag`（stage/route/exitCode/detail/causeKind/requestId）只在失败回包里 | `src/host.ts:962-977`、`:680-710` |
| 失败任务状态只在内存（#179），日志是唯一持久证据 | `src/service.ts:720-739`、`docs/research/20261017-更新系统对抗审查.md` |

**为何不够**：`exitCode:null` 至少对应六种互斥原因（超时被杀/崩溃/终止失败/起进程失败/宿主拒绝/构建待批），`exitCode: nonzero` 也分"包管理器报错"与"宿主拒绝码"；`result:'failed'` 不携带任何原因。维护者只能让用户重试并再要一份诊断副本——而诊断副本本身也可能被用户省略或截断。又因为两行都是 `info`，README 推荐的 `--level warn` 首次检索会**整段漏掉**安装失败。

**替代证据**：`job.message`（面板可见、`readStatus` 回包 `diag` 可带）能提供一部分原因，但它依赖用户复制、且 #179 下重启即失；`copy-diag` 的 detail≤300 字、路径被 `<路径>` 替换，无法承载分型。

**最小提案（P0）**：新增 1 个常驻 `warn` 事件 **`update.install.fail`**，在闸门拒绝、执行器失败、装后校验失败三处各发一次（每次失败一条，边沿=失败事件本身）：

| 字段 | 类型/枚举 | 说明 |
|---|---|---|
| `stage` | `gate` \| `exec` \| `verify` | 失败发生在哪一段 |
| `reason` | `host-rejected` \| `timeout` \| `crashed` \| `nonzero-exit` \| `spawn-failed` \| `terminate-failed` \| `version-mismatch` \| `not-registered` \| `env-blocked` \| `noop` \| `gate-refused` \| `unknown` | 失败分型；`unknown` 显式存在（X6） |
| `hostCode` | 稳定码字符串或 `none` | 宿主/电话层稳定码（`install-failed`/`installation-changed`/`update-busy`/…），禁止原话 |
| `check` | `version` \| `registered` \| `env` \| `none` | verify 阶段具体没过哪一项 |
| `exitCode` | number \| null | 保留现有信息 |
| `observedVersion` | semver \| null | 装后磁盘观测版本 |
| `pendingRestart` | boolean | 是否需要重启才生效 |
| `intentHash` | hash8 \| null | `requestId`/`job.id` 的 hash8，跨外部落点也能聚合 |

- `exec` 行保持冻结形状不动（`tests/phones.test.mjs:222/232`、`tests/routes.test.mjs:106` 锁死）；`verify` 行保持现状只做结果记录。**失败原因只在新事件里出现一次**，避免双写。
- 噪声：稳态 0 行；失败操作日每条失败 1 行（典型 < 10 行/天）。
- 验收测试：timeout/crash/nonzero/spawn-failed/terminate-failed/version-mismatch/not-registered/env-blocked/noop/gate-refused 十类路径各断言 1 行且字段完整；`--level warn` 能检索到；负断言（无路径/URL/原话/`=` 形状）沿用 `tests/host-log.test.mjs` 的 gate 模式。
- 同时修 `readStatus` 回包 `diag`：新增 `intentHash`，使"用户没复制诊断"时还能靠日志聚合。
- 成本：清单 1 event + 3 发射点 + `bilingual.ts` 1 组 key + 类型两处 + 测试；不新增依赖。

**置信度**：高。E 复核 A-02/A-03 均 CONFIRMED，A-04 §4.3 的附带断言（"install.request 在全部闸门后发"）被修正为"在 acquire/锁后复核之前发"（`src/service.ts:892` vs `:905`、`:909-916`），但不影响本缺口方向。

### 4.2 S1-2 单面板 UI 故障近零证据 + 客户端日志桥自故障

**症状（工单式）**

- "面板一打开就空白"：挂载校验抛错发生在日志通道创建之前，默认路径 0 次 `logAppend`、0 行；
- "面板白块/点哪都没反应"：`paint()` 异常只有 `render.fail{kind:'unknown'}`，无错误类别/hash/phase，且无去重（持续抛错每秒一行）；
- "一直停在正在读取/点安装没反应"：`refresh()` 传输失败只 `setLatch`，无行；`act()` 动作行没有结果；
- "日志目录里啥也没有"：客户端队列丢行（no-channel/overflow/host-refused/send-failed/disposed）只有内存计数；面板卸载时 `dispose()` 直接丢掉待发行。

**四问现状**：Q1 发生基本不可判（挂载前失败/批量/HTTP 全无行）；Q2 环节不可判（render.fail 单 kind）；Q3 原因不可判（无 errorHash/类别）；Q4 不可给（不知道是产品 bug 还是日志坏了）。

**现证据与机制**

| 事实 | 位置 |
|---|---|
| 通道在校验之后创建：先读 `clientLog` 选项、再依次校验 container/options/pluginId/call，最后才 `createClientLogChannel` | `src/panel.ts:2351-2406` |
| 前四类挂载失败调用 `logMountFailure` 时通道尚不存在 → 行被静默丢弃；只有调用方显式注入 channel 时才可能留下 | `src/panel.ts:2374-2392`、E-03（prefix 唯一无保护校验点） |
| `themeTokens` 非法（`:2436`）与 locale 非法（`:2443-2447`）直接 throw，连 `render.fail` 都不记 | `src/panel.ts:2436-2447` |
| `render()` 兜底只有 `render.fail{kind:'unknown'}`，无错误类别/stack/hash，无去重 | `src/panel.ts:3017-3025` |
| `act()` 在 finally 里只记 `action`（copy-diag 附带 bytes/truncated），不含成败/错误码/耗时 | `src/panel.ts:3327-3340` |
| `refresh()` 传输失败只 `setLatch(volatileLatch('check'))`，无行 | `src/panel.ts:3312-3325` |
| busy 时轮询静默 `return`，无任何行 | `src/panel.ts:3877-3880` |
| 全仓无 `window.onerror` / `unhandledrejection` 兜底（grep 0） | — |
| 客户端丢行只累加内存计数；`onDrop` 可选但 panel/install-button/entry/http 均未接线；`dispose()` 不 flush 直接丢 | `src/log/client-queue.ts:176-196`、`:393-412`；`src/panel.ts:2365-2373`（logClient 吞异常） |
| 宿主 `logAppend` 拒收只回 `{accepted,dropped}`，不落行、不产 `host.call` | `src/host.ts:1294-1352` |
| HTTP 直挂：超时/非 2xx/JSON 非法/断网只抛给内存态，客户端无日志；宿主根本没收到请求 | `src/http.ts:230-305`、`:345-354` |
| 安装按钮同构：挂载校验（含额外 prefix/auto-check/theme-tokens/locale kind）在通道前/后混杂，action 无结果 | `src/install-button.ts:620-673`、`:1239-1253`、`:996-1003` |

**为何不够**：这些是最高频的 UI 工单（面板空白/白块/没反应），却恰好落在"通道还没建"的窗口里；即使通道建好，`action` 行只能证明"点了"，不能证明"点出了什么结果"；`render.fail` 无法区分"挂载校验失败"与"paint 抛错"，也没有 hash 可用于跨工单聚类。更糟的是桥自身的丢弃不可见——维护者看到"没有行"无法判断是"没发生"还是"没送到"。

**替代证据**：宿主侧 `host.call.fail` 只在电话到达宿主后存在（挂载前失败没有电话）；`copy-diag` 不含日志健康；面板 UI 的 toast/latch 是内存态、用户关闭即失。

**最小提案（P0）**

1. **重排挂载校验顺序**：`call` 最小依赖先校验 → 建通道 → 其余校验（container/pluginId/prefix/pollMs/mode/theme/themeTokens/locale）全部经 `logMountFailure` 落 `render.fail{phase:'mount', kind:<枚举>, errorHash:hash8(err.message)}`；`install-button.ts` 同样处理。
2. **动作行补结果**（扩展 `update.panel.action` 字段，不新增事件）：`ok:boolean`、`errorKind:稳定码|null`、`durationMs:number`；`runAction` 的 catch/latch 结果同步发射。批量面板动作（P1，见 §4.3）复用同形状。
3. **渲染失败补语义并去重**：`render.fail` 增 `phase: mount|paint|poll|global`、`errorHash`；同 `kind+errorHash` 60 秒窗口最多 1 行（边沿指纹），防 paint 风暴；新增 `window.onerror` / `unhandledrejection` 兜底（phase=global，只 hash）。
4. **客户端丢弃上浮**：把 `onDrop` 接到聚合器；每个 flush 周期内 `dropped>0` 时发一条 `update.log.degraded{reason:'client-drop-<no-channel|overflow|host-refused|send-failed>'}`（客户端白名单扩到 6 个事件；宿主扩 reason 枚举并接受；warn selfmon 恒落）。`dispose()` 前先尝试一次 final flush（能救多少救多少），并至少把 `disposed` 丢弃上浮。
5. **宿主拒收上浮**：`logAppendRows` 判 dropped 时发一条 resident warn `update.log.degraded{reason:'client-batch-refused'}`（按 reason 指纹去重，防刷）。
6. **HTTP 模式的传输失败**：P1（宿主没收到，客户端无处落盘）；最小做法是把连续 transport 失败计数与最近错误类别进 `copy-diag` 的"连接"段，并在 UI 上从"读取中"切到可复制错误态；不承诺落盘。

- 噪声：失败时才发；render.fail 去重后风暴 ≤1 行/分钟；drop 上浮每个 flush 周期最多 1 行。
- 验收：`tests/panel-log.test.mjs` 扩：五种挂载校验失败各 1 行；action 成败四值；render.fail phase/errorHash/去重；client-log 测试用假 call 断言 drop 上浮；HTTP 传输失败不产行但 copy-diag 含计数。
- 成本：无新事件（action/render.fail 扩字段、degraded 扩 reason、客户端白名单 +1）、`window.onerror` 一行接线、测试 ~6 项。

**置信度**：高。B-ui-01/03/04/05 全部 CONFIRMED；E-01/E-02/E-03 为新增 S2 并经探针复现；E 对 B-ui-01 的措辞修正（"logMountFailure 并非空路径，注入 channel 时会落行"）已吸收——**默认集成**路径结论不变。

### 4.3 S1-3 批量更新零/近零现场证据

**症状（工单式）**

- "批量面板打不开/一片空白"：面板 HTML 渲染前后的异常全裸 throw，无任何行；
- "点了全部更新，一直转圈没进展"：驱动侧只在进入时发一条 `entry.request`、收尾边沿发 `summary`，卡住时不发 summary——日志里**没有"进行到第几步/卡在哪个目标/为什么停"**；
- "列表里某一行失败，但不知道哪家、为什么"：`entry.fail` 落在**目标插件自己的目录**（用户通常只看一个目录），且只有 `targetHash`（不可反查）、`errorKind`、可选 `exitCode`，无阶段/序号。

**现证据与机制**

| 事实 | 位置 |
|---|---|
| 批量入口挂载面板时不传 `clientLog` → 批量面板无客户端日志通道 | `src/entry-batch.ts:531-552` |
| `panel-batch.ts` 全文零日志发射（grep 无 `emitUpdateLog`/`clientLog`/`logAppend`） | `src/panel-batch.ts` 全文 |
| 批量级事件只有 `selfKey` 存在时才发；`selfKey` 缺省 → 一行不发 | `src/host-batch.ts:751-756`、`:229-232` |
| `entry.request` 每会话一次、无批次标识；`summary` 只在 finished 边沿、无 `stoppedBecause` | `src/host-batch.ts:857-868`、`:876-893` |
| 单项失败只记 targetHash/errorKind/exitCode，落目标目录；无阶段/序号/详情 | `src/batch-run.ts:105-116` |
| 驱动 stop 分支（用户取消/超时/队首阻塞）无行；settle 超时被归类为普通失败；precheck 失败静默；drain 异常被吞 | C-F02（`C-functional.md` §3）；A-06/A-07 |
| 批量队列端口未传 `logFor`，队列行丢归属（一行修复） | C-F02③ |

**为何不够**：批量是"多目标 × 多阶段 × 长时间"的操作，最需要的恰恰是**相位与归属**；现在只有"进入/单项失败/收尾"三个孤立事实，缺少批次号无法把散落在 N 个目录的行拼起来，缺少 phase 无法回答"卡在 check 还是 install"。

**最小提案**

- **P0（面板侧，属 S1）**：批量面板复用单面板的 `clientLog`（`mount:'batch'`），挂载/动作/失败三行与单面板同形状；客户端白名单扩批量 action 值（`batch-install-all`/`batch-retry`/`batch-skip`/`close-batch`）。
- **P1（契约扩展）**：三事件统一加 `sessionHash`（`hash8(批次 id)`，可反查需维护者知道 id 派生规则）；`entry.fail` 加 `stage ∈ check|install|timeout|settle` 与 `index`（批内序号，number）；`summary` 加 `stoppedBecause ∈ user-cancel|timeout|gate|error|done`；驱动 stop 分支复用 `entry.fail` 发射（不新增事件）。
- **一行修复**：批量队列端口补传 `logFor`（C-F02③），让 `queue.transition/store.fail` 落到正确目录。
- 噪声：批量操作日每条失败 1 行 + 每个 stop 1 行；steady 0。
- 验收：`tests/batch-log.test.mjs` 扩 sessionHash/stage/index/stoppedBecause；批量面板 mock call 断言 mount/action；`selfKey` 缺省时的行为（无行但回包带 warning?）写入 README。

**置信度**：高。B-ui-02、F-02、F-11 均 CONFIRMED（E 独立复跑）。

### 4.4 S1-4 日志管道自故障与"无日志"不可判定

**症状（工单式）**

- "日志目录是空的 / 没有这个目录 / 只有一两行 / 写到一半停了"：目前**没有任何行能解释**，维护者无法区分"插件没加载/没接线/外部落点没 merge/开关把行挡了/写失败/队列丢空"；
- "我明明复现了，日志里却没有"：客户端桥丢行只累加内存计数，`dispose()` 还把待发行直接丢掉。

**现证据与机制**

| 事实 | 位置 / 机制 |
|---|---|
| 自建落点失败时，`wire.ready{logSink:'off'}` 在 `router.unbind` **之后**发出 → 必被 `no-sink` 丢弃 | `src/host.ts:841-843` |
| self 接线期间 `onDegrade` 发的 `update.log.degraded` 落在尚未 attach 的 pending sink（无最终落点） | `src/host.ts:826-843` |
| 发射口 `degrade()` 遇到 `resolveSink` 为 null 时直接 return——"没有落点"这个坏消息结构上写不出去 | `src/log/emit.ts:134-152` |
| 发射口计数（dropped/skipped/degraded）只在内存，`logEmitterCounts()` 全仓无消费者；注释声称的 #125 面板展示未接线 | `src/log/emit.ts:115/240`、`src/log/index.ts:21` |
| pending sink（自建异步窗口）上限 200，超限丢弃只计数，无消费者 | `src/log/sink.ts:104-151` |
| 引擎自身持久化失败（`log.persist.fail`/`log.rotate.*`/`log.retain.evict`）不在本包 26 事件契约内，维护者不会预期去读 | dsh-log 0.3.4 dist；D-INFRA-04 |
| 外部落点"假接线"：`sinkFromLogCtx` 不探 `isEnabled`、不核对清单是否 merge，就按 external 上报 | `src/log/sink.ts:59-67`、D-INFRA-03 |
| 多进程/多副本共享同目录：行内无写者身份，租约冲突只由引擎事后记 `foreign-write` | D-INFRA-08、ADR-0005 |

**为何不够**：这是"证据的证据"缺口（X7）。当用户说"没有日志"时，维护者必须能区分**四种完全不同的结论**：①插件没加载（连 C1 都不存在）②加载了但日志没接上（wire=off）③接上了但该事件被开关挡住（ondemand）④接上了但行被丢（队列/客户端/协议）。当前四种在持久层面**同形**——都是"没有"。

**替代证据**：README §10 与工单四件套要求用户提供目录内容，但无法自证"目录该有什么"；`copy-diag` 不含日志健康；面板日志路牌只在集成方传 `logDir` 时出现。

**最小提案**

1. **把接线状态变成可交付数据（P0）**：`updateStatus` 电话回包增加只含派生量的 `logHealth`（`sink: external|self|off`、`dirHash: hash8|none`、`droppedSinceStart: number`、`lastEventAt: epochMs|null`、`switchEnabled: boolean`）——不带路径；面板"日志"区域与 `copy-diag` 的"日志"段渲染它。**"空目录"从此可自证**：`off` / `external` / `self` 三种状态直接区分。
2. **把可修的丢失路径变成行（P0）**：客户端 drop 上浮（S1-2 第 4 条）、宿主 `logAppend` 拒收上浮（第 5 条）、pending sink 超限时经一次 `update.log.degraded{reason:'pending-overflow'}` 尝试（自建成功后才能落，属于"部分可修"）。
3. **顺序修正（P0，务实版）**：`wire.ready{logSink:'off'}` 无法在自己没有落点时落盘，这是 ADR-0005 的结构极限，**不假设能修**；改为在 unbind 前把该状态写入 `createHostUpdate` 的不可变状态供 `logHealth` 回包读取（代码里保留状态对象即可），并写进 README 的"空目录决策树"。
4. **README/工单流程（P0 文档）**：给出"日志为空"的四步判定树（查 `logHealth` → 查开关文件是否存在 → 查 external 是否 merge 清单 → 查 dsh-log 版本/副本），并明确"没有日志目录"本身就是需要上报的故障。
5. **P1**：dsh-log 侧提供 `getDroppedCount`/`lastPersistFail` 的只读句柄（本包自建实例已有句柄时可直接读），把 `update.log.degraded{reason:'persist-fail'}` 接上；多进程写者身份进 `wire.ready`（`hostKind`）。

- 噪声：health 走回包不落行；degraded 只在真有丢失时发且按 reason 去重。
- 验收：假 host 场景四种（无 dsh-log/外部未 merge/写入失败/客户端拒收）各断言：回包 `logHealth` 正确、可上浮的 reason 有行、不可上浮的有 UI 证据；README 决策树与实现一致。
- 置信度：高（机制直读 + D 报告 + 探针）。**保留一句诚实结论**：完全无落点时"写一行证明自己没落点"是不可能的；本提案用"回包/上屏的带外证据"替代，不承诺日志侧自证。

### 5.2 S2-2 重启后真相与部署偏斜

- 噪声：随边沿，0 增量。

### 5.3 S2-3 检查失败原因不可分

- **症状**："检查更新失败"（断网/DNS/代理/TLS/超时/404/限流/JSON 坏/名字不符/超 256KB 墙/integrity 失败，全都长一样）。

### 5.4 S2-4 数据源与通道决策不可见

- **症状**："为什么给我这个版本/这个通道"、"stable 为什么回退到 npm"（#183）、"更新说明是从哪取的"。

### 5.5 S2-5 队列/锁/意向

### 5.11 S2-11 外部落点"假接线"与写者身份

### 5.12 S2-12 常驻 warn 无速率限制

- **症状**：断网/代理坏时每秒一次 `host.call.fail`，一天可上万行，淹没真信号（D-INFRA-05）。

- 噪声：显著降低。

### 8.4 D 与 E 的分歧裁决：trace 到底覆盖到哪

- **D 的结论（正确）**：`void runBackground(...)` 从 `withLogTrace` 的异步上下文派生，ALS 在 `await`/detached promise 上保留；自建 sink 的 `install.exec`/`install.verify` 行与 `install.request` 共享同一 `traceId`，`--trace` 能追完整链。
- **E 的 C8 判定（推理有误）**："exec/verify 无 trace"被判 CONFIRMED，但其依据是"电话已返回，异步行不在链内"，与 HEAD 的 ALS 语义不符；`tests/log-trace.test.mjs:245-272` 明确锁定"await 之后链仍是自己的"。
- **Lead 裁决**：采纳 D；E 的 C8 结论改写为——**关联缺口的准确表述是"无 requestId/intentHash；外部落点、客户端行、旧副本、重启补记、电话外行无链"**，而非"安装链无 trace"。此修正同时收敛了 A-08/A-S9 的 S3 定级：关联是残余缺口，不是整链断链。
- **保留**：`update.install.request` 与 `host.call` 在**外部 logCtx** 下确实无 trace（`sinkFromLogCtx` 不暴露 `trace`），这也是 §4.1 坚持 `intentHash` 字段的理由。

### 11.3 术语表

- **resident / ondemand / selfmon**：常驻（开关关闭也落）/ 按需（开关打开才落）/ 自监控（warn 恒落）；
- **派生命名空间**：日志目录名，pluginId 无损直用，有损则 `slug24+sha256(raw)6`；
- **diagnostic / detail**：宿主原话（永不出边界）/ ≤300 字人话格（可进回包、路径替换）；
- **在册 registered**：是否在 `dsh.profile.bundles` 或 deps 中，三态 true/false/null；
- **最后手段四态**：`last-resort`/`salvageable`/`dead-end`/`unknown`；
- **当帧命令 vs carried-over**：当前帧数据 vs 沿用旧帧（旧值不得展示/复制/高亮）。
