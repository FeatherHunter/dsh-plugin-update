## 结论摘要（TL;DR）

1. **包身份**：`dsh-log@0.3.1`，MIT，作者王辰浩，仓库 `git+https://github.com/FeatherHunter/dsh-log.git`，`engines.node >= 22`，纯 ESM（`"type": "module"`），**零运行时依赖**（`package.json` 只有 `devDependencies.typescript = 5.6.3`，没有 `dependencies` 键）。发布时刻 `2026-10-14T11:40:16.913Z`，比 0.3.0 晚约 6 小时 52 分。
   来源：registry；`<TAR>/package.json:1-57`
2. **包体积与文件数**：tarball 155.7 kB / 解包 464.3 kB / **103 个文件**；`dist.shasum` 与我们 `npm pack` 拿到的 tarball `310cc6b0008606e45550b3efabe54c1600eceb13` 逐字一致（即下文引用的确为官方发布物）。
   来源：registry `versions.0.3.1.dist`；`npm pack dsh-log@0.3.1` 的 `npm notice` 输出
3. **四个入口**（exports map 每个子路径都带 `types` 条件）：根 `dsh-log`（环境无关公共面）、`dsh-log/host`（宿主侧建库+电话）、`dsh-log/client`（客户端转发）、`dsh-log/node`（独立 Node 程序）。另有 `bin: { "dsh-log": "./dist/cli.js" }`，装包即带 `dsh-log tail` 只读查看命令。**没有任何 default export**，公开面全是具名导出，数量被 `tests/public-surface.test.mjs` 钉死为根 35 / host 23 / client 17 / node 4。
   来源：`<TAR>/package.json:15-36`；`<TAR>/dist/index.d.ts:1-4`；`<TAR>/README.md:272-279`；`<TAR>/dist/*.js` 全文无 `export default`（实测 grep）
4. **日志落点**：路径完全由调用方给的目录 + `pluginId` 决定，包内**不读任何环境变量、不带默认路径**。文件 = `<cacheDir>/<logDirName>/YYYY-MM-DD.log`，`logDirName` 默认派生 `logs-<pluginId>`（`pluginId === 'wf'` 时为 `logs`）；开关文件 = `<cacheDir>/log-switch-<pluginId>.json`（`wf` 时为 `log-switch.json`）。日志内容**只写文件**，不写 stdout/stderr（stdio 只用在 CLI 读侧）。
   来源：`<TAR>/dist/config/resolve.js:19-29`；`<TAR>/dist/node.d.ts:23-32`；`<TAR>/dist/cli/tail.js:129,137,178`（唯一 stdio 写入点）
5. **单目录单写者**是核心隔离语义：同一**日志目录**同一时刻只许一个活跃写者。`dsh-log/node` 是同步入口，第二个实例**建库当场抛中文错**（且解析 realpath，符号链接/junction 同键）；`dsh-log/host` 是异步入口，冲突在**写盘那一刻**判（租约等待 `DIR_LEASE_WAIT_MS = 200`），那批行不写共享文件、计入丢弃数，之后 `log()` 抛中文错，对方 `release()` 后自愈。登记表是**模块副本级**的，跨进程不设防。
   来源：`<TAR>/dist/engine/dir-lease.d.ts:1-9`；`<TAR>/README.md:26-33`；`<TAR>/INTEGRATION.md:26-33`
6. **多插件共存**：**没有全局单例、没有共享 transport**。每次 `createHostLog`/`createClientLog`/`createNodeHostLog` 都得到独立实例（内存队列、丢弃数、开关状态各自独立）；隔离靠三件事——① 目录按 `pluginId` 派生；② 电话名前缀按 `prefix` 拼（撞名注册时抛错、不覆盖）；③ 查询只回自己的桶，跨桶默认 `denied`，要跨插件必须宿主用 `aggregateLogQuery(ownerId, sources, allowedIds, args)` 显式授权。
   来源：`<TAR>/README.md:301-303`（"一次建库调用得到一个独立实例：内存队列、累计丢弃数、开关状态各自独立，互不串"）；`<TAR>/dist/host.d.ts:18-24`；`<TAR>/dist/host/types.d.ts:65-79`
7. **配置面很窄**：级别只有 `error | warn | info | debug`（单源 `LOG_LEVEL_ORDER`）；没有颜色配置、没有时间戳格式配置、**没有任何 `DSH_LOG_*` / `LOG_LEVEL` 环境变量**（全包 `process.env` 只出现一处：CLI 的 `NO_COLOR`）；sink/transport 靠注入依赖对象自定义而不是配置键（host 注入 `fs/timer/getCacheDir/getPlatform/DEFAULT_CWD`，node 注入 `fs/timer/joinPath`）。
   来源：`<TAR>/dist/core/level.js:13`；`<TAR>/dist/cli/tail.js:25`；`<TAR>/dist/store.d.ts:11-18`；`<TAR>/dist/node.d.ts:23-32`
8. **与 DSH 宿主的关系**：dsh-log **不是 DSH 宿主核心的一部分**。本机 `D:\DeepseekHarness\resources\app.asar`（121 MB，含 asar 头 JSON）全文检索 `dsh-log` / `createHostLog` / `logBatch` / `logQuery` / `dsws.debug` / `log-switch` **全部 -1**（方法有效性已用 `deepseek`、`DSH`、`node_modules` 三个必然存在的串自检通过）。它是**插件侧**日志库：由插件自己装、自己接线，宿主只被要求提供 `timer`（`ctx.get('timer')`）等依赖。包内唯一与 DSH 强耦合的东西是**固定的 43 个 DSH 事件名常驻表**（`BUILTIN_RESIDENT_EVENTS`）。
   来源：本机 `D:\DeepseekHarness\resources\app.asar` 字节级实测（`[System.IO.File]::ReadAllText` + `IndexOf`，含 sanity check）；`<TAR>/dist/core/resident.js`（43 条，逐条核过）
9. **本机实际跑的不是 0.3.1，而是 0.2.2**：`C:\Users\辰辰洋洋\.dsh\profiles\desktop\node_modules\dsh-log` 版本 `0.2.2`（11 个文件、无 `.d.ts`、无 `bin`），是 profile 里**唯一一份**（hoisted，无嵌套副本），被 `dsh-opencode-palette@2.0.28`、`dsh-prompt@0.4.14`、`dsh-plugin-update@0.13.0` 依赖。磁盘上历史日志是 0.2.x 形状（**无 `v` 键**），0.3.x 读侧查询会把这些行计入 `skipped`。
   来源：本机 `C:\Users\辰辰洋洋\.dsh\profiles\desktop\node_modules\dsh-log\package.json`；同 profile 各插件 `package.json`；`C:\Users\辰辰洋洋\.dsh\logs\**\*.log` 实测首行
10. **0.3.x 是断裂版本**：不兼容 0.2.x（无 shim、无双读、无回退）。0.3.1 = 0.3.0 全部内容 + 读侧工具（`parseLogLine`/`formatRow`/`formatRows`）+ `dsh-log tail` CLI + 客户端丢弃计数口径修正；公共接口只增不改，从 0.2.x 升级需要按 README 第 12 节的 7 步走（`pluginId` + `prefix` 双必填、目录不再手拼、`ready()` → `synced()`/`log.ready` 等）。
    来源：`<TAR>/README.md`（第 10 节、第 12 节）；`<TAR>/README.md:322-331`

### 3.3 并发写：目录租约 + 追加写 + 逐块核对

**同一日志目录同一时刻只许一个活跃写者**（0.3.0 口径），两条入口的处置不同：

| 入口 | 判冲突时机 | 冲突后果 |
|---|---|---|
| `dsh-log/node`（同步可知目录） | **建库当场** | 第二个活跃实例**抛中文错**；入口把目录解析成 realpath，符号链接/junction 指向同一真实目录时同样撞键抛错；上一个 `release()` 后才能接管 |
| `dsh-log/host`（目录要异步问宿主） | **写盘那一刻**（租约最多等 `DIR_LEASE_WAIT_MS = 200` ms） | 那批行计入丢弃数、**不写共享文件**；之后 `log()` 抛中文错；判冲突后队列残留行也不写共享文件；**只有 `log.persist.fail` 这类自监控诊断行不丢**，留着闸门解除后补写；冲突期间清空与导出降级为失败形状 |
| 开关文件 | 同样在写盘那一刻判占用 | 共用同一 `switchFileName` 的第二个实例**不会覆盖**前一个写下的开关 |

**冲突会自愈**：闸门只在"判定那一刻的持有者还在"时有效；对方写完交还或 `release()` 之后，本实例的下一行照常落盘。`release()` 同步幂等。
来源：`<TAR>/README.md` 开头「先跑起来」段的 blockquote；`<TAR>/INTEGRATION.md:26-33`；`<TAR>/dist/engine/dir-lease.d.ts:1-9`

**跨进程没有登记**（原文："登记表是模块副本级的，另一个进程看不见，包不做跨进程协调"）。实际后果取决于文件服务**有没有 `appendText`**：

- **有追加能力**（`dsh-log/node` 自带；自己实现时包一层 `fs.appendFile`）：两个进程**只交错、不互相覆写**。实测两进程同目录各写 8 行 → 16 行一行不少、无撕裂行；大行也验过（各 20 行 × 64 KB → 40 行、0 条半行），因为引擎把批次按**行边界**切成 ≤ `APPEND_ATOMIC_MAX = 4096` 字节的块再逐块追加（一次大块 `O_APPEND` 写不保证原子，不切块时实测出现 2 条读不出来的半行）。**边界**：单行自己超过 4 KB 时整行写、不再切——"一行几十 KB × 多进程同写"仍有理论风险。
- **没有追加能力**（只有读改写）：后写者按自己读到的旧内容整份覆写，**会吃掉对方刚写的行**（实测两进程各写 5 行、间隔 30 ms → 10 行只剩 9 行；双方 `exit 0`、`dropped` 不增）。
- 两种形态都补了事后可观测：记得上次写完的字节数，下次读回来对不上就落一条 `log.persist.fail(reason: 'foreign-write')`（只报告"有人动过"，不猜被吃了几行，所以 `dropped` 不会跟着涨）。
- 引擎**不把"追加动作正常返回"当证据**：有 `sizeOf` 就每笔追加后 stat 核对，没有就每 8 笔或累计 256 KB 回读一次；发现少写就**只补没落地的那段**并落 `append-not-effective` / `append-partial` / `append-failed`。

来源：`<TAR>/INTEGRATION.md:33`；`<TAR>/INTEGRATION.md:146-147`；`<TAR>/dist/engine/io.d.ts:1-9`；`<TAR>/README.md` 第 6 节

**写盘是异步的**：约 1000 ms 防抖（`LOG_DEBOUNCE_MS = 1000`），`error`/`warn` 走直通不等防抖，但"直通"只是不等防抖、写盘仍是异步的——实测 `log('error', …)` 紧跟 `process.exit(0)` 是 **0 行落盘**；只有 `await log.ready` / `await store.synced()` 才能保。写盘失败**先不丢行**：整批进重试位、有界自动重试；只有还压在内存里的行（重试位 + 队列）超过 `maxQueue × 10` 才丢最旧的普通行并响一次 `onDrop('write-fail')`，`error`/`warn` 留到最后。
来源：`<TAR>/dist/config/constants.d.ts:1`；`<TAR>/README.md` 第 0.1 节 ⑪ 与 2.1 节第 1 条；`<TAR>/README.md` 第 6 节

## 4. 多实例 / 多插件共存语义

### 4.1 没有全局单例、没有共享 transport

> "一次建库调用得到一个独立实例：内存队列、累计丢弃数、开关状态各自独立，互不串。"
> 来源：`<TAR>/README.md:303`

术语表也逐条钉住这个口径：实例 = 一次建库（`createHostLog` / `createNodeHostLog` / `createQuickLog` / `createClientLog`）得到的对象，"队列、丢弃数、开关状态各自独立"。
来源：`<TAR>/README.md` 术语表（"实例"一行）

工程上也印证：`createHostLog(deps, config)` 的实现只是 `createLogStore` + `buildPhoneNames`，没有任何模块级缓存；`registerHostLogPhones(registry, hostLog)` 把处理函数写进**调用方自己的 registry**（包不持有全局注册表）。
来源：`<TAR>/dist/host.js`（`createHostLog` / `registerHostLogPhones` 实现）；`<TAR>/dist/host.d.ts:13-24`

### 4.2 隔离靠三件事（没有 namespace/label/channel/tag 这种"标签"概念）

**没有** `namespace` / `label` / `channel` / `tag` 配置项。隔离维度就两个字符串：`pluginId`（决定目录与开关文件名）与 `prefix`（决定电话名前缀）。二者都是**双必填**、缺一即抛中文错，且**不再互相回退**（0.2.x 的"prefix 缺省回退到 pluginId"已删）。

字符约束（两者同一套）：只能用小写英文字母、数字、中横线，长度 1–32；收到大写**直接报错不做静默转小写**；含点或文件不安全字符（`/ \ : * ? " < > |` 空格）同样报错。
来源：`<TAR>/dist/config/resolve.js:9-18`（抛错文案原文）；`<TAR>/dist/config/validate.d.ts`；`<TAR>/README.md` 第 4 节；`<TAR>/INTEGRATION.md:305-306`

① **目录隔离**：默认 `logs-<pluginId>`，不同 pluginId 天然分目录。
  来源：`<TAR>/dist/config/resolve.js:19-24`
② **电话名隔离**：新电话名 = `prefix + '.' + 动作名`；撞名注册时**抛错、不覆盖旧的**；`wf` 是保留命名空间（只给首个官方插件）。
  来源：`<TAR>/dist/config/phones.d.ts`；`<TAR>/INTEGRATION.md:305`（常见坑第 4 条）；`<TAR>/README.md` 第 5.1 节
③ **查询隔离（默认拒绝）**：查询电话名 = `前缀.logQuery`（由 `buildLogQueryPhoneName` 单源派生，**不进** `phoneNames` 那份冻结映射）。查询只回自己的桶；`handleLogQuery({ pluginId: 'other-plugin' })` 回 `denied: true`、`entries` 空、**一行不读**；被拒不等于源行被删。
  来源：`<TAR>/README.md` 第 0.1 节 ⑤ 与第 5.1 节；`<TAR>/dist/host.d.ts:22`；`<TAR>/dist/config/constants.d.ts:17`

**跨插件读需要宿主显式授权**：

```js
const sources = [
  { pluginId: 'my-plugin',    query: (args) => hostLog.store.handleLogQuery(args) },
  { pluginId: 'other-plugin', query: (args) => otherStore.handleLogQuery(args) }
]
const agg = aggregateLogQuery('my-plugin', sources, ['other-plugin'], { pluginId: 'other-plugin' })
// agg.denied 里列出的就是被拒的来源；agg.entries 只含被授权来源的行
```

来源：`<TAR>/README.md` 第 0.1 节 ⑤；`<TAR>/dist/host/types.d.ts:65-79`

`traceChain` 通道还有一层防伪：**跨桶伪造的 `traceId` 读被拒（`denied`）**，源行不会被删。
来源：`<TAR>/README.md` 第 5.3 节

### 4.3 各插件各自 node_modules 里各有一份 dsh-log 副本时

- **登记表是模块副本级的**——不同副本各有各的目录租约登记表，**互相看不见**。所以"同 pluginId、同目录、两份副本"这种组合下，`dsh-log/node` 的"建库当场抛"**不会触发**，两边都会认为自己独占，退化成 §3.3 的跨进程情形（有 `appendText` 则交错、没有则可能覆写吃行）。
  来源：`<TAR>/INTEGRATION.md:33`（"登记表是模块副本级的，另一个进程看不见"）；`<TAR>/README.md` 开头 blockquote（"跨进程没有登记（风险提示，不是保证）"）
- **官方给的正确做法**：一个日志目录只给一个写者；目录按 `pluginId` 派生，第二个插件走默认派生自然分到不同目录。
  来源：`<TAR>/INTEGRATION.md:302`（常见坑第 1 条）
- **本机现状（一手实测）**：`C:\Users\辰辰洋洋\.dsh\profiles\desktop` 下**只有一份** dsh-log（`node_modules\dsh-log` v0.2.2，hoisted），没有嵌套副本——即当前所有插件**共享同一个模块实例**。下游依赖：`dsh-opencode-palette@2.0.28 → dsh-log 0.2.2`、`dsh-plugin-update@0.13.0 → dsh-log 0.2.2`、`dsh-prompt@0.4.14 → dsh-log ^0.2.1`。
  来源：本机 `Get-ChildItem .dsh\profiles\desktop -Recurse -Directory -Filter dsh-log` 只回一条；各插件 `package.json` 的 `dependencies` 实测

### 4.4 同一进程内两个实例同目录会怎样（明确定义的失败）

- `dsh-log/node`：第二个 `createNodeHostLog`/`createQuickLog` 同目录 → **建库当场抛中文错**；前一个 `release()` 后才可接管。
- `dsh-log/host`：建库不抛，**写盘那一刻**才判；那批行**不写共享文件**、计入 `dropped`，之后 `log()` 抛中文错，对方交还后自愈。
- 同一 `cacheDir` 下**不同 `pluginId` 各写各的目录与开关文件，可以并存**。
 来源：`<TAR>/INTEGRATION.md:26-32`；`<TAR>/README.md` 开头 blockquote 末条

## 6. 与 DSH 宿主的关系

### 6.1 它是不是 DSH 官方/伴生日志库？

- **是同一作者/同一生态的一手产物，但不是 DSH 宿主的一部分。** 作者王辰浩、仓库 `FeatherHunter/dsh-log`；包的自我定位是"把本仓日志系统装成的 npm 包：DSH 插件与独立跑的 Node 程序都能照着它集成使用"，由三块合成（宿主落盘引擎 / 客户端转发引擎 / 事件清单格式与通用检查器），是"地图 #556 的产物"。
  来源：registry `author` / `repository` / `readme` 首段
- registry 里 `maintainers` 只有 `feather_wch <975559549@qq.com>`，与 `dsh-plugin-update`、`dsh-mattpocock-skills-deck` 同一位维护者。
  来源：registry `maintainers`；本机 `D:\dsh-plugin\dsh-opencode-palette\node_modules\dsh-log` 等仓库同源
- **本机宿主里没有它**：见 §7.1 的字节级检索结果。

### 6.2 它假定自己跑在 DSH 插件进程里吗？

- **不假定**。四个入口里 `dsh-log/node` 明确"不是插件的独立 Node 程序用"，"它不碰电话层、也没有客户端转发"，且"**不决定日志写到哪**——目录由调用方传入，入口自己不读任何环境变量、也不带默认路径"。
  来源：`<TAR>/README.md` 第 2 节、第 2.1 节
- **不读 `ctx`、不读宿主注入的全局**。0.3.0 明确删掉了全局裸函数：`dswsLogHash` 与 `dswsLogTrunc` 两个全局裸函数已删，"包内不再读全局对象"。
  来源：`<TAR>/README.md` 第 8 节第 1 条
- **唯一的宿主耦合点是"43 个 DSH 常驻事件名"**：`BUILTIN_RESIDENT_EVENTS` 是写死的 DSH 事件清单（`host.call`、`host.start`、`update.install.exec`、`git.exec`…共 43 条，均已逐条核对），与 `research/489-appendix.md` 第 1 章的计数门禁对齐。DSH 侧既有行为靠它一字不变。
  来源：`<TAR>/dist/core/resident.js`（`BUILTIN_RESIDENT_EVENTS` 数组 + 注释"DSH 常驻 43 条（与 research/489-appendix.md 第 1 章一致，计数门禁逐项核对）"）
- **`wf` 是给首个官方插件留的保留命名空间**：前缀传 `wf` 时 5 个电话字面与现状一字不差、目录名与开关文件名也走 legacy 字面。
  来源：`<TAR>/README.md` 第 5.1 节；`<TAR>/README.md:299`

### 6.3 有没有"第三方开发者把日志交回来"的机制？

有，而且是明写的设计目标（隔离在写侧、聚合在读侧且需授权）：

| 机制 | 形态 |
|---|---|
| **事件清单（清单即契约）** | `event-list.template.json` 模板；对象形式传给 `eventList`；`parseEventListManifest` 验形状、`lintEventFields` 两档字段白名单（未知字段 warn、未知事件 error，**红不拦上线**）、`computeEventCounts` 自算三类条数 |
| **让第三方 info 不靠开关落盘** | 清单里 `kind: 'resident'` → 写侧放行集合 = 43 个内置名 ∪ 清单 resident。注释里写明这是为第三方补的正路："外部插件把自己的 info 标成 resident 也照样静默消失（2026-10-14 独立审查实测…）…第三方插件终于有一条「不用打开开关就能让某类 info 落盘」的正路" |
| **导出** | `logExport` 电话回 8 键含原文 `text`、摘要 `summary`（`pluginVersion`/`os`/`cwd`/`logSwitch`/`header{pid,startedAt,dir}`）、以及**目录与路径 `dir`/`path`**——用户拿到路径就能自己去看文件 |
| **诊断行** | `log.persist.fail`（warn，`reason` ∈ `write-fail`/`dir-conflict`/`no-dir`/`foreign-write`/`append-not-effective`/`append-partial`/`append-failed`）、`log.rotate.seal`/`log.rotate.degraded`/`log.rotate.oversize`/`log.retain.evict`（info）、`log.forward.summary`（warn） |
| **脱敏** | 清单的 `codes` 是"截断或散列代号"、`rules` 是"具名正则名"，"都是引用名，命中只记规则名不记原文"；`log.export.fail` 的 `errorHash` 用 8 位十六进制散列；`lastPersistFail` 只给 `op`/`reason`/`dirHash`（**不含真实路径**）；导出失败截断固定为错误消息前 120 字切片 |
| **官方不做的** | "不自动上报日志，只做本地落盘加手动导出；不压缩、不外传归档"——轮转只在本地改名封存、按天删旧件，不打包、不上传 |

### 6.4 它不是什么（避免误判）

- 不是"DSH 宿主统一日志"：宿主侧没有它的痕迹（§7.1），落盘者是**插件自己的宿主半区**。
- 不提供"日志回传给宿主/云端"的通道：只有本地文件 + 导出电话 + 查询电话。
- 0.3.x 与 0.2.x 数据不互通：`v != 3` 的旧行查询跳过并计入 `skipped`，但"仍在文件里、导出看得见"。
  来源：`<TAR>/README.md` 第 0.2 节故障排查表、第 12 节第 7 步

## 8. 不确定 / 未证实清单

1. **DSH 宿主是否存在原生日志电话机制**——未证实。只能证明本机 asar 里没有 `dsh-log` 与它那几个电话名字符串（`logBatch`/`logQuery`/…）。若宿主是通过 profile 侧动态装载插件、插件自行 `import 'dsh-log/host'`，宿主本就不需要出现这些字符串。
2. **0.3.1 README 内两处日期口径**（第 1/9 节仍写"当前版本 0.3.0"、第 10 节写 0.3.1 是 2026-10-15）与 registry 时间（2026-10-14T11:40Z）的矛盾——未证实是笔误还是本地日期口径，不排除 README 发布后未同步。
3. **`pluginId === 'wf'` 的 legacy 派生是否会在 0.4 被移除**——README 只说"`wf` 是保留命名空间，只给首个官方插件"，未给弃用时间表。
4. **`registry` 顶层 `readme` 与 tarball `README.md` 是否逐字一致**——只抽查了第 2.2、3.1 两节，逐字相同；未做全文 diff。
5. **app.asar 检索的边界**：用的是"整份文件按 UTF-8 解码后 `IndexOf`"，其中含二进制段。这对纯 ASCII 的模块名/电话名是可靠的（sanity check 用 `deepseek`/`DSH`/`node_modules` 三个必然存在的串验证过），但若有**压缩过的**子资源内含这些串，本方法查不到。未证实 asar 内是否存在压缩子资源。
6. **0.3.1 尚未在任何本机插件里跑过**：profile 里只有 0.2.2；0.3.x 的断裂语义（双必填、目录不手拼、`ready()` 移除）在本机**没有实测样本**，全部依据是包内文档与 d.ts。
