02总体架构：一条日志行怎么走到磁盘

三段旅程：发射侧（谁在什么环节说什么）→ 内核侧（脱敏、白名单、准入、预算、路由）→ 落盘侧（dsh-log 引擎按天写文件、封存、保留）。任何一段坏了都不得影响主流程，这是四条纪律里最硬的一条。

三侧职责边界：发射侧只负责「在这个环节说这件事」；内核侧决定「这行合不合规、有没有地方去、是不是重复」；落盘侧是上游引擎，本包不碰文件格式、不自己做轮转。图为概念图，实线表示调用方向。

为什么要有唯一发射口

脱敏、白名单、准入、预算四条纪律如果散在各个调用点写，就一定有人漏一条，而漏掉的那条只会在第三方交日志时才被发现。所以全包只有 emitUpdateLog 一处可以把行交给落点，其余地方只许调它。

src/log/emit.ts:1-19

为什么要有待接落点

自建引擎是异步的（动态 import + 读盘），而 createHostUpdate 是同步契约，不能为日志改成 async 而破坏所有集成方调用点。于是先接一个环形 200 行的「先收后转」落点，建好了按序灌进去，建不起来整体丢弃并计数。

src/log/sink.ts:65-115

为什么降级绝不外抛

日志是旁路：拿不到 dsh-log、撞租约、目录写不了 —— 一律降级成「没有落点」，事件照发、主流程零影响。降级带 60 秒冷却，冷却过后下一次接线会重新试（插件重装、面板重挂就是恢复路径）。

3.1 命名空间：把任意标识安全地映成一棵目录

dsh-log 只收 [a-z0-9-]{1,32} 形状的 pluginId，收到大写直接抛；而本包允许集成方用 My.Plugin 这类标识。只做小写化会让两个不同标识撞进同一棵目录 —— 那恰好就是要消灭的「同一目录两个写者」。所以派生规则是有损即补指纹。

src/log/namespace.ts:64-76 · 派生算法
export function deriveLogNamespace(rawPluginId: unknown): string {
  const raw = typeof rawPluginId === 'string' ? rawPluginId.trim() : ''
  const slug = raw.toLowerCase().replace(/[^a-z0-9-]+/g, '-').replace(/-+/g, '-').replace(/^-+|-+$/g, '')
  // 无损且合法：原样通过（集成方最常见情形，也是「目录名 = 我写的标识」的保证）
  if (slug && slug === raw && NAMESPACE_SHAPE.test(slug)) return slug
  const base = slug.slice(0, SLUG_CHARS).replace(/-+$/g, '') || FALLBACK_SLUG   // SLUG_CHARS = 24
  const derived = `${base}-${hashToken(raw, HASH_CHARS)}`                       // HASH_CHARS = 6
  return NAMESPACE_SHAPE.test(derived) ? derived : `${FALLBACK_SLUG}-${hashToken(raw, HASH_CHARS)}`
}

三条不变量（测试逐条钉住）

  1. 已经是合法命名空间的 id 原样通过（目录名与集成方写的标识一致）；合法标识最长 32 字符走无损分支。
  2. 有损分支：SLUG_CHARS = 24 + - + HASH_CHARS = 6 = 31 ≤ 32，概率性不重名 —— 见第 6 节边界实测（5000 个同前缀超长标识里 1 组撞名）。
  3. 返回值恒满足 dsh-log 的 pluginId 形状（小写字母数字连字符，1..32）。

3.2 登记表：同进程内「一个目录一个写者」由机制保证

dsh-log 的目录租约登记表是模块副本级的 —— 同一进程里两份 dsh-log 模块副本互相看不见。而本包同进程出现两份副本是现实（顶层一份、别的插件嵌套一份）。两份副本各自建库同一目录时，谁都不知道对方在写，后写的会把先写的整份文件吃掉（dsh-log 实测：10 行剩 9 行）。

所以登记表挂在 globalThis[Symbol.for('dsh-plugin-update.log.registry')]：同进程所有副本共用一张表，同一目录只有一个句柄，第二份副本拿到的是同一个实例。

登记表到底挡住了什么（实测口径，不是推测）

负对照 A：绕开登记表、保留追加能力 → 两个写者共存，但在本机（appendText 可用）20 行一行不少 —— 即本机登记表挡住的不是「丢行」，而是「两个写者 + 相互看不见」这件事本身。

负对照 B：绕开登记表并把 appendText 摘掉，引擎退回「读旧文 + 拼新行 + 全文覆写」通道 → 每轮发 10 行只剩 5 行，共发 50 行 → 文件里只剩 25 个标记。这就是丢行的真实形态，也是登记表存在的理由。

3.3 路由表：取代模块级 last-writer-wins

改造前的实现用 let phoneLogCtx 装落点，deps.logCtx ?? phoneLogCtx 是单向且不清零的 —— 谁最后调一次 createHostUpdate，谁就把别人的落点覆盖掉。同一份 DSH 里装两个用本更新系统的插件时，后装的那个会把前一个的日志行一并收走。这是「日志互相覆盖」的根因，不在文件格式。

现在的语义

  • 每个插件标识一个落点，各写各的；bind 覆盖是预期行为（同一插件只有一份日志，重装面板会再 bind 一次）。
  • resolve 取不到就回 null，发射口按「丢弃并计数」处理，绝不回退到别人的 sink。
  • unbind 带 sink 参数时只在当前绑的就是它时才摘，避免把后绑的误摘。

src/log/router.ts:16-49

为什么路由表不做成 globalThis 单例

多副本时每份副本各服务自己创建的实例，各自路由才是对的。真正需要跨副本共享的是「同一日志目录只许一个写者」那件事 —— 它在登记表上，那边才是 globalThis。两件事分得很清楚：路由是本副本的事，写者独占是跨副本的事。

src/log/router.ts:51-56

丢行与串台的取舍：代码注释写得很直白 —— 「丢行看得出来，串台看不出来」，所以取不到落点时宁可丢并计数，也不猜一个落点。

08脱敏与可聚合：日志行里只有稳定码

ADR-0006 立了一条听起来苛刻、但让日志真正可用的规矩：日志行只承载稳定码与参数，人话在渲染层产出。理由不是洁癖，是量级 —— 934 KB/天、5309 行同名事件的日志，只有稳定码才能计数、才能跨版本对齐；一句中文人话既不能聚合也不能 grep。

允许的三类字符串值

  1. 版本号 —— 经中央校验器规范化后的 semver 形状；
  2. 枚举白名单值 —— 每个枚举在事件清单里逐值声明（channel: 'stable'|'beta'、outcome: 'delegated'|'manual'|'failed'…）；
  3. 导出量 —— hash8 短哈希、计数、时长（ms）、字节数、布尔。

不允许的字符串

宿主原话、错误 message、命令行、文件路径、URL、usage 原文、插件标识原文。
边界怎么守：发射口 sanitizeLogFields 对字符串过 sanitizeDetail；对象/数组先序列化再脱敏（宁可变成字符串，也不许原样落盘）；fields 只许扁平键值，不嵌套。

它解开了 ADR-0001 登记的一条老张力

ADR-0001 曾登记：detail 是全系统唯一自由文本出口，而真实存在的唯一诊断通道恰恰是宿主原话。日志是长期留存的出口（按天落盘、14 天保留、第三方会贴进 issue），所以不能沿用那条口径。ADR-0006 的解法是让两个出口不重叠：要看人话去面板（或渲染层生成），要聚合去日志；同一份宿主原话绝不进日志行。detail/diagnostic 的现有口径一个字不改。

代价（自觉取舍，不是遗漏）

  • 人话要在两条渲染路径各实现一次（dsh-log tail 的终端格式化、面板的 src/bilingual.ts）。
  • 新增一个字段要改三处：发射点、事件清单、负向断言用例。这是用「写三处」换「日志行永不夹带文本」。
  • 需要人读的细节（例如错误原因）只能给稳定码 + hash8；排查细节要去面板的 detail 或工具返回的 steps[]。
  • 回退线也写清了：若实测发现某类问题只能靠文本才能查，走破冰新增一个具名字段，而不是放开任意文本。
