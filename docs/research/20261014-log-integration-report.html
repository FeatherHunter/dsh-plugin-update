三条需求各自的交付物

  • 每个环节都能交日志 → 28 事件覆盖 19 个环节；宿主／中立侧 11 个环节逐环节落到函数级唯一发射口，客户端 11 个落点走 <prefix>.logAppend 电话回宿主。

  • 多插件互不覆盖 → 每插件一棵目录 + globalThis 登记表（同目录单句柄）+ 按 pluginId 路由表，三件东西合起来取代了旧实现里那个「后注册者夺走前一个落点」的模块级变量。

这次集成真正的性质变化

  • 日志从「三个事件名、五个发射点、16 个环节为零」变成一张登记制的事件面：事件名、级别、档位、字段白名单都在随包 JSON 里，未登记即不落盘。
  • 日志出口从「一个模块级 let phoneLogCtx，谁最后接线谁说话」变成按标识寻址的路由表：取不到落点就丢弃并计数，绝不回退到别人的 sink。
  • 噪声治理落在发射侧而非读侧：1 秒一拍的轮询不再产生任何常驻行，稳态预算从实测 86400 行/天降到 0 行/天。
  • 本包由此第一次带上运行期依赖（dsh-log@^0.3.1），这是一次显式立字的纪律破例，理由与回退线都在 ADR-0005。

一句话结论

日志集成已经功能闭环、有实证：19/19 环节接上、事件表 28 条成册、隔离三场景实测全过、预算 8/8 达标、全量测试 0 失败。剩下的不是「日志能不能用」，而是发布收口（票 #123）与几条如实登记的边界（跨进程同目录只承诺「交错不覆写」、文档面个别措辞滞后）——见第 12 节。

02总体架构：一条日志行怎么走到磁盘

三段旅程：发射侧（谁在什么环节说什么）→ 内核侧（脱敏、白名单、准入、预算、路由）→ 落盘侧（dsh-log 引擎按天写文件、封存、保留）。任何一段坏了都不得影响主流程，这是四条纪律里最硬的一条。

三侧职责边界：发射侧只负责「在这个环节说这件事」；内核侧决定「这行合不合规、有没有地方去、是不是重复」；落盘侧是上游引擎，本包不碰文件格式、不自己做轮转。图为概念图，实线表示调用方向。

为什么要有唯一发射口

脱敏、白名单、准入、预算四条纪律如果散在各个调用点写，就一定有人漏一条，而漏掉的那条只会在第三方交日志时才被发现。所以全包只有 emitUpdateLog 一处可以把行交给落点，其余地方只许调它。

src/log/emit.ts:1-19

为什么要有待接落点

自建引擎是异步的（动态 import + 读盘），而 createHostUpdate 是同步契约，不能为日志改成 async 而破坏所有集成方调用点。于是先接一个环形 200 行的「先收后转」落点，建好了按序灌进去，建不起来整体丢弃并计数。

src/log/sink.ts:65-115

为什么降级绝不外抛

日志是旁路：拿不到 dsh-log、撞租约、目录写不了 —— 一律降级成「没有落点」，事件照发、主流程零影响。降级带 60 秒冷却，冷却过后下一次接线会重新试（插件重装、面板重挂就是恢复路径）。

src/log/registry.ts:94-96, 271-289

3.1 命名空间：把任意标识安全地映成一棵目录

dsh-log 只收 [a-z0-9-]{1,32} 形状的 pluginId，收到大写直接抛；而本包允许集成方用 My.Plugin 这类标识。只做小写化会让两个不同标识撞进同一棵目录 —— 那恰好就是要消灭的「同一目录两个写者」。所以派生规则是有损即补指纹。

src/log/namespace.ts:64-76 · 派生算法
export function deriveLogNamespace(rawPluginId: unknown): string {
  const raw = typeof rawPluginId === 'string' ? rawPluginId.trim() : ''
  const slug = raw.toLowerCase().replace(/[^a-z0-9-]+/g, '-').replace(/-+/g, '-').replace(/^-+|-+$/g, '')
  // 无损且合法：原样通过（集成方最常见情形，也是「目录名 = 我写的标识」的保证）
  if (slug && slug === raw && NAMESPACE_SHAPE.test(slug)) return slug
  const base = slug.slice(0, SLUG_CHARS).replace(/-+$/g, '') || FALLBACK_SLUG   // SLUG_CHARS = 24
  const derived = `${base}-${hashToken(raw, HASH_CHARS)}`                       // HASH_CHARS = 6
  return NAMESPACE_SHAPE.test(derived) ? derived : `${FALLBACK_SLUG}-${hashToken(raw, HASH_CHARS)}`
}

三条不变量（测试逐条钉住）

  1. 已经是合法命名空间的 id 原样通过（目录名与集成方写的标识一致）。
  2. 不同 raw 标识永不派生出同一个名字（含空格、点、大写、超长、中文、空串）。
  3. 返回值恒满足 dsh-log 的 pluginId 形状（小写字母数字连字符，1..32）。

tests/log-kernel.test.mjs

两个容易踩的细节

  • 目录身份键要做平台归一：Windows 下 Logs 与 logs 是同一目录，必须折叠大小写，否则同一目录会拿到两个句柄、两个写者又回来了；POSIX 大小写敏感，不能乱折叠。namespace.ts:83-86
  • wf 是 dsh-log 的保留命名空间：pluginId === 'wf' 时目录退化成一棵共用树，所以本包只把 wf 当前缀默认值，绝不用它当 pluginId；开关文件名同规则。namespace.ts:88-91 · ADR-0005 决策 3

3.2 登记表：同进程内「一个目录一个写者」由机制保证

dsh-log 的目录租约登记表是模块副本级的 —— 同一进程里两份 dsh-log 模块副本互相看不见。而本包同进程出现两份副本是现实（顶层一份、别的插件嵌套一份）。两份副本各自建库同一目录时，谁都不知道对方在写，后写的会把先写的整份文件吃掉（dsh-log 实测：10 行剩 9 行）。

所以登记表挂在 globalThis[Symbol.for('dsh-plugin-update.log.registry')]：同进程所有副本共用一张表，同一目录只有一个句柄，第二份副本拿到的是同一个实例。

src/log/registry.ts:98-106 · 登记表状态挂在 globalThis（Symbol.for 跨副本同名同键）
function registryState(): RegistryState {
  const holder = globalThis as unknown as Record<string | symbol, unknown>
  let state = holder[Symbol.for(OWN_LOG_REGISTRY_KEY)] as RegistryState | undefined
  if (!state || !(state.handles instanceof Map)) {
    state = { handles: new Map(), degraded: new Map(), cooldownUntil: new Map(), lastDegraded: null }
    holder[Symbol.for(OWN_LOG_REGISTRY_KEY)] = state
  }
  return state
}

登记表到底挡住了什么（实测口径，不是推测）

负对照 A：绕开登记表、保留追加能力 → 两个写者共存，但在本机（appendText 可用）20 行一行不少 —— 即本机登记表挡住的不是「丢行」，而是「两个写者 + 相互看不见」这件事本身。

负对照 B：绕开登记表并把 appendText 摘掉，引擎退回「读旧文 + 拼新行 + 全文覆写」通道 → 每轮发 10 行只剩 5 行，共发 50 行 → 文件里只剩 25 个标记。这就是丢行的真实形态，也是登记表存在的理由。

docs/research/20261014-log-isolation-verification.md:56-76

3.3 路由表：取代模块级 last-writer-wins

改造前的实现用 let phoneLogCtx 装落点，deps.logCtx ?? phoneLogCtx 是单向且不清零的 —— 谁最后调一次 createHostUpdate，谁就把别人的落点覆盖掉。同一份 DSH 里装两个用本更新系统的插件时，后装的那个会把前一个的日志行一并收走。这是「日志互相覆盖」的根因，不在文件格式。

现在的语义

  • 每个插件标识一个落点，各写各的；bind 覆盖是预期行为（同一插件只有一份日志，重装面板会再 bind 一次）。
  • resolve 取不到就回 null，发射口按「丢弃并计数」处理，绝不回退到别人的 sink。
  • unbind 带 sink 参数时只在当前绑的就是它时才摘，避免把后绑的误摘。

src/log/router.ts:16-49

为什么路由表不做成 globalThis 单例

多副本时每份副本各服务自己创建的实例，各自路由才是对的。真正需要跨副本共享的是「同一日志目录只许一个写者」那件事 —— 它在登记表上，那边才是 globalThis。两件事分得很清楚：路由是本副本的事，写者独占是跨副本的事。

src/log/router.ts:51-56

丢行与串台的取舍：代码注释写得很直白 —— 「丢行看得出来，串台看不出来」，所以取不到落点时宁可丢并计数，也不猜一个落点。

3.4 唯一发射口：四条纪律与它们的计数口径

createLogEmitter 内部四个计数器 + 两个集合，全部可从诊断面读出（logEmitterCounts()）
计数含义触发条件
emitted真交给落点的行数四条纪律全过、且没被预算守卫或准入短路拦下
suppressed被边沿预算守卫压掉的行数事件在清单里标了边沿触发（或调用方给了指纹），且指纹与上次相同
skipped被准入短路拦下的行数sink.isEnabled(level, event) 回假 —— 这是「开关没开」，不是丢行，不触发 degraded
dropped真丢的行数（带 droppedByReason）unknown-field / unknown-event / no-plugin-id / no-sink / emit-threw

丢弃原因会经 update.log.degraded 露出（同一原因全进程只记首次）；no-plugin-id 是唯一没有对应行的原因 —— 连插件标识都没有的行没法路由，也就没有落点可以承载这条坏消息。

function emit(level, event, fields, opts) {
  const pluginId = opts?.pluginId ?? fields['pluginId']
  if (!pluginId) { countDrop('no-plugin-id'); return false }              // ① 没标识没法路由
  const tableNow = table()
  if (tableNow && !checkLogFields(event, Object.keys(raw), tableNow)) {    // ② 清单字段白名单
    countDrop(tableNow.events?.[event] ? 'unknown-field' : 'unknown-event'); return false
  }
  const sink = resolveSink(pluginId)
  if (!sink || sink === NOOP_SINK) { countDrop('no-sink'); return false }  // ③ 取不到落点即丢，绝不回退
  if (!sink.isEnabled(level, event)) { counts.skipped++; return false }    // ④ 准入短路（不算丢）
  const sanitized = sanitizeLogFields(raw)
  const fingerprint = opts?.fingerprint ?? (isEdgeEvent(event, tableNow) ? fieldFingerprint(sanitized) : undefined)
  if (!opts?.always && previous === fingerprint) { counts.suppressed++; return false }  // ⑤ 边沿预算守卫
  sink.fire(level, event, sanitized); counts.emitted++; return true
}

口径分明：什么是「丢」，什么是「准入」

协议层拒收（形状不对／级别不认识／不是客户端事件／字段不合清单／超量／过期）计入 dropped；而引擎因调试开关关掉而 skip 的按需行不计 drop —— 那是准入，不是丢行。

  • 跨进程没有协调，这是设计承诺：两个进程同写一棵目录只保证「交错、不整篇覆写」，不保证行序、不保证去重。

那次不达标是怎么修的（机制，不是玄学）

首测机制定位在 src/host.ts:796／:898：电话成功时无条件发 host.call；清单里 host.call 的 guard 虽然写着「成功且状态未变时轮询不发」，但 isEdgeEvent 只认 guard 文本里带「边沿触发」四个字的事件（只有 update.status.changed 与 update.queue.transition 命中），宿主侧也没实现「状态未变就不发」。于是 1 秒一拍 = 86400 行/天。

修法落在 src/host.ts:845-855：isStatusPoll 认出轮询电话，算快照指纹，只有「上次算得出、这次算得出、且与上次不同」才留一行；指纹算不出来时宁多发一行，也不误吞一次状态变化；失败行 host.call.fail 不受影响；host.call 的名字与五键形状一字未动。

08脱敏与可聚合：日志行里只有稳定码

ADR-0006 立了一条听起来苛刻、但让日志真正可用的规矩：日志行只承载稳定码与参数，人话在渲染层产出。理由不是洁癖，是量级 —— 934 KB/天、5309 行同名事件的日志，只有稳定码才能计数、才能跨版本对齐；一句中文人话既不能聚合也不能 grep。

允许的三类字符串值

  1. 版本号 —— 经中央校验器规范化后的 semver 形状；
  2. 枚举白名单值 —— 每个枚举在事件清单里逐值声明（channel: 'stable'|'beta'、outcome: 'delegated'|'manual'|'failed'…）；
  3. 导出量 —— hash8 短哈希、计数、时长（ms）、字节数、布尔。

不允许的字符串

宿主原话、错误 message、命令行、文件路径、URL、usage 原文、插件标识原文。
边界怎么守：发射口 sanitizeLogFields 对字符串过 sanitizeDetail；对象/数组先序列化再脱敏（宁可变成字符串，也不许原样落盘）；fields 只许扁平键值，不嵌套。

它解开了 ADR-0001 登记的一条老张力

ADR-0001 曾登记：detail 是全系统唯一自由文本出口，而真实存在的唯一诊断通道恰恰是宿主原话。日志是长期留存的出口（按天落盘、14 天保留、第三方会贴进 issue），所以不能沿用那条口径。ADR-0006 的解法是让两个出口不重叠：要看人话去面板（或渲染层生成），要聚合去日志；同一份宿主原话绝不进日志行。detail/diagnostic 的现有口径一个字不改。

代价（自觉取舍，不是遗漏）

  • 人话要在两条渲染路径各实现一次（dsh-log tail 的终端格式化、面板的 src/bilingual.ts）。
  • 新增一个字段要改三处：发射点、事件清单、负向断言用例。这是用「写三处」换「日志行永不夹带文本」。
  • 需要人读的细节（例如错误原因）只能给稳定码 + hash8；排查细节要去面板的 detail 或工具返回的 steps[]。
  • 回退线也写清了：若实测发现某类问题只能靠文本才能查，走破冰新增一个具名字段，而不是放开任意文本。

10集成方视角：拿到了什么、要做什么

对使用本更新系统的插件作者，这次集成带来的收益是「默认就有」，成本是「几乎为零动作」。

默认就有（不用做任何事）

  • 宿主侧一段接线之后，日志自动落到 <DSH_HOME>/logs/<你的命名空间>/；
  • 面板侧挂载组件后，客户端日志自动经 <prefix>.logAppend 回宿主落盘；

  • 多插件共存由机制保证（目录分离 + 登记表 + 路由表），不需要你协调别人。

可以覆盖（可选）
