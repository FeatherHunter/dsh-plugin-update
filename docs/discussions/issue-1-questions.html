基本信息

这个包是干什么的：dsh-plugin-update 给任意 DSH 插件提供「检查更新 / 安装更新」的能力。它向调用方交出三个电话名与处理器（查状态、查新版、装更新），自己负责版本比较、落盘（state.json / install.lock / before.json）、超时与凭证，以及**怎么把新版装进当前使用范围**。

两代宿主：这套系统最早是在第三方 DSH 桌面端（anywhere-labs 那一支）下开发的，现在跑在官方桌面版 0.2.0-rc.2 上。

时代 A · 第三方 Desktop时代 B · 官方桌面版 0.2.0-rc.2
「我是桌面」的信号发布 desktopProfiles不发布；该服务与 desktopPnpm 在 app.asar 里 0 命中
安装出口desktopPnpm.runPlugin(argv, 范围目录)进程内 pluginManager.installBundle(spec, 选项)
自己起子进程可用不可用：argv[1] 是宿主入口，认不出 CLI 入口
命令行兜底dsh plugin --profile <名> add …CLI 按名字拒绝 --profile desktop
使用范围名由 launcher 决定固定 desktop

包里的隐含假设是「桌面宿主 = 发布那两项服务的那一支」。这个假设在时代 B 不成立，于是判定落回「普通宿主」，而命令行那条在这个宿主里必然认不出入口 ⇒ 装不上。现象是「很多用这个包的插件无法更新」，根因是缺一条宿主出口。

官方宿主出口的已知契约（只读取证，来自 app.asar 内文件）

  • pluginManager.installBundle(spec, { enabled?, requestId?, approvedBuilds?, registry? })；服务是 root 级，普通插件上下文 ctx.pluginManager 直接可取。
  • 返回 application ∈ {applied, restart-required, overridden, failed, cancelled}；预期失败不 reject，而是 resolve 出 failed ＋ error:{code, diagnostic}。
  • spec 是单个字符串，形如 name@x.y.z（全小写）；不接受任何开关。registry 是选项不是开关。
  • 管理器自己有静默超时（默认 10 分钟杀树）与写锁等待（默认 120 秒）；cancelInstall(requestId) 返回 {status:'cancelled'|'too-late'|'not-running'}。
  • 命令行 dsh 在 boot 与 plugin 子命令都拒绝 --profile desktop（唯一豁免是桌面自带的 CLI 载体）。

包内与宿主耦合的只有三处（我 grep 过全仓 environmentKind 的 21 处引用）：detectEnvironmentKind（认宿主）、installRecipe（选路由、拼参数）、createUpdateExecutor（两条执行分支）。查更新的那条链（读磁盘版本、查源、落盘、锁）与宿主无关。

C2 · 新路由的参数数组怎么表达？

宿主管理器只吃一个 spec 字符串（['add', '<包名>@<精确版本>']），而 pluginArgs 现在的注释是「追加在 plugin --profile <名> 之后的参数数组」——两者不是一回事。

为什么问：五键配方是冻结项，「注释里的定义」也算契约的一部分。

➡️ 我的推荐：选 (a)。配方五键是冻结项，放宽注释不动键；选 (c) 让适配器翻译，会把政策漏进跑腿层。

C3 · 「源」怎么带过去？

官方管理器把 registry 当**选项**（installBundle(spec, { registry })），不是开关。而本包的政策是「一律官方源、不可达即诚实失败，不换源」。

为什么问：这条路上源要么跟着配置走，要么如实说明「这个配置在这条路上不生效」。

➡️ 我的推荐：选 (b)。官方源政策在这条路上不丢，又不动配方形状；代价是这条路的源走注入零件而不是配方，我在 src/ports.ts 与 README 里注明。

C4 · 对消费方的兼容承诺怎么写？

environmentKind 多一个取值之后，调用方若有 switch 或不认这个值，应当怎么表现？

为什么问：ilife / dshmarket 各自都有一层适配，行为不写清就会出现多种解读。

➡️ 我的推荐：选 (a)。新增取值属向后兼容；写死「不认就当普通宿主」，消费方不用被迫升级。

C5 · 日志事件的值域扩展，要不要同步消费方的门禁？

update.install.exec 的 route 字段会多一个取值。

为什么问：消费方仓库有自己的日志门禁（verify-log-count 一类），值域变化可能让那边变红。

➡️ 我的推荐：选 (b)。字段名与事件条数都不变，但消费方（ilife、deck）各有一道日志门禁，改完去跑一遍确认不变红；哪边有枚举白名单就同步补上。

C6 · 要不要把官方宿主的契约抄一份进本仓？

官方宿主没有 .d.ts，最精确的契约是生成物里的内嵌声明；而本包现在依的契约是第三方 Desktop 的 plugin-services.md。

为什么问：这个 bug 的成因之一就是「宿主契约换了、包不知道」；同类问题还会再来一次。

➡️ 我的推荐：选 (a)。这次 bug 的成因之一就是「宿主契约换了、包不知道」；留一份写明出处与宿主版本的只读引用文档，下次有据可查。

D · 安装语义（对抗式）

D1 · 成功怎么判？

为什么问：overridden 的含义是「改动已被保留，只是被别的层盖住」；当失败会让上层回滚一次已经落地的改动。

➡️ 我的推荐：选 (a)。overridden 的含义是「改动已被保留、只是被别的层盖住」；把它当失败会让上层回滚一次已经落地的改动。

D2 · 管理器的 restart-required 与本包的 pending-restart，是一回事吗？

本包自己按「磁盘版本 ≠ 运行版本」判 pending-restart；管理器按「宿主里有没有 hmr」判 applied / restart-required。两个判据不同源。

为什么问：判据不同源，用户可能同时看到「宿主说装好了」和「本包说待重启」两句互相矛盾的话。

➡️ 我的推荐：选 (a)。面向用户的状态仍由本包自己的磁盘判据决定（八种 blockedReason 与面板文案都建在它上面）；宿主的 application 进日志与事件，不当第二套真相。

D3 · 失败原话要不要回给调用方/面板？

为什么问：票面验收写着「不得是一条不可诊断的死码」，但回包形状是冻结项——两者的取舍要你定。

➡️ 我的推荐：选 (a)。本单不动回包形状；宿主原话挂在执行器抛出的错与日志上。要让面板直接看到详情，另开一单走破冰。

D4 · 失败原话的脱敏做到什么程度？

error.diagnostic 通常是 pnpm 的输出，可能含路径、registry、令牌。

为什么问：本包有「日志里不记命令与路径原文」的纪律；回给面板的字符串是另一条出口，纪律管不管它，要你定。

➡️ 我的推荐：选 (b)。与日志纪律同一精神：截断（约 300 字）＋ 去掉绝对路径；error.code 原样保留。

D5 · 时限：installTimeoutMs 在这条路上要不要自己计时？

管理器自己有 10 分钟静默超时与 120 秒写锁等待，没有整体墙钟；配方里的安装时限默认 15 分钟。

为什么问：不写清，这个配置项在这条路上就是「静默失效」。

➡️ 我的推荐：选 (a)。对齐老路由「超时即终止」的语义，也让这个配置项在这条路上不静默失效。

D6 · 取消：超时或用户取消时调 cancelInstall(requestId) 吗？

它返回 {status:'cancelled'|'too-late'|'not-running'}；cancelled 会等托管进程退出并把 package.json / pnpm-lock.yaml 还原，too-late 表示已经进入应用阶段、改不动了。

为什么问：取消会还原两个文件，不取消则可能留下半个改动——这与本包自己的 job / before.json 收尾是同一件事的两面。

➡️ 我的推荐：选 (a)。取消会等进程退出并把两个文件还原，不会留半个改动；too-late 说明已进入应用阶段，等它自己结束再按 application 判最诚实。

D7 · enabled 选不选？

installBundle 默认 enabled: true＝装完即选为 bundle 层；官方 Web 插件页传的是 false，两个进程内参照实现都不传。

为什么问：两种语义不同，且决定更新之后插件是不是立刻生效。

➡️ 我的推荐：选 (a)。两条进程内参照实现都不传；官方 Web 页传 false 是因为它的语义是「先在清单里出现，再由用户启用」，与「更新」不同。

D8 · 管理器自己会在多个 registry 之间轮询，与「不换源」冲突吗？

为什么问：同一个包里两条源政策，会让「装不上」的原因变得不可预测。

➡️ 我的推荐：选 (a)。这条路上宿主拥有安装，源策略归它；在 README 写明「这条路由不强制官方源」。

D9 · 构建脚本被拦（pendingBuilds）算哪种结果？

pnpm 11 会拦构建脚本，管理器返回 pendingBuilds——即「包装上了但脚本没跑」。

为什么问：这是第三种半成品状态，现有八种 blockedReason 里没有对应项。

➡️ 我的推荐：选 (c)。本单只把它记进日志，不新增对外状态——对外状态与 D3 的冻结面是同一件事，另开一单做。

E · 并发与状态（对抗式）

E1 · 同进程内并发：锁的语义变了，靠谁？

老路由是跨进程子进程，本包的 install.lock 有效；新路由是进程内调用。

为什么问：两个插件（比如 ilife 与另一家）在同一个宿主里同时点安装时，期望行为是什么，现在没有约定。

➡️ 我的推荐：选 (a)。保持现状：本包的锁负责「同一个插件不重复发起」，宿主自己的写锁负责排队；把「不同插件并发会排队、超时即诚实失败」写进文档，发现真实损坏再另开单。

E2 · 取消/超时之后，本包自己的 job 与 before.json 怎么收尾？

本包有 job 状态与「半截任务」（recovery-required）这条原因。

为什么问：宿主的取消会自己还原两个文件，本包的回滚记录可能与它重复或冲突。

➡️ 我的推荐：选 (a)。宿主的还原与本包的记录互不冲突，先不新增状态；等真出现不一致再谈。

E3 · 宿主自己的安装入口也在动同一个 profile，怎么处理？

用户可以同时在「设置 → 插件」或 Web 插件页点安装。

为什么问：两条入口同时改一个 profile，最终状态谁说了算，现在没有约定。

➡️ 我的推荐：选 (a)。撞上就诚实失败，先不做忙闲探测——宿主自己的写锁已经在兜底。

E4 · 装完之后拿什么校验成功？

为什么问：管理器返回 changed:false 但磁盘版本已经对上时，算不算成功，需要一个口径。

➡️ 我的推荐：选 (a)。本包的判据是磁盘版本（面板文案都建在它上面）；changed / bundle 进日志当旁证。
