脱敏边界画在哪

Issue #6 · FeatherHunter/dsh-plugin-update · 讨论与定案记录 · 2026-10-02

一、这件事要解决什么

失败时，插件现在只能回一个纯错误码。要加一个可选的 diag 小诊断块给集成方，让它能定位问题。这个票专门回答一件事：诊断块里哪些内容可以放，哪些永远不放。

边界已经划好了，是上游 #5 定的不动：

  • 失败回包里加一个可选的 diag 对象，面板只认稳定错误码，看不懂 diag 也不影响行为。
  • 敏感信息必须在生成的时候就不产生，不是生成完再过滤。
  • 宁可这一项不给，也不要给原文。
  • 出问题的大小顺序：泄漏 > 崩溃 > 契约腐坏 > 误导 > 缺失。关联编号断掉单独算。
  • detail 这一项永远是给人看的一行字：300 字封顶，路径换成 <路径>。
  • 宿主传进来的原始错误文字叫 diagnostic，永远不过边界。

本票不动上面任何一条，只在它们下面填具体内容。

二、代码现状（实测，不是推测）

  • 系统里现在没有 diag。src/ 里搜不到这个词。所谓"诊断"现在只是一行 "错误码: 说明"，最长 301 字。
  • 脱敏函数只管一件事：把空白压成一行、把绝对路径换成 <路径>、截到 300 字。它不认识令牌、密码、URL 里的账号密码。
  • 它只服务一条路：桌面管理器报错。其余所有出口都不经过它。
  • 包内没有令牌遮蔽。唯一的 npm_*** 写在一个不随包发布的维护脚本里。
  • 日志侧已经关死了：三个日志事件的字段名被测试**逐字锁死**，多一个键就红。这是全仓最强的约束。注意执行者不是 gate.ts——checkEventFields 是个纯函数，读清单、算结果、返回 {ok}，不抛错、不记日志、不被任何生产代码调用。它那两栏"脱敏引用"（rules/codes）也全仓无人读，注释里"命中只记规则名不记原文"这个行为没有实现。
  • 全仓没有"永不外发"清单。安全完全靠每个事件各自列字段。
  • src/store.ts:929 有一行原始调用栈直接挂在错误对象上，不过滤、不截断。全仓只写不读，README 从未记载。

三、探针实测：找到三个已经在线上的问题

照抄现有脱敏规则，喂真实字符串，结果如下（脚本：.scratch/probe-redaction.js）：

输入现在的输出判定
ENOENT: ... open '/tmp/secret/data.json'原样吐出 /tmp/secret/data.json泄漏
at path:/tmp/secret/data.json原样吐出路径泄漏
open 'C:\Users\someone\secret'open '<路径>'正常
https://registry.npmjs.org/dsh原样（该保留）正常
https://user:sup3rpass@mirror…原样泄漏
token=abcd1234 secret: hunter2原样泄漏
401 for user alice@example.com原样泄漏
实测结论（已修）

Windows 分支正常，POSIX 分支漏。 因为 Windows 那条不要求前面有字符，而 POSIX 那条要求前面必须是行首或空格。Node 报告文件不存在时，路径是用单引号包着的——这正好是 POSIX 分支唯一漏掉的形状。

规则注释里写的是"保证回给用户的字符串里不留路径原文"。这句话是承诺，而实现只做到了"尽力"。这是实现没兑现自己的承诺，不是设计取舍。

顺带说明为什么一直没被发现：现有两条脱敏测试用的都是 Windows 盘符——恰好是能工作的那个分支。

已落地

前置条件放宽到行首、空白、引号、括号、方括号、等号、冒号、逗号；路径体要求至少一个字符，免得散文里孤立的一个斜杠被当成路径。

中途踩了一个自己挖的坑：第一版用「后面不是斜杠」来保住 URL，结果把 UNC 形状 //server/share 也放过了——而旧规则本来能掩它。用「有没有两个斜杠」当判据是错的，URL 的 :// 和 UNC 的 // 在字符上分不开。改成按位置判据：行首或空白后的 // 是 UNC 要掩，前置带冒号或字母的不是。

教训记进 ADR 与测试：收紧安全规则时，必须拿新规则去比对旧规则能覆盖的全部输入，只测新加的用例会漏掉自己制造的回归。已固化 3 条回归（UNC 行首 / UNC 空白后 / URL 路径内多斜杠）。

仍未覆盖并已记进票里：UNC 反斜杠形状 \\server\share（Windows 分支只认盘符形状）与 file:///tmp/x。属同一类泄漏，但本轮未实测到具体输入，不在本次修复范围。

四、贯穿全部五题的那句话

第一性原理

整个系统只守一条：任何由外部（宿主、包管理器）决定的文字，不许无限制地越过边界。

落地方式只有一句：在生成的时候就不让它产生。不做事后扫描。

下面每一题的"最终定案"，都是从这句话推出来的。

五、逐题

Q1 · "源地址"是什么？域名什么时候才能给？

诊断块里能不能放请求来源的地址？

背景

  • 本票原文问的是"源地址"能不能进。
  • 但 #5 定的字段表里只有 registryHost（源主机），没有"源地址"这个字段。两回事。
  • "客户端 IP"从未被批准过，属于个人信息。
  • registryHost 旁边有一句"仅安全时给"，但从没定义过什么算安全。
  • 本包政策是"一律官方源"，这意味着它本来就持有一份自己认可的源名单。

选项与取舍

选项优点缺点
给域名，只要不含点或后缀是内网常见后缀就跳过看起来具体，评审容易过靠猜。真实的内网名有无数种写法，名单永远漏；而且清单在，会让人以为已经处理过了，就不再追问
域名永远不给最省事，不可能出错诊断价值少一半。#5 验收场景里"装不上是不是源的问题"要靠它
一律给域名最有诊断价值把集成方的公司名、内网域名粘到公开 issue 里
只给本包认可的源；不在名单里就整项不给不靠猜，名单是本来就有的政策；漏不了用企业镜像的用户拿不到源信息
对抗式审查改了什么

我第一轮选的是"内网后缀黑名单"。自己审的时候推翻了：那份清单会永远漏，而且它制造虚假的安全感。换成"只给本包认可的源"——名单不是新造的，是"一律官方源"这条政策本来就蕴含的一个集合，不是新增的长期维护负担。

最终定案
  • 客户端 IP 永远不进（#5 没批准，且对"定位到下一跳"没有帮助）。
  • 只给域名，不带账号密码、端口、路径、查询参数。
  • 只给本包认可的源；不认可就整项不给。不用后缀黑名单。
  • 只在跟源有关的阶段出现（由 #18 已定的期望表表达，不另造机制）。
  • 不给本身就是信息：等价于"这不是官方源"。对读的人够用，且不泄漏任何东西。

Q2 · 脱敏该在哪一层做？

规则写在哪：生成的时候就不产生，还是生成完再扫一遍？

背景

  • #5 已定："脱敏是生成属性"，缺诊断宁可省略。
  • 现状：脱敏是个函数，只服务一条路，其余出口都不经过。
  • src/gate.ts 里预留了"脱敏引用"字段（规则名、截断代号），注释里写了 R_WIN_ABS、H_CWD 两个名字，但全仓没有任何代码读它们，也没实现。真正的路径规则没登记在任何清单里。

选项与取舍

选项优点缺点
生成完统一扫一遍，违规就遮住能兜住漏网遮住和"本来就没有"在产物上无法区分。诊断的全部价值是"读它的人可以相信它"，遮住等于把一次泄漏变成一次看不见的错。#5 也把"误导"排在"缺失"前面——遮住两头都输
给每个字段建一张表，运行时查表看着统一字段名（枚举）、数字、自己生成的编号，类型本身就管住了。真正的自由文本只有 detail 一项。为一项建一张表，是把类型系统已经做完的事重做一遍
运行时扫描 + 构造器 + 完备性检查，四层看着最保险四层意味着四处都要读、都有各自的错。而且最内层那层经不起推敲（见下）
生成时就不产生：一个自由文本函数 + 一个查表 + 其余交给类型代码最少；出问题只有一处可查；把 #5 那句话变成字面为真要求后来加字段的人走同一条路，靠代码评审保证
对抗式审查改了什么

我推翻了自己上一轮的核心结论。 我原先说"不留运行时扫描会导致规则变成第二份真相"。错在把"两个执行点"当成了"两份真相"——如果扫描和构造读的是同一张表，就只有一个真相。

但继续推下去，扫描自己被自己的顺序规则推翻了：先脱敏、再截断，那么截断只做减法，不可能凭空造出秘密。既然如此，截断后再扫一遍就是多余的。真正要防的从来不是"有人手搓字符串绕过构造器"（那是一行代码，评审看得见），而是顺序搞错——顺序写死就够了，不需要一层常驻扫描兜底。

四层被砍到不需要任何一层机制。留下的全部是：一个函数、一张表、几个判断、删一行。

最终定案
  • 枚举、数字：类型本身管住，运行时零成本。
  • 取不到来源的项：不写。
  • detail：全系统唯一的自由文本，产出口只有一条路。
  • 关联编号：本包自己生成（见 Q3），不需要校验。
  • 不引入运行时扫描，不建逐字段清单，不建完备性检查。
  • #18 已经定好的"阶段×字段期望表"断言，本身就是最严格的门禁：新增字段必须回答"它在哪些阶段出现"，加不出静默。

Q3 · 关联编号能不能原样给出？

requestId 和 checkId 是不可控的外部字符串，要不要原样贴出去？

背景

  • #5 把这两个定成"跨回包/日志/任务记录"的关联锚，并把"关联断裂"单独列进风险。
  • 两条路分开看，结论不一样：
    • 执行器 → 宿主：requestId 是我们生成的（src/store.ts:817 用 randomUUID()），形状本来就在我们手里。
    • 接入方 → 公开电话：args.requestId 来自接入方，只过 validRequestId——它只校验"非空、trim 后 ≤128 字符"，任何字符都放行（src/service.ts:36-38）。路径、令牌形状的字符串都能通过。
  • 也就是说，要放进诊断块的那个值，是外部来的、只查了长度的。
  • checkId 由本包 ports.randomId() 生成（src/service.ts:444），形状可控。

选项与取舍

选项优点缺点
原样贴出最简单在赌第三方不在里面塞东西
过一遍脱敏保险会把编号里的斜杠换成 <路径>——等于告诉集成方"你的编号有问题"却不说哪有问题。误导，而且这个编号在宿主那边根本不是路径
改成短哈希安全直接砍掉 #5 唯一认定的关联手段，日志那边对不上
两个都自己生成，形状固定，不做运行时校验形状由构造保证、由测试锁死，校验分支整个消失；面板永远能关联跨宿主那道边本来就只能尽力而为——得在 ADR 里写明，不能假装它是保证
对抗式审查改了什么

我第一轮建议"校验形状，不合规就不给"。改成"自己生成"之后，那个校验分支不存在了——不是变简单，是整条路径被删除。这正是"生成时不产生"该有的样子。

同时我把一句说过头的话收回来了：不能说"一定出现"，只能说"确实传给宿主时才出现"。

最终定案
  • 两个编号由同一个生成函数产出，形状固定。
  • 不做运行时丢格。
  • 只在确实传给宿主时，才出现在诊断块里。
  • 跨宿主的关联是尽力而为，这一点必须写进 ADR。
  • 但不收紧 validRequestId。它是已公开的公开契约，收紧会影响现有接入方，属破冰。现状（只查长度）连同这个判断一并记进票与 ADR，留给规格阶段。
第三轮审查补正

我先前把 Q3 的背景写成「requestId 是我们自己生成的」，只对了一半。实际是两条路：

  • 执行器 → 宿主：randomUUID() 自产，形状在我们手里。
  • 接入方 → 公开电话：args.requestId 来自接入方，只过 validRequestId——它只校验「非空、trim 后 ≤128 字符」，任何字符都放行。

也就是说，要放进诊断块的那个值，是外部来的、只查了长度的。这比我原先写的更具体，也正因如此才需要单独立一条推迟项。

Q4 · 拦哪些形状？拦下来之后遮住还是丢掉？

敏感信息抓到之后，是替换成占位符，还是整项丢弃？

背景

  • 全仓现在没有"永不外发"清单。#18 写了"不得出现秘密形状"，但"秘密形状"没定义。
  • <路径> 这个占位符本身就是"遮住"，而且是 #5 冻结的。
  • 探针实测：URL 里的账号密码、令牌、密码键值对、邮箱，今天全部原样通过。
  • 但"响应正文原文""安装输出全文""调用栈"不该出现在这张清单里——它们根本不该被拼进来，是生成时就不拼，跟文字无关。

核心取舍：遮住 vs 丢掉

遮住（替换成占位符）丢掉（整项不给）
产物长什么样看起来像处理过了就是少了一项
出事时能看出来吗看不出来。和"本来就没有"完全一样能看出来
对照 #5 风险顺序属于"误导"，排在"缺失"前面属于"缺失"，排在最后
最终定案 · 一条可判定的规则

能明确找到秘密的起止位置 → 就地换成占位符。找不到 → 整项丢弃。

绝不用"盖住一部分"去处理"不知道剩下的是什么"。

判据是机械的：路径终止于空白（找得到）；URL 账号密码可能自身含 @（起止不唯一 → 整项丢掉）。这条规则最后产出的确实是"丢掉"，说明它不是装饰。

五条规则

抓什么动作占位符
绝对路径（Windows 盘符 / POSIX，一条规则两种形状）替换<路径>（冻结，不动）
URL 里的账号密码整项丢弃—
令牌前缀（npm_ / ghp_ / sk- / Bearer）替换<脱敏>
密码键值对（token= / password= / api_key= / cookie=）替换<脱敏>
邮箱替换<脱敏>

只有两个占位符。路径是唯一结构上可识别的类别，其余一律 <脱敏>——不值得为每种秘密建一套分类。

被剔出清单的三样（它们是生成问题，不是文字问题）

  • 响应正文 / 安装输出全文 → 自由文本的入口根本不接受这类参数。
  • 调用栈 → 见 Q5。
  • 内网主机名 → 不是高准确度的标记，是猜的，不进清单。detail 里出现源主机名是分工结果，源信息的隐私由 Q1 那个结构化项承担。

处理顺序

压平空白 → 五条规则依次跑 → 300 字封顶

顺序只是为了输出稳定，不是为了正确性（两种顺序实测输出相同）。另外：封顶之后不再扫描，因为截断只做减法，扫不出新东西。

对抗式审查改了什么

我第一轮建议"结构化字段丢掉、自由文本遮住"。自由文本那半是错的，理由就是上面那张对照表：遮住会销毁泄漏的证据，等于把一次泄漏变成一次静默的错误。

另外实测推翻了我另一个预测：我以为"令牌规则必须排在路径规则前面，否则路径会被标成凭据"。实测两种顺序输出相同（令牌规则的匹配范围把路径一起吃掉了），这条多余的约束已从方案里删掉。

最终定案
  • 五条规则如上，规则表按顺序执行（只为输出稳定）。
  • 替换 or 丢弃，按"起止能不能唯一确定"判断。
  • 两个占位符：<路径>、<脱敏>。
  • 每条规则必须有两套测试：一套"必须被处理掉"，一套"不能被误伤"。这不只是保险——探针已经证明只做单向会漏。
  • detail 300 字封顶保持不动（冻结口径）。
  • 额外补一条断言：序列化后的整个诊断块不得超过 #5 写的小诊断块上限。理由：300 个汉字就是 900 字节，加上来源信息可能越过 #5 说过线要破冰的那条线。把假设变成会响的测试。

Q5 · 那行原始调用栈怎么办？

src/store.ts:929 把完整的 error.stack 原文挂在错误对象上，不过滤、不截断。

背景

  • 调用栈里全是 file:///D:/… 绝对路径和完整调用过程。
  • 已核实：全仓只写不读，README 从未记载，删掉不改变任何外部行为。
  • 但 #18 落地后，诊断块会第一次有正式内容——而没有任何东西拦着这行代码进去。

选项与取舍

选项优点缺点
删掉这一行最干净，零读者零损失不防止将来有人再加回来
保留但走同一套脱敏保留原能力为一个零读者的字段养一条脱敏路径。#5 的取向是泄漏第一，但不为不存在的需求付维护费
代码不动，加一条 grep 检查防将来加回来是已有负向测试的更弱版本，属于重复
删掉这一行消掉现存唯一一处违规靠测试兜底（见下）
对抗式审查改了什么

我第一轮建议"删掉 + 加 grep 门禁"。grep 门禁被自己否掉了：#18 已经要求对产物做负向断言（"载荷里不得出现秘密形状"），而 grep 只是它的更弱版本。真有人把这行接回边界，负向测试先响。

最终定案
  • 删掉 src/store.ts:929 那一行。不留替代方案，不加 grep 检查。
  • 真要留调用栈，它的归宿是 #8 的本地落盘（不外发、可查），不是挂在一个即将被读的错误对象上。
